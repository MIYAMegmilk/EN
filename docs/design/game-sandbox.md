## 0. 確定している方針（オーナー判断済み）

1. **第1段はチーム製ゲームのみ。** ユーザー投稿は受け付けない。ゲームはリポジトリに入り、
   PR レビュー（人間の承認、§DoD）を通る。ユーザー投稿の受付は**第2段として構造だけ見据える**
   （本書では移行の要件のみ書き、実装しない）。
2. **置き場所は `public/games/*.js` + 一覧のマニフェスト**（§6）。
3. **サンドボックスゲームは公式スコアに算入しない。**
   ゲームロジックがクライアント側にあるため、自己申告のスコアは改造クライアントで盛れる。
   §3.2 原則1（サーバーが唯一の状態機械）を曲げないために、
   **順位が付くゲームは既存エンジン側／サンドボックスは場を盛り上げるもの**、と住み分ける。
   **サンドボックスゲーム自身の中での勝敗表示は自由。**

## 1. 位置づけ

### 1.1 何を解くか

既存のゲームエンジン（`server/engine.ts`）は **宣言的データ `GameDefinition`** でゲームを定義する。
サーバーが唯一の状態機械なのでチートが構造的に不可能で、これは §3.2 原則1 の核である。
ただし採点方式が **vote / match / correct の3つしかなく**、
入力も `text` / `choice` の2つしかない（§3.5）。

結果として「回答を集めて投票／一致／正解判定する」型のゲーム以外は**1本も作れない**。
反射神経・お絵かき・リアルタイムに動くものは、お題をいくら足しても作れない。

チームが自分たちでゲームを増やせるように、**JS で書いたゲームをブラウザ内のサンドボックスで
動かす仕組み**を、既存エンジンと**並列に**追加する。既存エンジンには一切手を入れない。

### 1.2 既存エンジンとの住み分け

| | 既存エンジン（§3.3〜3.5） | サンドボックスゲーム（本書） |
|---|---|---|
| ゲームの記述 | 宣言的データ `GameDefinition` | JavaScript（`public/games/*.js`） |
| 状態機械 | **サーバー**（§3.2 原則1） | **クライアント**（ホスト役のブラウザ） |
| サーバーの役割 | 進行・採点・可視範囲の制御 | **payload を解釈しない中継のみ**（§4） |
| チート耐性 | 構造的に不可能 | **防げない**（§7.3） |
| 公式スコア | 算入する（`ScoreEntry`） | **算入しない**（方針3） |
| フェーズ | `lobby→intro→…→finalResult`（§3.3） | フェーズを持たない。`lobby` 中の余興として動く |
| 秘密の保持 | できる（`PhaseView` が受信者ごとに違う） | **できない**（送った payload は同室全員に届く） |
| 誰が作れるか | 全員 + ユーザー（スタジオ §3.5） | **第1段はチームのみ**（PR レビュー必須） |
| 実行の隔離 | 不要（コードを実行しない） | iframe opaque origin + CSP（§2） |

### 1.3 どちらで作るべきかの判断基準

| 作りたいものの性質 | 選ぶ側 | 理由 |
|---|---|---|
| 順位・得点を宴の公式スコアに乗せたい | **既存エンジン** | 方針3。サンドボックスの得点は自己申告 |
| 「回答 → 投票 / 一致 / 正解」に収まる | **既存エンジン** | 既に動く。追加コストが最小 |
| お題を足すだけ | **既存エンジン**（スタジオ §3.5） | コードを書く必要が無い |
| 正解や他人の回答を**隠す**必要がある | **既存エンジン** | サンドボックスは全員に配るので隠せない |
| 毎秒動く・描画がいる（反射神経・アクション） | **サンドボックス** | フェーズ機械に乗らない |
| 独自ルールで3つの採点方式に収まらない | **サンドボックス** | 型を増やさずに済む |
| 短命なネタゲーム（1回の飲み会で使い捨て） | **サンドボックス** | 仕様書・型の変更が要らない |

**迷ったら既存エンジン。** サンドボックスは「既存エンジンでは表現できないと確認できたとき」の逃げ道であり、
既存エンジンで作れるものをサンドボックスで作ると、公式スコアに乗らないぶん損をする。

### 1.4 §3.5 ゲームスタジオとの関係（混同されやすい）

**この2つは別物である。** どちらも口語では「自作ゲーム」と呼ばれるため、必ず用語を分ける。

| | ゲームスタジオ（§3.5・既存仕様） | サンドボックス（本書・新規） |
|---|---|---|
| 呼び方 | **投稿ゲーム** | **サンドボックスゲーム** |
| 「自作」の主語 | **ユーザー**が作る | **チーム**が作る（第1段） |
| 中身 | 宣言的データ（`GameDefinition`） | JavaScript のソース |
| 保存先 | Deno KV（`game:{id}`、1アカウント50件） | **Git リポジトリ**（`public/games/`） |
| 共有 | 共有コード8桁・`/g/{shareCode}` | 共有しない（リポジトリに入る＝全ルーム共通） |
| 実行 | 既存エンジン | サンドボックス runner |
| ログイン | 作成・編集は必須 | 作る人＝チーム。実行はゲスト可 |
| 任意コード実行 | **無い**（§3.5 の「実行可能スクリプトは受け付けない」） | **ある**（だから §2 の隔離が要る） |

**重要**: §3.5 の「GameDefinition は実行不能な宣言的データのみのため、任意コード実行のリスクは
構造的に存在しない」という規定は**スタジオの規定であり、本書はこれを変更しない**。
スタジオは今後も宣言的データのみを受け付ける。サンドボックスはスタジオの入口を通らない、
**別の経路**である。

`studio.html`（担当【後決め】）からサンドボックスゲームを編集・投稿できるようにするのは**第2段**であり、
第1段では `studio.html` に一切手を入れない。

## 2. 隔離の設計

### 2.1 四重の壁

ユーザーコード（第1段はチーム製コードだが、**悪意あるコードを前提に**設計する）に対して、
以下を重ねる。1〜3 はプロトタイプで実測済み、4 は設計規約。

1. **`<iframe sandbox="allow-scripts">`（`allow-same-origin` を付けない）** → 不透明オリジン
2. **runner ページ専用の CSP**（`default-src 'none'` / `connect-src 'none'` / `worker-src 'none'` …）
3. **親はユーザーコードを評価しない**（文字列のまま postMessage で渡す）
4. **サーバーは payload を解釈しない**（§4）

### 2.2 `sandbox="allow-scripts"` — `allow-same-origin` を付けない

```html
<iframe sandbox="allow-scripts"
        referrerpolicy="no-referrer"
        title="ゲームサンドボックス"
        src="/sandbox/runner.html"></iframe>
```

- `allow-same-origin` を**付けない**ことで、その文書は**一意の不透明オリジン（opaque origin）**になる。
  親の DOM・`document.cookie`・`localStorage` / `sessionStorage`・IndexedDB のいずれにも触れない。
  **実測**（16項目、実 Chrome 2窓）で全て阻止を確認済み。
- `allow-scripts` と `allow-same-origin` を**両方**付けると、サンドボックス内のスクリプトが
  自分で `sandbox` 属性を外せてしまう。**この組み合わせは使わない。**
- `allow-popups` を付けないので `window.open` は不発（**実測**）。
  `allow-top-navigation` も付けないので親ごとの遷移もできない。
- **属性の綴りを間違えると隔離が丸ごと消える**ため、iframe の生成は
  `public/room/sandbox.js` の1関数に閉じ込め、他の場所で iframe を作らない（§9.2）。

### 2.3 runner ページの CSP

**プロトタイプが配った値（実測で16項目を阻止したもの）:**

```
default-src 'none';
script-src 'self' 'unsafe-eval';
script-src-elem 'self';
style-src 'unsafe-inline';
img-src data: blob:;
connect-src 'none';
worker-src 'none';
child-src 'none';
frame-src 'none';
object-src 'none';
base-uri 'none';
form-action 'none';
```

本実装では、これに **`frame-ancestors 'self'` をレスポンスヘッダーで追加**する（§2.6 / §7.4）。

各ディレクティブの理由:

| ディレクティブ | 理由 |
|---|---|
| `default-src 'none'` | 既定で全ての読み込みを禁止。書き忘れたディレクティブが素通りしないようにする |
| `script-src 'self' 'unsafe-eval'` | `runner.js` の読み込みと `new Function` によるゲーム評価。**このページの唯一の役目がユーザーコードの実行**なので、ここだけは許す |
| `connect-src 'none'` | **fetch / XHR / WebSocket / EventSource / sendBeacon を全面禁止**。外へデータを持ち出す経路と、外から追加コードを取り込む経路の両方を塞ぐ。**実測**で fetch / XHR / WebSocket の阻止を確認 |
| `img-src data: blob:` | canvas が生成した描画結果のみ。**外部画像の読み込みは実測で阻止** |
| `style-src 'unsafe-inline'` | インライン `<style>` のみ。外部 CSS は読めない |
| **`worker-src 'none'`** | **後述（§2.4）。実測で見つかった穴** |
| `child-src` / `frame-src 'none'` | 入れ子 iframe による同種のフォールバック経路を塞ぐ |
| `object-src 'none'` | プラグイン埋め込み |
| `base-uri 'none'` | `<base>` 差し替えによる相対 URL の乗っ取り |
| `form-action 'none'` | フォーム送信による外部遷移（`connect-src` では塞げない経路） |

**多層化**: 同じ CSP を **`runner.html` の `<meta>` とサーバーのレスポンスヘッダーの両方**に書く。
正本はヘッダー側とする（meta タグは配信物の書き換えや将来の編集で落ちうるため。
既に適用済みのポリシーが meta の削除で解除されるわけではないので、
これは「経路の取り違え」に対する保険である）。

### 2.4 `worker-src 'none'` — プロトタイプで実測した穴

**これは書き忘れてはいけない。実測で見つかった実際の突破経路である。**

CSP は `worker-src` を持たない場合、`script-src` にフォールバックする。
`script-src 'self'` なので、`new Worker("/なにかの.js")` が**通ってしまう**。
そして **Worker は自身のレスポンスヘッダーで独自の CSP を持つため、
親文書の `connect-src 'none'` を引き継がない**。
結果、Worker の中から fetch / XHR / WebSocket で外部通信できる。

プロトタイプではこれを**実測で確認し、`worker-src 'none'` を追加して塞いだ**。
`child-src` / `frame-src` も同じフォールバック構造を持つため明示している。

**教訓として本書に残す**: `default-src 'none'` を書いても、フォールバック規則があるディレクティブは
安心できない。CSP を変更するときは、**フォールバック先が何になるかを毎回確認する**。

### 2.5 親側の検証 — `event.origin` は使えない

**これはプロトタイプで実測した、最も間違えやすい点である。**

`allow-same-origin` を付けない iframe の文書は不透明オリジンなので、
そこから来る `postMessage` の **`event.origin` は文字列 `"null"`** になる
（サンドボックスの URL ではない）。

```js
// ✗ これは動かない。正しく設定できていても全メッセージが弾かれる
if (event.origin !== SANDBOX_ORIGIN) return;

// ✓ 自分が作った iframe の contentWindow そのものかを参照の同一性で検証する
if (state.frame === null || event.source !== state.frame.contentWindow) return;
```

ウィンドウ参照は偽装できないので、`event.source` の同一性検証が正しい方法になる。
**実測**でプロトタイプの親ページは `event.origin === "null"` をログに出して確認している。

同じ理由で、**親から runner へ送るときの `targetOrigin` は `"*"` にせざるを得ない**
（不透明オリジンは名前で指定できない）。宛先の同一性は
「自分が生成した iframe の `contentWindow` にだけ送る」ことで担保する。
したがって **postMessage に認証情報（session / entryToken / Cookie 由来の値）を一切載せない**
ことを規約とする（載せてよいものは §4.4 に列挙）。

runner 側の検証は逆向きに `event.source === window.parent` を使う（§3.3）。

### 2.6 【設計判断】別オリジン vs 同一オリジンの別パス

プロトタイプは **別ポート（= 別オリジン）** で runner を配信していた（8001 / 8002）。
本番は単一オリジン（`162-43-46-65.sslip.io`）で、
Deno 単一プロセス + Caddy の TLS 終端という構成（§6 / §5「単一プロセスデプロイが前提」）である。

#### 比較

| 観点 | A. 別サブドメイン（`sandbox.<host>`） | B. 同一オリジンの別パス（`/sandbox/runner.html`） |
|---|---|---|
| opaque origin による隔離 | 効く | **同じく効く**（sandbox 属性が origin を潰すので、配信元がどこでも結果は同じ） |
| CSP `connect-src 'none'` | 効く | **同じく効く** |
| 実測16項目 | 実測済み | **未実測**（構成が違うので再実測が要る。§8.2） |
| sandbox 属性を書き忘れた場合 | 別オリジンなので Cookie / localStorage には届かない（**多層防御の1枚が残る**） | **アプリのオリジンで実行されてしまう**（致命的） |
| ブラウザ側のバグ・仕様差 | 二重に守られる | 一重 |
| Caddy | **サイトブロック追加**（証明書取得が要る） | 変更不要 |
| Deno | 2ポート待受 or ホスト名ルーティング | **変更不要** |
| runner が親オリジンを知る方法 | 教えてもらう必要あり。`connect-src 'none'` のため runner は自分で `/config` を fetch できず、プロトタイプは `?appOrigin=` クエリで渡していた（＝親の自称値を信じている。プロトタイプの既知の限界5） | **`new URL(location.href).origin` で自力導出できる**（自称値に頼らない） |
| ゲームコードの配信 | 親オリジンのみで配信し、サンドボックスオリジンでは 404 にする分離が可能（実測） | 同一オリジンだが、`connect-src 'none'` のため runner から fetch できないので経路は無い |
| 第2段（ユーザー投稿）への適性 | **適する** | **不足**（下記） |

#### 推奨: **第1段は B（同一オリジンの別パス `/sandbox/runner.html`）**

理由:

1. **隔離の主力は sandbox 属性（opaque origin）と CSP であり、配信元オリジンではない。**
   実測16項目のうち、別オリジンでなければ阻止できないものは無い
   （親 DOM・Cookie・localStorage・IndexedDB は opaque origin が、
   fetch / XHR / WebSocket / Worker / 外部画像は CSP が阻止している）。
   別オリジンは「sandbox 属性を書き忘れた場合の保険」として効く多層防御の1枚である。
2. **第1段はチーム製コードのみで、PR レビューを通る**（方針1）。
   「悪意あるコードが常に入ってくる」前提ではないため、保険の1枚を落としても釣り合う。
3. **VPS 構成を増やさない。** §5 の「単一プロセスデプロイが前提」を崩さず、Caddy のサイト追加・
   追加の証明書取得・追加ポートが不要。sslip.io のサブドメインで証明書が問題なく取れるかは
   **未検証**であり、ここに検証コストを払う価値が第1段では薄い（§10-2 / §10-1）。
4. **プロトタイプで一番ややこしかった部分が消える。** 別オリジン構成では runner が
   `connect-src 'none'` のせいで自分の `/config` を読めず、親オリジンをクエリで受け取る
   （＝親の自称値を信じる）羽目になっていた。同一オリジンなら
   `new URL(location.href).origin` で自力導出でき、`/config` エンドポイントも
   `?appOrigin=` クエリも不要になる。

#### B を選ぶ場合の**必須**の補償措置（1つでも欠けたら B は成立しない）

1. **runner レスポンス専用のヘッダー分岐。**
   現在 `server/main.ts` の `SECURITY_HEADERS` は `serveDir` の全レスポンスに一律で付いている。
   `/sandbox/` 配下だけは §2.3 の CSP に差し替える。
2. **`frame-ancestors 'self'` を runner レスポンスに付ける。**
   **重要**: 現在の `SECURITY_HEADERS` は **`frame-ancestors 'none'`** を全レスポンスに付けている。
   このままだと **自分のページから自分の runner を iframe に入れられない**（**想定**。要実測）。
   runner のみ `'self'` に緩める。同時にこれは「外部サイトが sandbox 属性なしの `<iframe>` で
   runner を埋め込み、**アプリのオリジンで**ユーザーコードを走らせる」経路を塞ぐ、
   B にとって必須の防御でもある。
3. **runner.js の自己防衛ガード。**
   runner は起動時に「自分が不透明オリジンの子フレームに居ること」を確認し、
   そうでなければ**ゲームコードの評価を一切しない**。

   ```js
   // 想定: 不透明オリジンの文書では self.origin が "null" になる。ブラウザ差は要実測（§8.2 #17）
   var isolated = (self.origin === "null" || self.origin === null) && window.parent !== window;
   if (!isolated) { setStatus("隔離されていない文脈では実行しません"); return; }
   ```

   これにより、万一 `frame-ancestors` を回り込まれても、
   また誰かが `/sandbox/runner.html` をトップレベルで直接開いても、コードは動かない。
4. **親側の `frame-src`。** アプリの CSP は `default-src 'self'` 基調なので同一オリジンの
   iframe は既に許可されている（`frame-src` の追加は不要。**想定**、要実測）。

#### 第2段（ユーザー投稿を受け付ける）に進むなら何が要るか

B のままユーザー投稿を受け付けてはいけない。以下がまとめて必要になる。

- **A（別オリジン）への移行。** 投稿コードは「常に悪意がある」前提になるため、多層防御の1枚を捨てられない。
  移行コストを iframe の URL 組み立て1か所に閉じ込めるため、**第1段から `src` の組み立てを
  `public/room/sandbox.js` の定数1つに集約しておく**（設計上の前借り）。
- **Worker 化 + 実行時間監視**（§7.1）。無限ループでタブが固まるのを受容できなくなる。
- 投稿コードの保存先（KV or ファイル）、サイズ上限、件数上限（§3.5 の 1アカウント50件・64KB に倣う）。
- 通報導線（§3.7）とホスト承認、公開範囲の制御。
- `frame-ancestors` を A のオリジンに固定し、runner の CSP を再実測。

## 3. ランタイム API（`EN`）

runner はゲームコードに **グローバル `EN` だけ**を渡す。
`new Function("EN", code)` の引数として渡すため、ゲームは `EN` を必ず参照できる。

### 3.1 プロトタイプの API と本実装での扱い

| API | プロトタイプ | 本実装 | 変更理由 |
|---|---|---|---|
| `EN.onStart(fn)` | あり | **維持**（引数を拡張） | 途中参加の情報が要る |
| `EN.onPeer(fn)` | あり | **維持** | |
| `EN.onMessage(fn)` | あり | **維持** | |
| `EN.onInput(fn)` | あり | **維持**（イベント種別を追加） | 移動系ゲームが作れない |
| `EN.draw(fn)` | あり | **維持** | |
| `EN.send(msg)` | あり | **維持**（サイズ上限を追加） | §4.3 |
| `EN.log(msg)` | あり | **維持** | 開発時のデバッグ経路 |
| `EN.size` | あり | **維持** | |
| `EN.isHost` / `EN.youId` | あり（getter） | **維持** | ホスト交代で変わるため getter のまま |
| `EN.setScore(n)` | あり | **廃止 → `EN.setStatus(text)`** | 方針3。親に「スコア」欄があると公式スコアと誤認される（§10-4） |
| `EN.onEnd(fn)` | 無い | **追加** | ホストがゲームを畳む経路が要る（§5.2） |
| `EN.now()` | 無い | **追加**（提案） | 「ホストが合図を出す」型の同期に共通の時計が要る（§10-10） |

### 3.2 確定させる API（第1段）

```js
/**
 * ゲームコードに渡される唯一のグローバル。
 * これ以外（window / document / fetch / localStorage …）に触ってはならない。
 * 触っても隔離で失敗するが、失敗の仕方はブラウザ依存なので当てにしない（§7.2）。
 */
EN = {
  // --- 情報（読み取り専用） ---
  youId,          // string             自分の playerId
  isHost,         // boolean            自分がホストか（getter。ホスト交代で変わる）
  size,           // { width, height }  canvas の論理サイズ（480 x 320）

  // --- コールバック登録（各1本のみ。2回目の登録は上書き） ---
  onStart(fn),    // fn({ youId, isHost, peers, joinedLate })  開始時に1回
  onPeer(fn),     // fn({ kind: "join"|"leave", id, nickname })
  onMessage(fn),  // fn(fromPlayerId, msg)   他の参加者からの EN.send
  onInput(fn),    // fn({ type, x, y, key })
  onEnd(fn),      // fn()  ホストが終了した / 親が iframe を畳む直前
  draw(fn),       // fn(ctx, dt)  毎フレーム。dt は秒（0.1 で頭打ち）

  // --- 動作 ---
  send(msg),       // 同室の他の全員へ。自分には返らない。true=送れた / false=破棄された
  setStatus(text), // 親のヘッダーに短い文字列を出す（textContent 描画。80文字で切る）
  log(msg),        // 親のログ欄へ（開発用。500文字で切る）
  now(),           // サーバー時刻に補正した epoch ms（全員でほぼ一致する）
};
```

**`onStart` の引数**（プロトタイプから `joinedLate` を追加）:

```js
{
  youId: "…",                      // 自分の playerId
  isHost: true,                    // 開始時点でホストか
  peers: [ { id, nickname }, … ],  // 自分を含まない同室の参加者
  joinedLate: false                // true = 既に始まっているゲームに後から入った（§5.3）
}
```

**`onInput` のイベント種別**（プロトタイプに2種を追加）:

| `type` | `x` / `y` | `key` | 備考 |
|---|---|---|---|
| `pointerdown` | canvas 論理座標 | `null` | プロトタイプにあり |
| `pointerup` | canvas 論理座標 | `null` | プロトタイプにあり |
| `pointermove` | canvas 論理座標 | `null` | **追加**。runner 側で 60Hz に間引く |
| `key` | `0` | `event.key` | keydown。修飾キー付き（Ctrl/Meta/Alt）は runner が無視する |
| `keyup` | `0` | `event.key` | **追加** |

### 3.3 runner が守る規約（ゲームコードを信用しない）

プロトタイプの `runner.js` が既に実装しており、本実装でも維持する。

- **送信元の検証。** 親からのメッセージは `event.source === window.parent` を必ず確認する
  （同一オリジン構成では `event.origin` も自オリジンと一致するが、**判定の主は `event.source`**）。
- **`safeCall()` で必ず包む。** ゲームのコールバックが例外を投げても runner は死なず、
  親に `{ t: "error" }` を送って次のメッセージを受け付け続ける。
- **`window.onerror` / `unhandledrejection` を拾う。** 投げっぱなしの非同期例外も親に伝える。
- **`EN.send` のトークンバケット。** クライアント側で **30件/秒**（プロトタイプ実測値）に絞り、
  サーバーのソフト上限（§4.3）より内側に収める。破棄した件数は
  1件目と60件ごとにだけ `log` で知らせる（通知の洪水を防ぐ）。
- **二重読み込みの拒否。** `loadGame` は1回だけ。再読込は iframe を作り直す
  （前のゲームが残した `setInterval` / `requestAnimationFrame` / リスナを確実に捨てるため）。
- **`dt` の頭打ち。** タブ復帰などで `dt` が跳ねるとゲーム側の計算が壊れやすいので 0.1 秒で止める。
- **受信 payload のスキーマ検証。** 親から来る `peer` / `message` / `host` の各フィールドを
  型チェックし、壊れた要素は落とす。
- **表示は `textContent` のみ**（§3.8）。runner に `innerHTML` を書かない。

## 4. サーバー側に必要なもの

### 4.1 設計原則

**サーバーは payload を解釈しない。** §3.8 の `rtcSignal` と完全に同じ扱いにする。
サーバーが守るのは **形式・サイズ・レート・中継先** の4つだけで、ゲームのルールは知らない。
これにより「サンドボックスゲームがサーバーを壊す経路」が構造的に存在しなくなる。

サーバーが**知る**のは「どのゲームが動いているか（`gameId`）」だけである。
これは途中参加者に同じゲームを配るために必要で、`gameId` はマニフェスト（§6）の
ホワイトリストに載っているものだけを受理する。

### 4.2 C2S / S2C の型（提案）

`server/types.ts`（型の正本、§4.3）に追加する。**チーム合意必須。**

```ts
// ---------------------------------------------------------------------------
// サンドボックスゲーム（docs/design/game-sandbox.md）
// ---------------------------------------------------------------------------

/** 稼働中のサンドボックスゲーム。サーバーは gameId 以外の中身を知らない */
export type SandboxGameState = {
  /** マニフェスト（public/games/manifest.json）に載っているゲームID */
  gameId: string;
  /** 開始した playerId（開始時点のホスト） */
  startedBy: string;
  /** 開始時刻（epoch ms）。途中参加者の表示に使う */
  startedAt: number;
};

/** マニフェストの1件。GET /api/sandboxGames が返す */
export type SandboxGameInfo = {
  id: string;
  title: string;
  description: string;
  /** public/games/ 配下のファイル名（= id + ".js"） */
  file: string;
  minPlayers: number;
  maxPlayers: number;
  author: string;
};
```

```ts
// C2S に追加
  /** サンドボックスゲームを開始する（host only、docs/design/game-sandbox.md） */
  | { t: "sandboxStart"; gameId: string }
  /** サンドボックスゲームを終了する（host only） */
  | { t: "sandboxEnd" }
  /** ゲーム内メッセージ。サーバーは payload を解釈せず同室へ中継する（rtcSignal と同じ扱い） */
  | { t: "sandboxSignal"; payload: unknown }

// S2C に追加
  /** サンドボックスゲームの開始・終了。同室全員へ。null は「動いていない」 */
  | { t: "sandboxState"; game: SandboxGameState | null }
  /** 中継されたゲーム内メッセージ。送信者本人には返らない */
  | { t: "sandboxSignal"; from: string; payload: unknown }
```

`RoomSnapshot` にも1フィールド追加する（途中参加・再接続のため、§5.3）:

```ts
  /** 稼働中のサンドボックスゲーム。無ければ null（docs/design/game-sandbox.md） */
  sandbox: SandboxGameState | null;
```

**命名の理由**: 既存の `rtcSignal` と同じ「サーバーが解釈しない中継」なので `〜Signal` に揃えた。
`gameSignal` にしないのは、`game` が既存エンジン（`GameState` / `selectGame` / `startGame`）を
指す語として既に使われており、混同するため。

**エラーコードは既存の `ErrorCode`（§4.2）で足りる**ため、新設しない。

| 状況 | コード |
|---|---|
| 非ホストが `sandboxStart` / `sandboxEnd` | `NOT_HOST` |
| 未知の `gameId`、または `dev` ゲームを本番で指定 | `INVALID_INPUT` |
| 既存エンジンのゲームが進行中（§5.2 の排他） | `PHASE_MISMATCH` |
| 同じ `gameId` の二重 `sandboxStart` | `DUPLICATE` |
| `sandboxSignal` のレート超過 | `RATE_LIMITED`（または黙って破棄。§4.3） |

### 4.3 レート制限

#### 何が問題か

§3.8 の一般枠は **1接続 20件/秒 を超えたら切断**である。ゲームは入力やイベントを高頻度に送るため、
これでは正当なプレイヤーを切ってしまう。しかも WS は全用途1本共用（§3.2）なので、
ゲームの超過で切断するとチャットも VC も既存ゲーム進行も巻き添えで落ちる。

これは §3.8 が `rtcSignal` について既に解いた問題と**同じ構造**である。
`rtcSignal` は「ソフト上限 100件/秒 = 超過分を破棄するだけで切断しない、
ハードキャップ 500件/秒 = 乱用とみなして切断」という2段構えを取っている
（`WS_SIGNAL_RATE_MAX` / `WS_SIGNAL_HARD_MAX`。`server/types.ts` に実装済み）。

#### 提案: 同じ2段構えを `sandboxSignal` に別枠で適用する

```ts
/**
 * WS メッセージのレート制限: sandboxSignal の判定窓内最大件数。
 * 超過分は破棄する（切断しない）。判定窓は WS_RATE_WINDOW_MS を共用する。
 */
export const WS_SANDBOX_RATE_MAX = 30;   // 【暫定値】
/** sandboxSignal のハードキャップ。これを超える連投は乱用とみなして切断する */
export const WS_SANDBOX_HARD_MAX = 150;  // 【暫定値】
/** sandboxSignal の payload の直列化サイズ上限（バイト）。超過は破棄 */
export const SANDBOX_PAYLOAD_MAX_BYTES = 4 * 1024;  // 【暫定値】
```

| 値 | 根拠 |
|---|---|
| ソフト **30件/秒** | プロトタイプの runner が**クライアント側で 30件/秒**のトークンバケットを持っており、その値で REFLEX の2人対戦が成立することを**実測**している。正規クライアントはこの上限に触れない。プロトタイプのサーバー側 60件/秒 は「クライアント側上限の2倍」として置かれた値だが、正規クライアントが 30 を超えない以上、サーバー側も 30 でよい（超過は破棄なので、稀な取りこぼしは通知1回で済む） |
| ハード **150件/秒** | `rtcSignal` のソフト:ハード = 100:500 = **1:5** の比に揃えた【暫定値】。乱用の判定であって正規利用の想定値ではない |
| payload **4KB** | 既存の `MAX_MESSAGE_BYTES`（64KB）のままだと、10人ルームで 64KB × 30件/秒 × 10人 の受信 → fan-out 9倍 で非現実的な帯域になる。4KB なら 1ルームあたり最大 約1.2MB/秒 に収まる【暫定値】 |

超過時の挙動は `rtcSignal` に完全に倣う:

- ソフト超過 → **当該メッセージを破棄するだけ。切断しない。**
  通知（`RATE_LIMITED`）は判定窓につき最大1回（エラーの増幅を防ぐ）。
- ハード超過 → `RATE_LIMITED` を返してから `close(1008)`。
- payload サイズ超過 → 黙って破棄（`rtcSignal` の中継条件違反と同じ扱い）。

#### 負荷の試算（**想定**。負荷試験は未実施 → §10-3）

10人ルームで全員が 30件/秒 送ると、サーバーの受信 300件/秒、
fan-out 9倍で送信 2,700件/秒。§7 の同時20ルームで全ルームがサンドボックス稼働なら
送信 54,000件/秒 になり、**単一プロセスでは持たない見込み**である。

そのため、上限を上げる方向ではなく **ゲーム側の設計規約**で抑える:

> **サンドボックスゲームは「入力とイベント」を送る。毎フレームの状態は送らない。**
> 目安として1人あたり平均 **10件/秒 以下**【暫定値】。

プロトタイプの REFLEX はこの規約を満たしている
（1ラウンドあたり `round` / `go` / `tap` / `result` の数件しか送らない）。
この規約は §6.4 の PR チェックリストに入れて、レビューで守らせる。

### 4.4 中継の条件

`relayRtcSignal`（`server/rooms.ts`）に倣う。

| 条件 | 満たさない場合 |
|---|---|
| 送信者が join 済みでルームに居る | 黙って破棄 |
| サンドボックスゲームが稼働中（`room.sandbox !== null`） | 黙って破棄 |
| payload が `SANDBOX_PAYLOAD_MAX_BYTES` 以下 | 黙って破棄 |
| レート内 | §4.3 |

宛先は**同室の接続中メンバー全員（送信者を除く）**。
`rtcSignal` と違い宛先指定（`to`）は持たない。**理由**: サンドボックスゲームは
「送った payload は全員に届く」という単純な前提の上に作る（§1.2 の「秘密を隠せない」）。
`to` を用意すると「隠せる」という誤解を生むが、実際には受信側クライアントを改造すれば
見えてしまうため、最初から全員配信に固定する。

**postMessage に載せてよいもの**（§2.5 の規約）:
`playerId` / `nickname` / `isHost` / `gameId` / `serverTime` / ゲーム自身の payload のみ。
`session` / `entryToken` / userId / Cookie 由来の値は**絶対に載せない**。

## 5. ルームへの組み込み

### 5.1 開始・終了の権限

**ホストのみ**（`sandboxStart` / `sandboxEnd` は host only）。
既存の `selectGame` / `startGame` / `skipPhase` と同じ流儀で `requireHost()` を通す。

理由: 既存エンジンのゲーム操作がホスト権限（§1 用語「ホスト」）である以上、
サンドボックスだけ誰でも開始できると「勝手に画面を乗っ取られる」荒らし経路になる（§3.7）。

ホスト交代（`hostChanged`）が起きても**サンドボックスゲームは終了しない**。
新しいホストに `EN.isHost === true` が伝わり、進行役が引き継がれる。
プロトタイプの REFLEX はホスト交代を受けて進行を引き継げる作りになっている
（コード上はそうなっているが、**ホスト交代の実測は未実施**）。

### 5.2 既存フェーズとの排他

サンドボックスは §3.3 のフェーズ機械に**参加しない**。`Phase` 型を増やさない
（型を増やすと `PhaseView` の union すべてに波及し、既存エンジンの回帰リスクが跳ね上がるため）。

代わりに **`room.game`（既存エンジン）と `room.sandbox`（サンドボックス）を相互排他**にする。

| 現在の状態 | `sandboxStart` | `startGame` / `selectGame` |
|---|---|---|
| どちらも動いていない（`lobby`） | 受理 | 受理 |
| 既存エンジンのゲームが進行中 | **`PHASE_MISMATCH`** | 既存の挙動のまま |
| サンドボックス稼働中 | `DUPLICATE`（同じ gameId なら冪等に無視） | **`PHASE_MISMATCH`** |

理由: 画面の同じ領域を取り合うこと、参加者の注意が割れること、
そして既存エンジンの `deadline` タイマーとサンドボックスの `requestAnimationFrame` が
同時に走ると重いこと。

**サンドボックス稼働中にホストが `startGame` を投げたら**、`PHASE_MISMATCH` を返し、
クライアント側で「先にサンドボックスゲームを終了してください」と案内する。
自動で `sandboxEnd` に落とさない（§3.2 原則1: 状態遷移をクライアントが判断しない）。

### 5.3 途中参加・切断・退室（§8 の異常系マトリクスに倣う）

| イベント | 挙動 | 理由 |
|---|---|---|
| **途中入室** | `roomState.sandbox` が入っているので、クライアントは自動で iframe を立て `onStart({ joinedLate: true })` で開始する。ゲームが途中参加に対応するかは**ゲーム側の責務** | サーバーは payload を解釈しないので、途中参加者に「今の状態」を配れない。既存エンジンの「★観戦のみ（次ラウンドから）」に相当する扱いはゲームが決める |
| **参加者切断** | `EN.onPeer({kind:"leave"})` がゲームに届く。サンドボックスは**中断しない** | 余興であり、公式スコアが無いので進行を守る必要が薄い |
| **再接続（60秒以内）** | `roomState` を受け取り、`sandbox.gameId` が同じなら **iframe を作り直して途中参加として再開**（`joinedLate: true`） | ゲームの内部状態は復元できない（サーバーが持っていない）。作り直すほうが、壊れた状態で動き続けるより安全 |
| **ホスト切断** | 60秒後にホスト委譲（既存の `hostChanged`）。サンドボックスは継続 | §8 の既存ゲームと同じ扱い |
| **退室・キック** | クライアントは iframe を破棄。残りには `onPeer leave` | §3.7 の「退出はワンタップ」を妨げない |
| **2人未満になった** | **中断しない**（既存エンジンは §8 共通規定で `lobby` へ落ちる） | 1人でも遊べるゲームがありうる。ホストが `sandboxEnd` すれば終わる |
| **サーバー再起動** | ルームごと消滅（§8 共通規定のまま） | 変更なし |
| **遅延メッセージ** | サーバーは中継するだけ。ゲーム側が形式検証して捨てる | プロトタイプの REFLEX が既にラウンド番号で弾いている |

### 5.4 VC・チャットとの共存

- **サンドボックスは `room.html` のゲーム表示領域に、既存エンジンの UI と排他で表示する**
  （§5.2 の排他と対応）。チャット欄・参加者一覧・VC 操作は**そのまま横に残す**。
- **音は出さない**（第1段）。CSP `default-src 'none'` により音声ファイルは読めない。
  Web Audio API による合成音は CSP のリソース読み込みを経由しないため鳴らせる**想定**だが、
  **VC の会話にかぶるため第1段では禁止**とし、PR チェックリスト（§6.4）に入れる（§10-7）。
- **画像アセットは使えない。** `img-src data: blob:` のみなので、描画は canvas の図形と
  `fillText`（システムフォント）に限られる。プロトタイプの REFLEX はこの制約下で成立している（**実測**）。
- **キーボード入力の奪い合い**: runner は修飾キー付き（Ctrl/Meta/Alt）を無視し、
  スペースのみ `preventDefault` する（プロトタイプの実装）。
  チャット入力欄にフォーカスがあるときは親が iframe にフォーカスを渡さないため干渉しない**想定**。
  §8.3 の手動テスト項目に入れる。

## 6. ゲームの追加手順

### 6.1 置き場所

```
public/
├── games/
│   ├── manifest.json      … 一覧の正本。サーバーが起動時に読んで検証する
│   ├── reflex.js          … ゲーム1本 = 1ファイル
│   └── <id>.js
└── sandbox/
    ├── runner.html        … 実行基盤（CSP・canvas）
    └── runner.js          … 実行基盤（EN API・ゲーム評価）
```

ゲームは1本1ファイル。ファイル名は `<id>.js` とし、マニフェストの `id` と一致させる
（パストラバーサル対策として、サーバーは `file` が `id + ".js"` と一致することも検証する）。

### 6.2 マニフェストの形式

`public/games/manifest.json`:

```json
{
  "version": 1,
  "games": [
    {
      "id": "reflex",
      "title": "反射神経バトル",
      "description": "緑になったら押す。全5ラウンドで反応速度を競う",
      "file": "reflex.js",
      "minPlayers": 2,
      "maxPlayers": 10,
      "author": "ちいかわ",
      "dev": false
    }
  ]
}
```

| フィールド | 型 | 検証（サーバー起動時） |
|---|---|---|
| `version` | number | `=== 1` |
| `games` | array | 1〜50 件 |
| `id` | string | `^[a-z0-9_][a-z0-9_-]{0,31}$`・一意 |
| `title` | string | 1〜20 文字・制御文字禁止（§3.5 の title と同じ上限） |
| `description` | string | 0〜100 文字・制御文字禁止（§3.5 と同じ） |
| `file` | string | `id + ".js"` と一致すること |
| `minPlayers` | number | 1〜10（§7: 1ルーム最大10人） |
| `maxPlayers` | number | `minPlayers`〜10 |
| `author` | string | 1〜20 文字 |
| `dev` | boolean | 省略可（既定 `false`）。`true` は環境変数 `EN_SANDBOX_DEV=1` のときだけ有効（§8.2） |

**検証に失敗したらサーバーは起動しない（fail fast）。**
不正なマニフェストのまま起動すると、ルームで初めて壊れていることに気づくため。

**ID の正本はサーバー**（§3.2 原則1）。クライアントは `GET /api/sandboxGames` で一覧を取り、
`sandboxStart` で送られた `gameId` はサーバーがホワイトリストで照合する。
`public/games/manifest.json` を直接 fetch させない（正本を2つ作らないため）。

### 6.3 追加の手順（そのまま実行できる粒度）

**1. 作業ブランチを切る**（main への直接コミットは禁止）

```powershell
git switch -c feature/game-<id>
```

**2. `public/games/<id>.js` を作る**

- 先頭に「これはサンドボックスゲームである」旨のコメントを書く（`reflex.js` の書き出しに倣う）。
- `"use strict";` を書く。
- **使えるのは `EN` だけ**（§3.2）。`window` / `document` / `fetch` / `localStorage` に触らない。
- 受信メッセージは必ず形式検証してから使う（`reflex.js` の `apply()` の流儀）。
- 通信の形式（`{ k: "…" , … }` のようなメッセージ種別）はゲーム内で完結して決める。
  サーバーもフレームワークも関与しない。

**3. `public/games/manifest.json` に1件追記する**（§6.2 の形式）

**4. ローカルで起動して2人プレイを確認する**

```powershell
deno task start
# ブラウザで http://localhost:8000/ を開く（動作確認ページ）
```

**必ず「別ウィンドウ」を2つ並べる。同一ウィンドウの2タブでは検証にならない**
（背面タブの `requestAnimationFrame` が間引かれる／停止するため。**実測**で確認済み）。

**5. 動作を確認する**

2人で成立する / 3人目が途中参加できる / 1人が退室しても落ちない /
ホストが抜けて交代しても進行が引き継がれる / ホストが終了できる。

**6. 静的検査とテストを通す**

```powershell
deno task check
deno task lint
deno task fmt
deno task test
```

**注意**: `deno.json` の `lint.include` / `fmt.include` は `server/` のみなので、
`public/games/` は対象外である。整形は既存ゲーム（`reflex.js`）の書式に手で揃えるか、
`fmt.include` に `public/games/` を追加する（**要相談** → §10-13）。

**7. PR を作り、本文に §6.4 のチェックリストを貼る**

人間のレビュー承認を得てマージする（§DoD 4）。

### 6.4 PR チェックリスト（レビュー観点）

**第1段の安全性は、このレビューが最後の砦である**（§7.1）。

- [ ] 無限ループ・終了条件の無い再帰が無い（`while (true)` / `for (;;)` を書いていない）
- [ ] `EN.send` を毎フレーム呼んでいない（入力・イベント時のみ。1人あたり平均 10件/秒 以下）
- [ ] `EN.send` の payload が 4KB 以下（大きな配列・文字列を丸ごと送っていない）
- [ ] 受信メッセージ（`onMessage` / `onPeer`）を形式検証してから使っている
- [ ] 巨大な配列 / `new Array(1e8)` / 巨大 canvas の確保が無い
- [ ] `setInterval` を張りっぱなしにしていない（`onEnd` で片付ける）
- [ ] **音を出していない**（第1段の方針、§5.4）
- [ ] 外部リソース（画像・フォント・音声・CSS）を読んでいない
- [ ] 参加者が1人でも0人でも落ちない
- [ ] 途中参加（`joinedLate: true`）・退室・ホスト交代で落ちない
- [ ] **公式スコアと誤認される表示をしていない**（「宴の順位」「総合成績」等の文言を使わない。方針3）
- [ ] `EN` 以外のグローバル（`window` / `document` / `fetch` …）を参照していない
- [ ] 実 Chrome の**別ウィンドウ2窓**で対戦が成立することを確認した

## 7. 防げないこと（正直に書く）

**この節を読まずにサンドボックスを本番へ出さないこと。**

### 7.1 無限ループ・メモリ食い潰しで、見ている人のタブが固まる

iframe は親と同じレンダラープロセス／イベントループを共有しうるため、
ゲームコードが `while(true){}` や巨大な確保を行うと**タブごと固まる**。
CSP でも sandbox 属性でも防げない（どちらも「何を読めるか」の制御であって、
「どれだけ回してよいか」の制御ではない）。**プロトタイプで防げていないと明記されている項目。**

- **第1段では受容する。** チーム製コードのみで、PR レビュー（§6.4）と
  テストプレイ（§6.3-5）を通るため。悪意ではなく事故（うっかりループ）が主たるリスクであり、
  レビューとテストプレイで拾える。
- **第2段（ユーザー投稿）に進むなら受容できない。**
  **Worker 化 + 実行時間監視が必須になる**（ゲームロジックを `Worker` で動かし、
  一定時間ハートビートが返らなければ `terminate()` する。描画は Worker から
  `OffscreenCanvas` を使うか、描画コマンド列を親フレームへ postMessage して描く）。
  これは runner の作り直しに近い規模の変更であり、第1段のスコープ外とする。

### 7.2 `new Function` はスコープを閉じない

`runner.js` は `new Function("EN", code)` でゲームを評価する。これは**変数スコープによる隔離ではない**。
関数の引数として渡した `EN` 以外に、**グローバルスコープ（`window` / `document` / …）が
そのまま見える**。ゲームは `window` に触れる。

隔離は **あくまで iframe のオリジン境界（opaque origin）と CSP によるもの**であり、
「`EN` しか見えない」わけではない。§3.2 の「使えるのは `EN` だけ」は**規約であって強制ではない**。

- 触れても、その `window` は不透明オリジンの空の文書のものなので、
  Cookie も localStorage も親の DOM も取れない（**実測**で16項目を阻止）。
- 実害は「ゲーム同士が同じグローバルを汚す」程度だが、iframe をゲームごとに作り直すため
  第1段では問題にならない。
- **将来の強化案**（第2段）: `with` + Proxy によるスコープ遮蔽、あるいは
  `ShadowRealm`（ブラウザ対応は**未検証**）。いずれも第1段のスコープ外。

### 7.3 チート（だから公式スコアに算入しない）

ゲームロジックが全部クライアント側にあり、サーバーは中継するだけなので、
**改造クライアントは任意の `payload` を送れる**。
反応速度も、スコアも、勝敗も、自己申告である。ホストが集計する型のゲームでも、
ホスト自身が改造されていれば成立しない。

- **これが方針3（公式スコアに算入しない）の理由である。**
  §3.2 原則1（サーバーが唯一の状態機械）を曲げずにサンドボックスを足すには、
  「サンドボックスの結果は宴の成績ではない」と線を引くしかない。
- サンドボックスゲーム**自身の中での**勝敗表示は自由（方針3）。
  ただし §6.4 のとおり「宴の順位」等と誤認される文言は使わない。
- 真剣に順位を競わせたいゲームは、既存エンジン側で作る（§1.3）。

### 7.4 `frame-ancestors` はヘッダーでしか効かない

`<meta http-equiv="Content-Security-Policy">` では `frame-ancestors` は**無視される**（仕様）。
プロトタイプは meta CSP のみだったため `frame-ancestors` を設定できておらず、
**サンドボックスページは任意の外部サイトから iframe で埋め込める状態**だった
（プロトタイプの既知の限界4）。

本実装では **サーバーのレスポンスヘッダーで `frame-ancestors 'self'` を付ける**（§2.6 補償措置2）。
同一オリジン構成（B）ではこれが**必須**である。付け忘れると、外部サイトが
sandbox 属性なしの iframe で runner を埋め込み、**アプリのオリジンでユーザーコードを走らせられる**。
§8.1 の自動テストで「runner のレスポンスに `frame-ancestors 'self'` が入っていること」を必ず検査する。

### 7.5 その他

- **`'self'` が不透明オリジンでどう解決されるかは Chrome での実測しかない。**
  プロトタイプは `script-src 'self'` で `runner.js` が読めることを Chrome で**実測**しているが、
  不透明オリジン文書における `'self'` の解釈はブラウザ差がありうる。
  **iOS Safari（§7 の必須動作対象）では未検証**（§10-2）。
- **ゲームの秘密は隠せない。** §4.4 のとおり payload は全員に届く。
- **サーバーは payload を見ないので、ゲーム内の不適切な文言を検閲できない。**
  第1段は PR レビューで担保する。第2段では §3.7 の通報導線が必要になる。
- **プロトタイプの実測は Chrome・2窓・別オリジン構成でのもの。**
  同一オリジン構成（§2.6 B）での16項目は**未実測**であり、§8.2 で再実測する。

## 8. テスト方針

### 8.1 自動テスト（`Deno.test`、`server/tests/sandbox_test.ts`）

サーバー側は既存の流儀（`rooms_test.ts` / `static_test.ts` / `main_test.ts`）に合わせる。

**マニフェスト**

- [ ] 正しいマニフェストが読める
- [ ] `version !== 1` / `id` の正規表現違反 / `id` 重複 / `file !== id + ".js"` /
      文字数超過 / `maxPlayers > 10` で**起動に失敗する**
- [ ] `dev: true` の項目が `EN_SANDBOX_DEV` 未設定時に `GET /api/sandboxGames` に出ない
- [ ] `dev: true` の `gameId` を `sandboxStart` に投げると `INVALID_INPUT`

**中継（`sandboxSignal`）**

- [ ] 同室の他の全員へ `{ t:"sandboxSignal", from, payload }` として**無改変**で届く
- [ ] **送信者本人には返らない**
- [ ] 別ルームへは漏れない
- [ ] 未 join の接続からは破棄される
- [ ] サンドボックス未稼働のとき破棄される
- [ ] payload が 4KB 超のとき破棄される

**レート制限**

- [ ] 30件/秒 を超えた分は破棄され、**接続は切れない**
- [ ] `RATE_LIMITED` の通知は判定窓につき最大1回
- [ ] 150件/秒 を超えたら `RATE_LIMITED` の後に `close(1008)`
- [ ] 一般枠（20件/秒）とは**別枠**でカウントされる（チャットが巻き添えで切れない）

**開始・終了・排他**

- [ ] 非ホストの `sandboxStart` / `sandboxEnd` は `NOT_HOST`
- [ ] 未知の `gameId` は `INVALID_INPUT`
- [ ] 既存エンジンのゲーム進行中の `sandboxStart` は `PHASE_MISMATCH`
- [ ] サンドボックス稼働中の `startGame` は `PHASE_MISMATCH`
- [ ] 同じ `gameId` の二重 `sandboxStart` は `DUPLICATE`（冪等）
- [ ] `sandboxStart` / `sandboxEnd` が同室全員に `sandboxState` として届く

**途中参加・切断**

- [ ] 稼働中に join した参加者の `roomState.sandbox` に `gameId` / `startedAt` が入る
- [ ] ホスト退出後、新ホストに `hostChanged` が届き、`sandbox` は継続する
- [ ] 全員退出でルームが消えるとき `sandbox` も消える

**静的配信・ヘッダー**（`static_test.ts` の流儀）

- [ ] `GET /sandbox/runner.html` の CSP に `default-src 'none'` / `connect-src 'none'` /
      **`worker-src 'none'`** / `'unsafe-eval'` が入る
- [ ] `GET /sandbox/runner.html` の CSP に **`frame-ancestors 'self'`** が入る（§7.4）
- [ ] アプリ側の他のパス（`/` / `/room/chat.js`）の CSP は**変わっていない**
      （`frame-ancestors 'none'` のまま。既存への影響なし）
- [ ] `GET /games/reflex.js` が 200 で `content-type: text/javascript`
- [ ] `GET /games/../../deno.json` / `GET /games/../server.ts` が 404（パストラバーサル）
- [ ] `GET /games/`（ディレクトリ）が 404（一覧を出さない）

### 8.2 隔離突破試験を回帰テストとして残す

プロトタイプで**実 Chrome 2窓・16項目すべての阻止を実測した**試験は、
自動テスト（`Deno.test`）では再現できない（ブラウザが要る）。
そこで **「攻撃を試みるゲーム」そのものをサンドボックスゲームとして残す**。

```
public/games/_probe.js          … 下記の項目を自分で試し、結果を EN.log で親へ報告する
public/games/manifest.json      … { "id": "_probe", …, "dev": true } として登録
```

- `dev: true` なので、**環境変数 `EN_SANDBOX_DEV=1` で起動したときだけ**
  `GET /api/sandboxGames` に現れ、`sandboxStart` が受理される。
  **本番環境では構造的に起動できない。**
- 実行すると親のログ欄に `PASS` / `FAIL` が並ぶ。**FAIL が1つでも出たら隔離が壊れている。**

**プロトタイプの実測16項目（そのまま移植する）:**

| # | 試すこと | 期待 |
|---|---|---|
| 1 | `window.parent.document` へのアクセス | 例外 |
| 2 | `window.parent.location.href` の読み取り | 例外 or 不可 |
| 3 | `document.cookie` の読み取り | 例外 or 空 |
| 4 | `localStorage` への書き込み | 例外 |
| 5 | `sessionStorage` への書き込み | 例外 |
| 6 | `indexedDB.open()` | 例外 or 失敗 |
| 7 | `fetch("/")` | 失敗（CSP `connect-src`） |
| 8 | `fetch("https://example.com/")` | 失敗 |
| 9 | `XMLHttpRequest` の送信 | 失敗 |
| 10 | `new WebSocket(…)` | 失敗 |
| 11 | `new EventSource(…)` | 失敗 |
| 12 | `navigator.sendBeacon(…)` | 失敗 |
| 13 | `new Worker("/room/chat.js")` → Worker 内から fetch | **Worker の生成自体が失敗**（`worker-src 'none'`。§2.4） |
| 14 | 外部ドメインの `<img>` 読み込み | 失敗（`img-src data: blob:`） |
| 15 | `window.open("https://example.com")` | `null`（`allow-popups` なし） |
| 16 | 入れ子 `<iframe src="…">` の生成 | 失敗（`frame-src 'none'`） |

**第1段で追加する項目（同一オリジン構成 B の検証。§2.6）:**

| # | 試すこと | 期待 |
|---|---|---|
| 17 | `self.origin` の値 | `"null"`（不透明オリジンであることの確認） |
| 18 | `/sandbox/runner.html` をトップレベルで直接開く | 自己防衛ガードが働き、ゲームを評価しない（§2.6 補償措置3） |
| 19 | 外部の HTML から sandbox 属性なしで runner を `<iframe>` に入れる | `frame-ancestors 'self'` により表示されない |

- 実施タイミング: **`server/main.ts` の CSP か `public/sandbox/` を変更した PR では必須。**
  手順は `docs/testing/sandbox-manual.md`（新規）に書く。

### 8.3 手動で見るもの（`docs/testing/sandbox-manual.md`）

自動化できない・自動化に見合わないもの。

### 9.3 進め方の順序

サーバーとフロントを並行に進められるよう、**型を先に確定させる**。

1. **`server/types.ts` の型追加をチーム合意**（§4.2）。ここが全ての前提。
2. サーバー: `sandbox_games.ts` → `main.ts`（配信・CSP）→ `rooms.ts`（中継）→ テスト
3. フロント（並行）: `public/sandbox/runner.*` を**プロトタイプから移植**（別オリジン前提の
   `?appOrigin=` / `/config` を落とし、自己防衛ガードを足す）
4. `public/room/sandbox.js` で橋渡し（サーバーの型が固まってから）
5. `reflex.js` と `_probe.js` を載せ、**`_probe.js` の19項目が全て PASS することを確認**
6. 実 Chrome 2窓 + iOS Safari で §8.3 を通す
7. PR → 人間レビュー承認（§DoD）

## 付録 A. プロトタイプからの主な変更点

移植担当が見落としやすい点をまとめる。

| プロトタイプ | 本実装 | 理由 |
