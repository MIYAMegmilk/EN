# VC 画面共有 設計書

VC ルーム（§3.6）で、参加者が自分の画面を他の参加者へ見せられるようにする。 共有された画面は
**その人のカメラを映しているタイルの中に表示する**（Discord のタイル内表示に倣う）。

対象コード: `public/room/vc.js` / `public/app.js` / `public/index.html` / `public/assets/en.css` /
`server/main.ts`（ヘッダのみ）。 **サーバーのメッセージ契約（`server/types.ts` /
`server/rooms.ts`）は変更しない。** 理由は §4.3。

## 0. この文書の読み方

この機能は「ブラウザの実際の挙動」に強く依存する。推測で書くと実装が壊れるので、記述の性質を区別して書く。

| 印         | 意味                                                           |
| ---------- | -------------------------------------------------------------- |
| 【確定】   | W3C 仕様・libwebrtc のソース・既存コードの実読で裏が取れている |
| 【判断】   | 確定した事実をもとにした設計上の選択。他の選択肢も併記する     |
| 【未確認】 | 実測しないと決められない。実装前または実装中に確かめる         |

## 1. 要件

### 作るもの

- VC 参加者が **自分の画面（画面全体・ウィンドウ・タブのいずれか）を共有できる**
- 共有された画面は **共有者のタイルの中**に出る。専用の大枠や別タイルを新設しない
- **タイルの中では読めないので、拡大表示を必ず用意する**（§7。これが無いと機能として成立しない）
- 共有は **本人の明示操作でのみ開始し、本人の操作でいつでも止められる**
- **同時に共有できるのは1人**（§4.4）
- 共有中であることが、共有者本人にも他の参加者にも画面から分かる（§9）
- 品質が劣化したときは既存の映像自動停止（§3.6）と噛み合って音声を守る（§8）

### 作らないもの（スコープ外）

| 外すもの                                 | 理由                                                                                                                                                                                                                                              |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **共有音声（システム音・タブ音）**       | 【確定】音声付き `getDisplayMedia` は Chrome / Edge のみ。Firefox / Safari は非対応。特定ブラウザでしか成立しない機能を、フルメッシュのミキシング・エコー対策込みで持ち込む価値は無い。§6.5 で「音声トラックは常に0本」を前提にした実装規約を置く |
| **スマホからの共有**                     | 【確定】iOS Safari と Android Chrome は `getDisplayMedia` 非対応。スマホは**受信専用**（受信は普通の映像トラックなので全端末で動く）                                                                                                              |
| **カメラと画面の同時送出**               | メッシュでは1人あたりの送出が2倍（画面5本＋カメラ5本）になる。要件が「カメラのタイルの中に画面を出す」である以上、1タイル＝1映像で足りる。§4.1 参照                                                                                               |
| **共有の録画・保存**                     | 記録を残す機能は §3.7 の安全設計（見知らぬ人と会う導線）と正面から衝突する                                                                                                                                                                        |
| **共有中の注釈・ポインタ描画**           | 別機能。データチャネルの新設が要る                                                                                                                                                                                                                |
| **2人以上の同時共有**                    | §4.4                                                                                                                                                                                                                                              |
| **bot タイル（`#vc-bots`）への共有表示** | bot は映像を持たない。共有対象は `#vc-people` の人のタイルだけ                                                                                                                                                                                    |

## 2. ブラウザ対応

### 対応表

| 環境                          | `getDisplayMedia` | 共有音声 | `selfBrowserSurface` | `contentHint` | この設計での扱い                                                            |
| ----------------------------- | ----------------- | -------- | -------------------- | ------------- | --------------------------------------------------------------------------- |
| Chrome / Edge（デスクトップ） | あり              | あり     | あり（112+）         | あり          | 送信・受信とも可                                                            |
| Firefox（デスクトップ）       | あり              | **なし** | **なし**             | **なし**      | 送信・受信とも可。`degradationPreference` は `setParameters` で明示（§6.4） |
| Safari（macOS）               | あり              | **なし** | **なし**             | あり          | 送信・受信とも可                                                            |
| **iOS Safari**                | **なし**          | —        | —                    | —             | **受信専用**                                                                |
| **Android Chrome**            | **なし**          | —        | —                    | —             | **受信専用**                                                                |

いずれも【確定】。

### 非対応時の UI

**特徴検出で出し分ける。** UA 文字列は見ない（偽装・将来の対応で必ず壊れる）。

```js
const screenShareSupported = typeof navigator.mediaDevices?.getDisplayMedia === "function";
```

**ボタンは消さずに `disabled` にして `title` で理由を出す。**【判断】 既に `bindVoice()`
が文字起こし非対応ブラウザで同じことをしている（`transcribeBtn.disabled = true` +
`title`）ので、流儀を揃える。
消してしまうと「自分の端末にだけ機能が無い」ことに気づけず、「壊れている」と誤解される。

- 文言: 「この端末では画面共有を始められません（他の人の共有は見られます）」
- **受信は常に有効。**
  受信側は普通の映像トラックを受け取るだけなので、非対応ブラウザでも何もしなくても映る

`selfBrowserSurface` / `contentHint` が無いブラウザでは、それぞれ §9-1 / §6.4 の代替手段に倒す。

## 3. 現状の把握（実読で確認した事実）

設計の前提になるので、`public/room/vc.js` を読んで確かめた事実を先に置く。

- **送信映像の口は `peer.videoSender`（`RTCRtpSender`）に1本だけ保持されている。** カメラ
  ON（`setCamera(true)`）も品質劣化時の自動停止（`stopVideoForQuality`）も、既に `replaceTrack`
  で付け外ししている。**差し替えの土台は出来ている**
- **受信側は1ピアにつき `<video>` が1枚**（`createPeerView`）。`ontrack` で受け取ったトラックは
  `peer.stream` に足され、`attachRemoteVideo` が `video.srcObject = peer.stream` を張る
- **`localTracks()` は `micStream` と `camStream` しか見ない**
- **状態告知は `{ kind: "video", on }` の真偽値1個**で、`announceVideoState()` は
  **既存ピアにしか送らない**
- **`rtcSignal` の payload はサーバーが解釈しない。**
  `relayRtcSignal()`（`server/rooms.ts`）は宛先が同室・VC 枠内であることだけを確かめて `payload`
  をそのまま転送する
- 静的配信のセキュリティヘッダ（`server/main.ts` の `SECURITY_HEADERS`）に **`Permissions-Policy`
  は無い**

## 4. アーキテクチャ

### 4.1 不変条件: 送出する映像トラックは常に高々1本

**この機能全体が、この1行の不変条件の上に乗る。**

理由は3つある。

1. **要件がそう言っている。** 「共有はカメラのタイルの中に表示する」＝ 1タイル1映像。
2. **【確定】1つの `MediaStream` に映像トラックを2本入れても、`<video>`
   はどちらか一方しか描かない。** 受信側は `peer.stream`
   に届いたトラックを全部足しているので、2本目の映像が来ると「どちらが映るか」がブラウザ任せになる。タイルを増やさない以上、送る側で1本に絞るしかない。
3. **【確定】メッシュではエンコーダが PeerConnection ごとに独立している**（libwebrtc
   のソースで確認済み。共有されるのは生フレームだけ）。 6人なら同じ画面を
   **5回別々にエンコード**する。カメラと画面を同時に送れば 10 本のエンコードになる。§6.2
   の表のとおり、標準案の5本ですら 720p30 換算 1.67 倍の負荷である。

したがって、映像ソースは排他とする。

```
videoSource: "none" | "camera" | "screen"
activeVideoTrack() = screen があれば screen、無ければ camera、どちらも無ければ null
```

**画面共有を始めると自分のカメラ映像は送出されなくなる。**【判断】 Discord
は顔と画面を別タイルで両方見せるが、あれは
SFU（サーバー中継）だから成立する構成であって、フルメッシュでは送出が倍になる。
代わりに、共有中は自分のタイルに「画面を共有中」の札を出して、顔が消えたのが不具合ではないことを示す（§9-3）。
将来 SFU に移るか、2本目の m-line を許すかは §12 の未決に残す。

### 4.2 トラックの差し替え

**再ネゴシエーションは「映像の m-line が既にあるとき」だけ不要。**
プロンプトで渡された前提より一段細かい条件が付く。実読の結果は次のとおり。

- `peer.videoSender` は、**カメラを一度も ON にしていないピアでは `null`**（`createPeer` は
  `localTracks()` にある映像だけを `addTrack` する）
- `setCamera(false)` は `removeTrack` するので `videoSender` を `null` に戻す

したがって、**カメラ OFF のまま画面共有を始めた場合は `pc.addTrack()` になり、`onnegotiationneeded`
経由で offer/answer が1往復する。** これは既存のカメラ ON と同じ経路で、Perfect Negotiation
が衝突を解消するので安全だが、「再ネゴが一切起きない」わけではない。ここは正確に書いておく。

差し替えの手順（1ピアぶん）:

```
applyVideoTrack(peer, track):          // track は null 可
  if peer.videoSender !== null:
      await peer.videoSender.replaceTrack(track)      // 再ネゴ不要
  else if track !== null:
      peer.videoSender = peer.pc.addTrack(track, ownerStream(track))   // ここだけ再ネゴが走る
  applyEncodingProfile(peer.videoSender, profileFor(currentSource))    // §6.4
```

**`applyEncodingProfile` は sender 1個ずつに呼ぶ。**【確定】輻輳制御（BWE）も PeerConnection
ごとに独立しているので、5本ぶんの `setParameters()` を個別に呼ばないと片側しか効かない。

**`localTracks()` を映像ソース対応にする。**
これをやらないと、共有中に入ってきたピアにだけ画面が載らない（§5 の T3）。

```
localTracks():
  micStream の音声 + (activeVideoTrack() があればそれ1本)
```

`createPeer` の `addTrack(track, ...)` の第2引数は現在 `state.camStream`
固定なので、`activeVideoStream()` に直す。

### 4.3 状態告知（`rtcSignal` payload の拡張）

**受信側は、届いたトラックがカメラなのか画面なのかを自力では判別できない。**【確定】 `replaceTrack`
は remote 側に新しい `ontrack` を発火させない。`MediaStreamTrack`
のオブジェクトは同じまま、中身の解像度だけが変わる。 `getSettings().displaySurface`
はローカルの取得元トラックにしか無い。 だから **明示的に告知するしかない。**

既存の payload には自前のミニプロトコルがある（`ready` / `bye` / `desc` / `ice` / `video`）。
**サーバーは payload を素通しするので、ここに相乗りすればサーバー側の変更は一切要らない**（§3
の実読で確認）。

#### 拡張後の `video`

```jsonc
{
  "kind": "video",
  "on": true, // 既存。映像を送出しているか（この意味は変えない）
  "source": "screen", // 追加。"camera" | "screen"。省略時は "camera" とみなす
  "surface": "monitor" // 追加・任意。"monitor" | "window" | "browser" | null
}
```

- **`on` の意味は変えない。** 古いクライアントは `source`
  を無視して従来どおり表示の出し入れだけを行う。デプロイの入れ替わり中に混ざっても、映像が消える／出っぱなしになる事故は起きない
- `source` を受け取った側は `peer.remoteVideoSource` に保持し、**タイルの `object-fit`
  の切り替え（§7.1）と「共有中」の札（§9-3）にだけ使う**。表示の出し入れは従来どおり `on` と
  `updateVideoVisibility()` が受け持つ
- `surface` は **共有者本人が自己申告する情報**であり、【確定】`displaySurface`
  は希望の表明にすぎず選択を制限できないため、`track.getSettings().displaySurface` で
  **事後確認した実際の値**を載せる。受信側では表示にしか使わない（信頼して制御に使ってはいけない）

#### 告知の穴をふさぐ

**現状の `announceVideoState()` は `state.peers` の中身にしか送らない。** つまり「自分がカメラ ON
にした後で入ってきた相手」には映像状態が飛ばない。これは画面共有以前からある穴で、`remoteVideoOff`
の初期値が `false` なので実害が出にくかっただけである。 画面共有では `source` が飛ばないと
`object-fit` も札も間違うので、ここで直す。

**ピアを作った／受け入れた直後に、そのピアだけへ現在の映像状態を送る。**

- `onReady()` で `ensurePeer()` した直後
- `handleServerMessage` の `playerJoined` で `ready` を送った直後

順序は保たれる。【確定】WS は1接続を全用途で共用し（§3.2）、`relayRtcSignal` は宛先リンクへ順に
`send` するので、`ready` → `video` の順で届く。受け手は `ready`
でピアを同期的に作ってから戻るので、後続の `video` は必ずピアを見つけられる。

### 4.4 同時共有者を1人に絞る

**【確定】2人が同時に共有すると、各自が「画面5本＋カメラ5本」を送ることになる。**
メッシュではこれを許せない。

**サーバーは payload を解釈しないので、排他はクライアント同士の合意で作る。**【判断】
サーバーに新しいメッセージ型（共有ロック）を足せば厳密な排他になるが、§4.3
の「サーバー変更ゼロ」という利点を捨てることになるうえ、ロックの解放漏れ（切断・キック・再接続）の面倒をサーバーが背負う。
VC 枠は最大6人の小さな卓で、悪意ある実装を排除するための機構でもない。**協調的な排他で足りる。**

#### 通常経路

開始前に `state.peers` を走査し、`remoteVideoSource === "screen"` のピアが居れば
**開始せずに断る**（「〇〇さんが画面を共有中です」）。 `getDisplayMedia()`
は呼ばない（呼ぶと選択ダイアログが出てから断ることになり、体験が悪い）。

#### 競合したとき（境界）

告知が行き違う窓（片道 RTT ぶん）で2人が同時に開始し得る。両者が同じ規則で解けば必ず1人に収束する。

**規則: `playerId` の辞書順で小さい方が共有権を持つ。負けた側は自分の共有を止め、`video/off`
を告知して利用者に理由を出す。**

- **時刻（`Date.now()`）は使わない。**【判断】端末の時計は同期していない（NTP
  ずれ・手動設定）ので、「先に押した方」を跨端末で比較できない。比較できない値で分岐すると、両者の判定が食い違って**どちらも止まる／どちらも残る**という最悪の結果になり得る
- `playerId` 順は **Perfect Negotiation の polite /
  impolite（`state.selfId > playerId`）と同じ流儀**で、既にコードにある考え方をそのまま使える
- 代償として「先に押した人が負ける」ことがある。窓は片道 RTT
  なので実際にはめったに起きず、負けた側には必ず文言が出るので黙って消えることはない

**共有権は状態変数として持たない。** 常に「今どのピアが `screen`
を告知しているか」から導く（`derive`）。 こうしておくと、共有者が切断・キックされたときに
`closePeer()`
がピアを消した時点で自動的にロックが解ける。持ち回りのフラグにすると必ず解放漏れが出る。

## 6. 解像度・フレームレート・ビットレートの設計

### 6.1 前提（メッシュで何が起きるか）

【確定・libwebrtc のソースで確認済み】

- **エンコーダは PeerConnection ごとに独立。** 6人なら同じ画面を
  **5回**エンコードする。共有されるのは生フレームだけ
- **輻輳制御（BWE）も PeerConnection ごとに独立**で、5本が互いに帯域を食い合う
- したがって **`setParameters()` は sender 5個それぞれに個別に呼ぶ**
- ハードウェアエンコーダのセッション上限に当たり得る（§8.4）

つまり **「1本ぶんの品質」を決めた瞬間に、その5倍が上りと CPU に乗る。**
単体通話の感覚で数字を決めてはいけない。

### 6.2 プロファイル

|                        | 軽い        | **標準（既定）**  | 高画質           |
| ---------------------- | ----------- | ----------------- | ---------------- |
| 解像度 / fps           | 640×360 / 5 | **1280×720 / 10** | 1920×1080 / 15   |
| `contentHint`          | `"text"`    | `"text"`          | `"text"`         |
| `maxBitrate`（1本）    | 250 kbps    | **700 kbps**      | 1500 kbps        |
| **上り合計（×5）**     | 1.25 Mbps   | **3.5 Mbps**      | 7.5 Mbps         |
| **CPU（720p30 換算）** | 0.21×       | **1.67×**         | **5.6×（危険）** |

CPU 欄は `解像度 × fps × 本数` を 1280×720×30 で割った比。 標準案は
`1280×720×10×5 ÷ (1280×720×30) = 1.67`、高画質案は `1920×1080×15×5 ÷ (1280×720×30) = 5.6`。
**高画質は既定にしない。** 720p30 のビデオ通話 5.6
本ぶんを1台で回すことになり、ハードウェアエンコーダのセッション上限（§8.4）にも触れやすい。

### 6.3 なぜ 1280×720 / 10fps を既定にするか

**「読めるかどうか」は、送出する画素数で決まる。**
拡大表示をどれだけ大きくしても、取り込みの時点で潰れた文字は戻らない。 1920×1080
のデスクトップにある 14px の文字が、各案の**エンコード後のフレームの中で何画素になるか**:

| 取り込み     | 縮小率 | 14px の文字 | 判定                       |
| ------------ | ------ | ----------- | -------------------------- |
| 640×360      | 1/3    | **4.7 px**  | 読めない                   |
| **1280×720** | 2/3    | **9.3 px**  | **拡大表示があれば読める** |
| 1920×1080    | 等倍   | 14 px       | 読める                     |

- **640×360 は「文字を見せる用途」には成立しない。** タイル内表示しかしないなら 640×360
  が実用上の上限（§7）だが、それは「タイルの中では何をやっても読めない」ことの裏返しであって、640
  で十分という意味ではない
- **1280×720 が意味を持つのは拡大表示があるときだけ。** だから §7 の拡大表示は「あると便利」ではなく
  **この解像度を選ぶ前提条件**である
- **10fps を選ぶ理由**:
  画面共有の中身は資料・コード・ブラウザであって動画ではない。フレームレートより解像度が価値を持つ。
  【確定】WebRTC 本家も画面共有の基本レイヤを **5fps / 200kbps** で設計している。標準案の 10fps /
  700kbps はそれより上を取っている
- **700 kbps の根拠**: 上り合計 3.5 Mbps に収める点から逆算した値。一般的な家庭回線の上り（10〜30
  Mbps 級）に対して、音声（Opus 約 32kbps × 5 = 約 160kbps）と他人のカメラを乗せても余裕が残る

**動画・ゲーム画面用の別枠**【判断】: 1280×720 / 24fps / 1200 kbps・`contentHint = "motion"`。
`"text"` のままだと動きのある内容で**解像度を守るために fps が捨てられ**、紙芝居になる。
利用者に「文字を見せる／動きを見せる」を選ばせる（§10）。既定は「文字」。

### 6.4 送出パラメータの当て方

```js
// 1. 取り込み（ideal / max のみ。min / exact / advanced は TypeError）
const stream = await navigator.mediaDevices.getDisplayMedia({
  video: {
    width: { max: 1280 },
    height: { max: 720 },
    frameRate: { max: 10 },
  },
  audio: false,
  selfBrowserSurface: "exclude", // Chrome 112+。非対応ブラウザでは無視される
  surfaceSwitching: "include",
  systemAudio: "exclude",
});

// 2. 内容のヒント（Firefox は非対応）
track.contentHint = "text";

// 3. sender 1個ずつに当てる（BWE が独立しているため）
const p = sender.getParameters();
if (!p.encodings || p.encodings.length === 0) p.encodings = [{}];
p.encodings[0].maxBitrate = 700_000;
p.encodings[0].maxFramerate = 10;
p.degradationPreference = "maintain-resolution"; // encodings の外側
await sender.setParameters(p);
```

**なぜ制約を `max` で書くか。**【確定】`getDisplayMedia` の制約は `ideal` と `max`
しか受け付けない。`min` / `exact` / `advanced` を渡すと **TypeError** で落ちる（W3C 仕様）。 `ideal`
は「希望」でしかないので、上限を保証したいなら `max` を使う。

**なぜ制約だけに頼らないか。**【確定】`getDisplayMedia` の制約は
**利用者が画面を選んだ後**にしか適用されない（ソースの絞り込みには使えない）。 また【確定】Chromium
の既定は 2880×1800 / 最大 120fps で、明示的に絞らないとこれを掴む。
制約で取り込みを絞り、`setParameters` で送出を絞る **二重の歯止め**にする。

**なぜ `degradationPreference` を明示するか。**【確定】`contentHint = "text"` にすると
`degradationPreference` は `maintain-resolution`
になり、**文字が潰れる前にフレームレートが落ちる**（W3C 規範）。
これは画面共有で欲しい挙動そのものだが、**Firefox は `contentHint` に非対応**なので、`setParameters`
側で同じ値を明示して揃える。

**`setParameters` は `replaceTrack` のたびに当て直す。** パラメータは sender
に属するのでトラックを替えても消えないが、**カメラに戻すときは `maintain-resolution` と 10fps
上限を外さないといけない**（カメラは逆に解像度を捨てて滑らかさを守るべき）。ソースが変わるたびにプロファイルを当て直すのが確実。

### 6.5 音声トラックは常に0本として扱う

`audio: false` で要求するので通常は返ってこないが、**`getAudioTracks()[0]`
を素で触るコードを書かない。** 【確定】音声付き共有は Chrome / Edge のみで、他では必ず0本になる。
将来 §12 の未決で音声共有を入れるとしても、0本の分岐が先に無いと Firefox / Safari で落ちる。
万一トラックが返ってきた場合は **その場で `stop()` して捨てる**（送らない）。

### 6.6 TURN リレー時は自動的に軽い案へ落とす

**【確定】TURN リレーは in と out の両方を通すので、VPS 側の帯域は2倍。** 標準案なら共有者1人あたり
**VPS に 7 Mbps**（上り 3.5 + 下り 3.5）。VPS の回線は **100 Mbps（全プラン共通）**
で、ここに全ルームの音声と HTTP も乗る。

**判定**: `getStats()` の `candidate-pair` から選択中のペアを取り（`pickCandidatePair()`
が既にある）、その `localCandidateId` / `remoteCandidateId` を `local-candidate` /
`remote-candidate` 統計で引いて `candidateType === "relay"` を見る。

**対処**: **1本でも relay のピアがあれば、全 sender を軽い案（640×360 / 5fps /
250kbps）に落とす。**【判断】

- relay しているピアだけ落とす、という手もあるが、**ボトルネックは VPS
  という共有資源**なので、共有者単位で絞るほうが目的に合う
- 軽い案なら relay 時でも VPS 負荷は 2.5 Mbps。標準案の 7 Mbps に比べて 1/3 弱
- 640×360
  では文字が読めない（§6.3）ので、**落としたことを利用者に必ず伝える**（「回線の都合で画質を落としています」）。黙って劣化させると「画面共有は使いものにならない」という誤った印象だけが残る
- 判定は共有開始直後には出ない（ICE の選択が固まるまで数秒かかる）。**開始時は標準案で始め、relay
  を検知した時点で落とす**

## 7. 拡大表示（この機能の必須要素）

### 7.1 タイルの中では読めない（計算で確定）

現在のレイアウトは
`.vc-peer { aspect-ratio: 4/3 }`、`#vc-people > .vc-peer { flex: 1 1 240px; max-width: 520px }`。

- **6人並ぶと1枠は 240〜260 px。** 4:3 なので高さは 180〜195 px
- そこに 16:9 を `object-fit: contain` で入れると、**表示は 240×135 〜 260×146 CSS px**
- 1920 px 幅の画面は **1/8 に縮む**。14px のフォントは **1.75 CSS px**（DPR 2 の端末でも 3.5
  デバイスピクセル）

**1.75 px の文字は読めない。** つまり
**「タイルの中だけ」の画面共有は、機能として何の役にも立たない。**
共有の目的はほぼ常に「相手に何かを読ませる・見せる」ことなので、**拡大表示が無い画面共有は要件を満たしていない。**

これは §6.3 とも接続する。**タイルにしか映さないなら 640×360
が実用上の上限**（それ以上送っても表示できない）で、**1280×720
が意味を持つのは拡大表示があるときだけ**である。
拡大表示は「あとで足す改善」ではなく、**解像度の設計を成立させる前提条件**として同時に作る。

### 7.2 設計

**覆い（オーバーレイ）で全画面に近い大きさで見せる。**【判断】

既に `#game-platform`（あそびの品書き）が `role="dialog" aria-modal="true"`
の覆いとして実装されており、Escape と背景クリックで閉じる結線も `app.js`
にある。**同じ流儀を踏襲する**（新しい作法を増やさない）。

- **開き方**:
  共有中のタイルをクリック、またはタイルに出る「拡大」ボタン。**共有中のタイルだけがクリック可能**（カメラのタイルは拡大しても情報が増えないので対象外）【判断】
- **閉じ方**: Escape / 背景クリック /
  閉じるボタン。**共有が止まったら自動で閉じる**（黒い枠だけが残らないように）
- **中身**: 覆いの中に `<video>` をもう1枚置き、`srcObject` に**同じ `peer.stream` を張る**。
  タイルの `<video>` を DOM ごと移動させない。【判断】`closePeer()` が `peer.view.root.remove()`
  でタイルごと消す作りなので、要素の持ち主を移すと後始末が壊れる。 同じ `MediaStream` を2つの
  `<video>` に張るのは通常の使い方で、**デコードは1回、描画が2回**になるだけ。追加の受信帯域はゼロ
- **大きさ**: 覆いは**窓いっぱい**に広げる。【確定】品書きの `.platform-sheet` は
  `width: min(1000px, 100%)` で、これを共有画面にそのまま使うと **1280px の映像が 960px
  に縮んで表示される**（送った画素を捨てている）。「拡大したのにあまり変わらない」の正体は
  ここで、`#vc-zoom` だけ上限と余白を外し、`<video>` も `max-width` ではなく
  `width/height: 100%` + `object-fit: contain` で枠を使い切る
- **端末の全画面**: 覆いの上でさらに `requestFullscreen()` を出す。 【確定】iOS Safari は
  `Element.requestFullscreen()` を持たない（`<video>` の `webkitEnterFullscreen()`
  のみ）。特徴検出で出し分け、**どちらも無ければ覆いだけで完結する**（覆いを基本形にしておけば全端末で成立する）。
  映像の二度押しでも入れる。全画面中の Escape は**ブラウザが全画面を外すための押下**なので、
  そこで覆いまで畳まない（一度で共有画面ごと消えてしまう）

### 7.3 タイル側の表示

**共有中のタイルだけ `object-fit: contain` に切り替える**（カメラのときは従来どおり
`cover`）。決定済み。

```css
.vc-video-screen {
  object-fit: contain;
} /* .vc-video は cover のまま */
```

- **なぜ切り替えるか**: `cover`
  は縦横比の合わない部分を**切り落とす**。カメラなら顔が中央にあるので問題ないが、画面共有で端が切れると、ツールバーやコードの行頭など**まさに読みたい部分が消える**
- `contain` にすると 4:3 の枠に 16:9 が入って上下に黒帯が出る。`.vc-video` の `background: #000`
  が既にあるので追加の指定は要らない
- `.vc-peer-label` は `z-index: 2` で下端に重なる。`contain`
  の黒帯の上に載るので、名前が映像を隠す度合いはむしろ小さくなる
- 適用先は「そのタイルの映像ソースが `screen` のとき」。自分のタイルは
  `state.videoSource`、他人のタイルは `peer.remoteVideoSource`（§4.3）から決める

## 8. 品質劣化時の扱い

§3.6 は「品質劣化時は映像を自動停止し音声優先」と定める。**この終着点は変えない。**
既存の品質ガード（`evaluateQuality`
以下）は**カメラを前提に組まれている**ので、噛み合わせを設計する。

### 8.1 判定の入口を映像ソースで変える

**共有中は実効 FPS を判定の入口条件にしない。**【判断・根拠あり】

現在の `sampleCause()` のフォールバック経路は `fpsRatio < 0.5`
を入口にしている。これが画面共有では**健全な状態で常時成立する**。理由は2つ。

1. 【確定】`contentHint = "text"` は `maintain-resolution` を選ばせる。つまり **fps
   が落ちるのは設計どおりの正常動作**である。「解像度を守るために fps
   を捨てた」結果を「劣化」と読むのは判定の取り違え
2. 画面共有は変化駆動で、静止した画面ではフレームがほとんど生成されない。`framesEncoded`
   が増えないのは**回線とは無関係**

したがって共有中の判定はこうする。

| 判定方式                            | カメラ             | 画面共有                                             |
| ----------------------------------- | ------------------ | ---------------------------------------------------- |
| 主判定（`qualityLimitationReason`） | 現状のまま         | 現状のまま（`cpu` は即、`bandwidth` は裏付けを要求） |
| フォールバック入口                  | `fpsRatio < 0.5`   | **使わない**                                         |
| フォールバックの判定材料            | RTT / 送出可能帯域 | **RTT / 送出可能帯域のみ**（fps ゲート無し）         |

RTT と送出可能帯域は、主判定の `bandwidth`
に対して既に「裏付け」として使われている指標で、**画面共有でも意味が変わらない**。fps
ゲートを外した代わりにこの2つだけで見る。

**代償**: `qualityLimitationReason` を持たないブラウザ（Safari 17.3 以下など）では、RTT
も送出可能帯域も取れない場合に判定が働かない。 これは既存の**リスク
R6「誤検知より検知漏れに倒す」**方針と同じ扱いにする。見逃しても音声は残るが、誤検知は健全な共有を奪う。

### 8.2 劣化したときに何を止めるか

`stopVideoForQuality()` を「今の映像ソースを止める」意味に一般化する（T8）。

**二段構えにする。**【判断・§12 に未決として再掲】

1. **1回目の劣化 → 降格。** 軽い案（640×360 / 5fps /
   250kbps）へ落とす。`applyConstraints({ width:{max:640}, height:{max:360}, frameRate:{max:5} })`
   と `setParameters` の当て直し。利用者に通知
2. **降格しても最小保持時間（60秒）の後になお劣化 → 共有を停止。** ここは §3.6
   のとおり音声優先で、既存のカメラ自動停止とまったく同じ扱い

**なぜ降格の段を挟むか。**
カメラは「その場に居ること」を伝える継続的な演出なので、止めても会話は続く。
**画面共有は会話の対象そのもの**で、いきなり消すと話している内容が成立しなくなる。まず画質を落として繋ぐほうが目的に適う。
**終着点（停止）は変えていない**ので §3.6 に反しない。

### 8.3 ウォームアップの取り扱い

**映像ソースが変わったら、`videoOnAt` を打ち直し、`quality.prev` / `quality.window` を捨てる。**

`vc.js` のコメントに実測が記録されているとおり、【確定】Chrome は送出開始直後、回線が健全でも
`qualityLimitationReason` に `"bandwidth"` を返し続ける（実測 9.8 秒 / 18.1 秒）。 `replaceTrack`
でカメラ→画面へ切り替えると**エンコーダも BWE
も立ち上げ直し**になるので、まったく同じ過渡状態が再現する。 古い `camOnAt`
と古い観測窓を持ち越すと、**共有を始めた直後に必ず誤検知する**。

`QUALITY_CAMERA_WARMUP_MS = 30000`（暫定値）をそのまま流用する。【未確認】この30秒が画面共有でも足りるかは実測していない。
恒久的な守りは「主判定の `bandwidth`
に裏付けを要求する」側（既存）に入っているので、時間はあくまで多層防御。

### 8.4 ハードウェアエンコーダの枯渇

【確定】メッシュではエンコードが5本並ぶため、**ハードウェアエンコーダのセッション上限に当たり得る**。
`hardware-encoder-not-available` のハンドリングが要る。

**【未確認】このエラーがどの経路で通知されるかはブラウザ依存で、実測していない。** 仕様上は
`RTCError` の `errorDetail` として定義されているが、Chrome
が実際にどのイベントで投げるか（あるいは黙ってソフトウェアエンコーダに落ちるか）を確かめていない。**推測で経路を1つに決め打ちしない。**

したがって、**通知経路に依存しない検出も併せて持つ。**

1. `replaceTrack` / `addTrack` / `setParameters` を `try/catch`
   で囲み、例外を握って共有を安全に畳む（既存コードの `replaceTrack` は既に `.catch` している）
2. **統計で見る**: `outbound-rtp(video)` の `framesEncoded`
   が、送出中にもかかわらず一定サンプル数（暫定 3 サンプル ≒ 6 秒）まったく増えない →
   エンコード不成立とみなして共有を停止し、理由を出す。 `encoderImplementation`
   も併せて記録する（ソフトウェアへ落ちたのか、そもそも動いていないのかの切り分けに使う）

## 9. セキュリティ・プライバシー

見知らぬ人と同席する導線（§3.7）に画面を映す機能を足すので、ここは丁寧に設計する。

### 9-1. 意図しない画面の露出

**最大の事故は「見せるつもりのないものを見せてしまう」こと。**
通知・パスワード入力・別のタブ・デスクトップのファイル名など。

| 手当て                                 | 内容                                                                                                                                                                                                                                                                                                            |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **自タブの誤共有を防ぐ**               | `selfBrowserSurface: "exclude"`（Chrome 112+）。EN のタブ自身を共有すると、無限の入れ子になるうえ**その部屋のチャット・参加者名がそのまま外へ出る**。【確定】非対応ブラウザでは効かないので、下の事後確認と併用する                                                                                             |
| **選ばれたものを事後確認する**         | 【確定】`displaySurface` は希望の表明にすぎず選択を制限できない。**実際に何が選ばれたかは `track.getSettings().displaySurface` で事後に確認する。** `"monitor"`（画面全体）なら「画面全体を共有しています。通知やパスワード入力も映ります」と**強めの警告を出す**（止めはしない。利用者の選択を機械が覆さない） |
| **送出内容が常に自分に見えている**     | `renderLocalVideo()` は自分のタイルに送出中の映像を映す。**共有中は「いま外に出ているもの」が常に自分の画面にある**ので、事故に即座に気づける。この性質を壊さないこと                                                                                                                                           |
| **止めるのが常に1手**                  | 停止ボタンは共有中ずっと目に入る位置に置く（タイルの上に重ねる）。§3.7 の「退出はワンタップ」と同じ思想                                                                                                                                                                                                         |
| **`stop()` では `ended` が発火しない** | 【確定】。**自前の停止ボタンからは明示的に後始末を呼ぶ。** `ended` に後始末を任せると、ブラウザの共有バーから止めたときしか動かない（＝アプリ側のボタンで止めたときに送出が畳まれない）。`ended` リスナは「ブラウザ側から止められたとき」用に**別途**残す                                                       |

### 9-2. `Permissions-Policy`

【確定】現状 `server/main.ts` の `SECURITY_HEADERS` に `Permissions-Policy`
は無い。`display-capture` の許可も拒否も宣言されていない。

**明示する。**

| 対象                                           | 値                                                                             |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| アプリ本体（`SECURITY_HEADERS`）               | `Permissions-Policy: display-capture=(self), camera=(self), microphone=(self)` |
| `/sandbox/` 配下（`SANDBOX_SECURITY_HEADERS`） | `Permissions-Policy: display-capture=(), camera=(), microphone=()`             |

- **`display-capture` の既定の許可リストは `self`**
  なので、この宣言は挙動を変えない。**変えないことに意味がある**:
  明示しておくと、将来だれかが埋め込みや iframe
  を足したときに、既定値の解釈に頼らず**この行を読んで判断できる**
- **`/sandbox/` は空リスト（誰にも許さない）にする。** runner
  はユーザーコードを実行するページであり（`game-sandbox.md`
  の設計どおり悪意あるコードを前提にする）、画面取得を渡す理由が1つも無い
- **現状でも runner から `getDisplayMedia` は呼べない**ことは確認済み: `public/room/sandbox.js` の
  `createFrame()` は `sandbox="allow-scripts"` のみを付け、**`allow-same-origin`
  を付けていない**。したがって runner の文書は一意の不透明オリジンになり、`self`
  の許可リストに一致しない。 **この前提が崩れたら（誰かが `allow-same-origin`
  を足したら）話が変わる**ので、§11 のテストで見張る
- アプリ本体は `frame-ancestors 'none'`
  なので第三者に埋め込まれる経路自体が無い。`Permissions-Policy` はその補強

### 9-3. 共有中であることの明示

**誰が見ても、誰が何を共有しているか分かること。**

- **共有者のタイル**に「画面を共有中」の札を出す（`.vc-share-badge`）。自分のタイルには**より目立つ形**（赤系の点＋停止ボタン）で出す
- 札の文言は**固定文字列**を `textContent` で入れる。ニックネームを混ぜる場合も `textContent`（§3.8
  の XSS 規約）
- **カメラが消えたことを不具合と誤解させない。**
  共有中は顔が出ない（§4.1）ので、札に「（カメラは停止中）」を添える
- **`#vc-status` は使わない。** `bindVoice()` の `onStatus`
  が同じ要素を上書きするので、共有の表示をここに置くと文字起こしの通知で消える。実読で確認済み
- 開始・停止は `notify("vcState", ...)`
  にも流す。ログ（`log("VC", ...)`）に残るので、後から経緯を追える

### 9-4. その他

- **新しい秘密情報は増えない。** TURN
  認証情報の扱い（§3.8「クライアント配布物に埋め込まない」）は現状のまま
- **画面の中身はサーバーを通らない**（P2P、または TURN
  のリレー）。サーバーに録画・保存の機構を作らない
- **キックされた相手との共有は即座に切れる**: `closePeer()` が `pc.close()`
  するので送出も止まる（§3.6 の既定の挙動）。共有権も §4.4
  のとおりピアの状態から導くので、キック後に自動的に解ける
- **レート制限**: 共有の開始・停止は `rtcSignal` を N-1 通送るだけで、`WS_SIGNAL_RATE_MAX = 100/秒`
  に対して無視できる量。ただし**開始・停止の連打を UI 側で抑える**（開始直後は数秒ボタンを無効化）

## 11. テスト観点

`server/tests/vc_teardown_test.ts` の流儀に沿う。すなわち **`public/room/vc.js` を偽の DOM・偽の
`RTCPeerConnection`・偽の `MediaStream` の上に `new Function` で読み込み、Deno から素の JavaScript
として動かす。**

### 偽物の拡張が要るもの

- `navigator.mediaDevices.getDisplayMedia` — 映像トラック1本の `FakeStream`
  を返す。**制約オブジェクトを記録**して検証できるようにする
- `FakeTrack` — `contentHint`（書き込み可）、`applyConstraints()`（呼び出しを記録）、`getSettings()`
  が `displaySurface` を返せること。**`stop()` で `ended`
  を発火させない**（実ブラウザの挙動に合わせる。ここを親切に発火させると §9-1
  のバグを検出できなくなる）
- `FakePeerConnection` の sender — `replaceTrack(track)`
  が**受け取ったトラックを保持**し、`getParameters()` / `setParameters()` が往復すること

### 純粋関数として切り出してテストするもの

既存の `evaluateQuality` を `VC.evaluateQuality`
として公開している前例に倣い、判断の芯を副作用から切り離す。

- `displayConstraints(profile)` — `getDisplayMedia` に渡す制約を組み立てる
- `resolveShareOwner(selfId, peerIds)` — 同時共有の競合解決（§4.4）
- `pickProfile({ requested, relay })` — relay 検知時の降格（§6.6）

### 正常系

| #  | 内容                                                                                                                                      |
| -- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| N1 | 共有開始で、**全ピアの sender に**画面トラックが `replaceTrack` される（ピア2本以上で確認。1本だと「5個それぞれに」の要件を検証できない） |
| N2 | 全ピアの sender に `maxBitrate` / `maxFramerate` / `degradationPreference` が個別に設定される                                             |
| N3 | 全ピアへ `{ kind: "video", on: true, source: "screen" }` が飛ぶ                                                                           |
| N4 | 画面トラックに `contentHint = "text"` が入る                                                                                              |
| N5 | 停止すると、カメラ ON なら**カメラへ戻り**、カメラ OFF なら `replaceTrack(null)` になる。どちらでも `{ on, source }` が正しく告知される   |
| N6 | `displayConstraints()` が `ideal` / `max` しか含まない（`min` / `exact` / `advanced` を1つも含まない）— TypeError の作り込みを構造で防ぐ  |

偽 DOM ではレイアウトも実際のエンコードも再現できないので、以下は実機で確認する。

- CPU 使用率が §6.2 の見積もりから大きく外れていないこと（**外れていたら既定プロファイルを見直す**）
- TURN 経由に落ちたときに軽い案へ降格し、通知が出ること
