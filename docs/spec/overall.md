## 1. 用語

| 用語 | 定義 |
|---|---|
| ルーム | 1つの飲み会に対応するセッション。6桁コードとURLを持つ。公開 / 招待制のいずれか |
| 公開ルーム | トップの一覧に表示され、ノック→ホスト承認で入室できるルーム |
| ノック | 公開ルームへの入室申請。ホストが承認/拒否する |
| entryToken | ノック承認時に発行されるワンタイム入室トークン（§3.1.1） |
| ホスト | ルーム作成者。ゲーム操作・ノック承認・キックの権限を持つ |
| ホスト画面 | 画面共有やプロジェクター投影を想定した表示専用ビュー |
| 手元画面 | 各参加者のスマホ/PCに表示される入力用ビュー |
| アカウント | ユーザーID+パスワードで登録する利用者情報。**作成系機能（ルーム作成・ゲームスタジオ）にのみ必須** |
| ゲスト | アカウントなしの参加者。ルームへの参加（招待・ノック）はゲストのまま可能 |
| ゲーム定義 (GameDefinition) | ゲーム1本を宣言的に記述したデータ。公式も自作も同一形式 |
| フェーズ | ゲーム進行の状態。サーバーのみが遷移を決定する |

## 2. 画面一覧と遷移

```
[ホーム] ─ルーム作成(要ログイン)→ [ロビー(ホスト)] ─ゲーム開始→ [ゲーム中] → [結果] ─┐
   │            ↑ 未ログイン時は [ログイン/登録] を経由      ↑          ↑____ループ____│
   ├─コード/URL/QRで参加(招待制・ゲスト可)→ [ロビー(参加者)] ─┘
   └─公開ルーム一覧→ノック→承認待ち→(entryToken受領)→ [ロビー(参加者)]
```

| 画面 | 主要要素 |
|---|---|
| ホーム | ルーム作成（公開/招待の選択）/ 参加コード入力 / 公開ルーム一覧 / ゲームスタジオ導線 / ログイン状態表示・ログイン導線 / 通報フォームへのリンク |
| ログイン / 登録 | ユーザーID・パスワード入力。登録とログインをタブ切替。作成系機能へ未ログインで進んだ場合の誘導先 |
| 公開ルーム一覧 | ルーム名・現在人数・遊んでいるゲーム・ノックボタン。HTTP GETで取得（10秒ポーリング） |
| ロビー | 参加者一覧、QR表示（招待制）、ノック承認バッジ（ホスト・公開のみ）、ゲーム選択、VC操作 |
| ゲーム中 | フェーズごとの表示（§3.3）。ホスト画面と手元画面でレイアウト分離。ホストはノック承認・キックをここでも操作可 |
| 結果 | ラウンド/累計スコア、次ラウンド・ゲーム変更・終了 |
| ゲームスタジオ | ゲーム定義の作成・編集・共有コード発行・インポート（要ログイン） |

## 3. 機能要件

### 3.0 認証・アカウント

- **ログインが必須なのは作成系のみ**: ルーム作成・ゲームスタジオ（定義の作成/編集/共有コード発行）。ルームへの参加（招待制の入室・公開ルームへのノック）はゲスト可。
- 登録: ユーザーID（半角英数 4〜20 文字、一意）+ パスワード（8〜64 文字）。メールアドレスは扱わない。
- パスワードハッシュ: Web Crypto の **PBKDF2-HMAC-SHA256、反復 600,000 回**（OWASP 推奨値）、ユーザーごとにランダム salt（16 バイト以上）。平文・可逆形式での保存禁止。
- セッション: ログイン成功時に 32 バイトのランダムトークンを発行し、**HttpOnly / Secure / SameSite=Lax の Cookie** で保持。サーバー側は Deno KV `authSession:{token}` に保存、有効期限 30 日。ログアウトでサーバー側も破棄。
- 認証 API は HTTP（§4）。WebSocket の作成系メッセージ（`createRoom`）は、WS アップグレード時の Cookie で認証済みであることをサーバーが検証する。
- パスワード変更・リセット・退会は v1 では作らない（割り切り。リセット不能である旨を登録画面に明記）。

### 3.1 ルーム管理

- 作成時に公開 / 招待制を選択（後から変更不可。変更したい場合は作り直し）。公開ルームはルーム名（20文字以内）必須。**作成にはログイン必須**
- **ニックネームは全画面共通で 20 文字以内**（ゲスト・ログイン済みとも入室時に入力。アカウントのユーザーIDとは独立）
- 参加方法:
  - 招待制: URL（`/r/{code}`）・QR・6桁コード → ニックネーム入力で入室（ゲスト可）
  - 公開: 一覧からノック（ニックネームを添える）→ ホスト承認で入室（§3.1.1）。拒否・60秒無応答はその旨を申請者に表示
- 定員: 10人（VC参加は最大6人。7人目以降はVCなしで参加）
- **満員時のノック承認**: 参加者が定員（10人）に達している間、ホストが `approveKnock` を送った場合サーバーは `error: ROOM_FULL` を返し、**ノック申請は保留のまま残す**（申請自体の60秒タイムアウトは進行する）。ホストUIは満員の間、承認ボタンを無効化して「満員」と表示する
- **キック**: ホストは任意の参加者を退出させられる。キック時に対象の sessionToken を当該ルームのブロックリストに追加し、同一セッションでの再入室・再ノックを拒否する（ブラウザ変更等での回避は防げない。v1の割り切りとして明記）
- 最終アクティビティから24時間で自動削除。公開一覧には稼働中ルームのみ表示
- ホスト切断時、60秒以内の再接続でホスト権限維持。60秒経過で最古参加者に自動委譲（ノック承認・キック権限も移る）

#### 3.1.1 ノック承認後の入室フロー（entryToken 方式）

公開ルームは6桁コードを公開しないため、承認済みであることの証明として**ワンタイムトークン**を用いる。

```
申請者                         サーバー                        ホスト
  │ knock {roomCode,nickname}    │                              │
  │─────────────────────────────→│ knockRequest {knockId,...}   │
  │                              │─────────────────────────────→│
  │                              │        approveKnock {knockId}│
  │                              │←─────────────────────────────│
  │                              │ entryToken 発行(60秒有効・1回限り)
  │ knockResult {accepted:true,  │                              │
  │   roomCode, entryToken}      │                              │
  │←─────────────────────────────│                              │
  │ join {roomCode, nickname,    │                              │
  │   entryToken}                │                              │
  │─────────────────────────────→│ 検証・消費 → 入室            │
```

- entryToken は 16 バイト以上のランダム値。ルームのメモリ上に保持し、**60秒で失効・使用は1回限り**
- 公開ルームへの `join` は有効な entryToken を必須とする（無い/不正/期限切れ → `error: INVALID_TOKEN`）。招待制ルームの `join` には不要
- ノック時のニックネームと join 時のニックネームは一致させる（サーバーが検証。表示上の別人偽装防止）
- 承認後60秒以内に join しなかった場合は失効。申請者には再ノックを促す表示を出す
- キック時、その対象に発行済みの未使用 entryToken は即時無効化する

### 3.2 リアルタイム同期基盤

**設計原則（実装より優先される規約）**

1. サーバーが唯一の状態機械。クライアントは表示とイベント送信のみを行い、状態遷移を判断しない
2. ルームごとにイベントを直列処理する。**状態遷移関数の内部で await を使用しない**（KVアクセス等は遷移の前後で行う）
3. クライアントには各自に見えてよい情報のみ送る（回答の匿名性、クイズ正解、ノック申請者一覧はホストのみ）

**接続管理**

- WebSocket 1本を全用途（ゲーム同期・VCシグナリング・ノック/キック通知）で共用
- 切断後60秒はセッション保持。同一 sessionToken での再接続時にフルスナップショットを送って復帰
- 60秒超過で退室扱い。進行中ゲームは§8の異常系マトリクスに従う

### 3.3 ゲームエンジン

フェーズ状態機械（全ゲーム共通）:

```
lobby → intro → prompt → input → reveal → judge → roundResult → (次ラウンド: prompt へ) → finalResult → lobby
```

- 各フェーズはタイマー（ゲーム定義で指定）または全員完了で遷移。ホストはスキップ可
- reveal は入力を匿名シャッフル表示（定義で実名に変更可）
- judge は scoring 方式に従いサーバーが計算

### 3.4 収録ゲーム（公式3種）

| ゲーム | input | scoring | 備考 |
|---|---|---|---|
| 大喜利 | text | vote（投票数=得点。自票禁止） | reveal は匿名 |
| 以心伝心 | text | match（正規化後の一致人数=各自の得点） | 全員一致でボーナス |
| クイズ | choice | correct（正解+早さボーナス） | お題セットから出題 |

- 公式ゲームも GameDefinition 形式で記述し、自作と同一エンジンで動かす（エンジンの特別扱い禁止）
- **match の正規化規則**（ユニットテスト対象のため確定仕様とする）: ①前後空白を除去 ②連続空白を1つに圧縮 ③英字は小文字化 ④全角英数字・記号は半角化 ⑤カタカナはひらがな化。**漢字/かなの表記ゆれ（例:「猫」と「ねこ」）は同一視しない**（v1 の割り切り）

### 3.5 ゲームスタジオ（自作ゲーム）

GameDefinition はコードではなく宣言的データ。実行可能スクリプトは受け付けない。

```ts
type GameDefinition = {
  id: string;              // uuid
  ownerId: string;         // 作成者のユーザーID（サーバーが付与。クライアント指定不可）
  title: string;           // 20文字以内
  description?: string;    // 100文字以内
  rounds: number;          // 1..10
  inputType: "text" | "choice";
  inputTimeSec: number;    // 10..180
  reveal: "anonymous" | "named";
  scoring: "vote" | "match" | "correct";
  prompts: Prompt[];       // 1..50件
};

type Prompt =
  | { kind: "open"; text: string }
  | { kind: "choice"; text: string; options: string[]; answer?: number }; // answer必須は scoring=correct のみ
```

- **作成・編集・共有コード発行はログイン必須**。定義は作成者アカウントに紐づき、スタジオには自分の定義のみ一覧表示。編集・削除は所有者のみ
- **インポート（共有コード/URL からの取込）とルームでの使用はゲスト可**（ホストがルームのゲーム選択に追加する操作を含む）
- バリデーション: 文字数/件数上限、scoring と inputType の整合（vote は text のみ等）をサーバー側で検証
- 保存: Deno KV。`game:{id}` に定義本体、共有コード（8桁英数）→ id のマップを別キー、`userGames:{userId}` に所有一覧
- **保存上限: 1アカウントにつき 50 定義**（超過時はエラー。古いものの削除を促す）
- 共有: 共有コード入力またはURL（`/g/{shareCode}`）でインポート。ルームのゲーム選択に「コードで追加」
- **安全性の考え方**: GameDefinition は実行不能な宣言的データのみのため、**任意コード実行のリスクは構造的に存在しない**。残るリスクは①表示テキスト経由の XSS（§3.8 の描画規定で対処）と②不適切な文言（通報＋ホスト承認制で対処）の2点であり、公開フィード・検索・ランキングは作らないことで拡散面も抑える

### 3.6 VC / カメラ（分離モジュール）

- WebRTC P2P フルメッシュ。シグナリングは既存WebSocketのメッセージとして実装
- STUN: 公開STUNサーバー。TURN: VPS上に coturn（P2P不成立の回線対策）
- 実装順: ①音声のみ → ②カメラ。品質劣化時は映像を自動停止し音声優先
- **カメラは全ルームで初期OFF**。本人の明示操作でのみON（公開ルームで知らない人にいきなり顔が映る事故の防止）
- キックされた参加者のピア接続はサーバー通知を受けた各クライアントが即時クローズする
- **フォールバック規定**: P4着手時点でP1〜P3に未完了項目が残る場合、VCは実装せず「外部通話ツール併用」を正式仕様とする（チーム判断で仕様書を改版）

### 3.7 安全設計（公開ルーム）

- ノック承認制・キック（§3.1）
- ニックネームのみ・プロフィールなし・フレンド/DMなし（アカウントのユーザーIDは他者に表示しない）
- 通報: ホームとルーム内フッターに外部フォーム（Google Forms）へのリンク。自動処理は作らない
- 対象年齢20歳以上を想定する旨をトップに表記（自己申告。厳密な年齢確認は作らない）

### 3.8 セキュリティ要件（全画面共通）

- **XSS**: ユーザー由来のテキスト（ニックネーム・ルーム名・ゲーム定義の全文言・回答・チャット的表示のすべて）を DOM に出す際は `textContent` を使用する。`innerHTML` への未サニタイズ代入は禁止。HTML を組み立てる場合は明示的にエスケープする（CLAUDE.md セキュリティ基準に準拠）
- **CSP**: 全ページに `Content-Security-Policy`（`default-src 'self'` 基調。WebSocket/STUN/TURN の接続先のみ許可）を設定する
- **CSRF**: 状態を変更する HTTP エンドポイントは `Origin` ヘッダを検証する。Cookie は SameSite=Lax
- **レート制限**（session/IP 単位。超過は `error: RATE_LIMITED`）:
  - ログイン試行: IP ごとに 5回/分
  - 登録: IP ごとに 3件/時
  - ノック: 同一セッションから同一ルームへ 10秒に1回。1ルームの保留ノックは最大5件（超過分は即時拒否）
  - ルーム作成: 1アカウントにつき同時 3 ルームまで
  - WS メッセージ: 1接続あたり 20件/秒 を超えたら切断
- **rtcSignal の中継条件**: サーバーは `to` が送信者と同一ルームの接続中メンバーである場合のみ中継する。それ以外は破棄
- **KV 上限**: ゲーム定義は 1アカウント 50 件（§3.5）。1定義の直列化サイズ上限 64KB
- 秘密情報（TURN 認証情報等）は `.env` のみ。クライアント配布物に埋め込まない

## 4. メッセージプロトコル

TypeScript の discriminated union で先に固定し、実装はこの型に従う。**型定義の変更はチーム合意を必須とする。**

### 4.0 HTTP エンドポイント

| メソッド/パス | 認証 | 内容 |
|---|---|---|
| `POST /api/auth/register` | 不要 | `{ userId, password }` → 登録+ログイン。Cookie 発行 |
| `POST /api/auth/login` | 不要 | `{ userId, password }` → Cookie 発行 |
| `POST /api/auth/logout` | 要 | セッション破棄 |
| `GET /api/me` | 任意 | ログイン状態の確認（`{ userId }` または 401） |
| `GET /api/rooms` | 不要 | 稼働中公開ルームの配列（一覧の10秒ポーリング用） |
| スタジオ CRUD (`/api/games` 系) | 要 | 定義の作成/更新/削除/一覧。詳細は設計書で確定 |

WS は接続後のリアルタイム用途に限定する。

### 4.1 WS メッセージ型

```ts
// Client → Server
type C2S =
  | { t: "createRoom"; nickname: string; visibility: "public" | "private"; roomName?: string } // 要ログイン(Cookie)
  | { t: "join"; roomCode: string; nickname: string; session?: string; entryToken?: string }   // 公開ルームは entryToken 必須
  | { t: "knock"; roomCode: string; nickname: string }                          // 公開・ゲスト可
  | { t: "approveKnock"; knockId: string }                                      // host only
  | { t: "rejectKnock"; knockId: string }                                       // host only
  | { t: "kick"; playerId: string }                                             // host only
  | { t: "selectGame"; gameId: string }                                         // host only
  | { t: "startGame" }                                                          // host only
  | { t: "skipPhase" }                                                          // host only
  | { t: "submitInput"; value: string | number }
  | { t: "submitVote"; targetPlayerId: string }
  | { t: "importGame"; shareCode: string }                                      // host only
  | { t: "rtcSignal"; to: string; payload: unknown }
  | { t: "leave" };

// Server → Client
type S2C =
  | { t: "roomState"; snapshot: RoomSnapshot }                 // 参加/再接続時のフル状態
  | { t: "playerJoined" | "playerLeft"; player: PlayerPublic }
  | { t: "knockRequest"; knockId: string; nickname: string }   // host only
  | { t: "knockResult"; accepted: boolean; roomCode?: string; entryToken?: string } // 申請者のみ
  | { t: "kicked" }                                            // 対象者のみ。受信後クライアントはホームへ
  | { t: "playerKicked"; playerId: string }                    // 残存メンバーへ（VCピア切断指示を兼ねる）
  | { t: "phase"; phase: Phase; deadline?: number; view: PhaseView } // view は受信者ごとに異なる
  | { t: "roundResult" | "finalResult"; scores: ScoreEntry[] }
  | { t: "hostChanged"; playerId: string }
  | { t: "rtcSignal"; from: string; payload: unknown }
  | { t: "error"; code: ErrorCode; message: string };
```

### 4.2 ErrorCode（初版）

```ts
type ErrorCode =
  | "AUTH_REQUIRED"    // 作成系を未ログインで実行
  | "ROOM_NOT_FOUND"   // コード不正・削除済み
  | "ROOM_FULL"        // 定員超過（join / approveKnock）
  | "NOT_HOST"         // host only メッセージを非ホストが送信
  | "INVALID_TOKEN"    // entryToken 不正・期限切れ・使用済み
  | "BLOCKED"          // キック済みセッションの再入室/再ノック
  | "RATE_LIMITED"     // §3.8 のレート制限超過
  | "PHASE_MISMATCH"   // 現フェーズで受理できないメッセージ（期限後 submit 等）
  | "INVALID_INPUT"    // バリデーション不正（文字数超過等）
  | "DUPLICATE";       // 冪等処理で弾いた二重送信
```

### 4.3 未確定型の確定プロセス

`RoomSnapshot` / `PhaseView` / `Phase` / `ScoreEntry` / `Knock` / `GameState` / `PlayerPublic` の詳細定義は**コアシステム実装（P1）で確定させ、確定後に本書 v0.4 へ反映する**。それまで本書のプロトコル型はドラフト扱いとし、確定前に他メンバーの実装がこれらの型に依存しないよう作業を分担する。確定後の変更はチーム合意必須（本節冒頭の規約に従う）。

## 5. データモデル

```ts
type User = {
  userId: string;          // 半角英数 4..20、一意
  passwordHash: string;    // PBKDF2-HMAC-SHA256 600,000回
  salt: string;
  createdAt: number;
};
// KV: user:{userId} / authSession:{token} → { userId, expiresAt }

type Room = {
  code: string;
  visibility: "public" | "private";
  roomName?: string;                 // publicのみ
  hostId: string;
  players: Map<string, Player>;      // メモリ上。KVには置かない
  pendingKnocks: Map<string, Knock>; // publicのみ
  pendingEntries: Map<string, PendingEntry>; // entryToken → 承認情報（60秒TTL・1回限り）
  blockedSessions: Set<string>;      // キック済みsessionToken
  game: GameState | null;
  createdAt: number;
  lastActiveAt: number;
};

type Player = {
  id: string; nickname: string;      // nickname は 20文字以内
  connected: boolean; disconnectedAt?: number;
  sessionToken: string;
  score: number;
};
```

- ルーム状態はプロセスメモリのみ（KV不使用）。**単一プロセスデプロイが前提**
- Deno KV に置くのは アカウント（User）・認証セッション・GameDefinition・共有コードマップのみ

## 6. デプロイ

- **想定環境: Xserver VPS 4GB プラン（vCPU 4コア / メモリ 4GB / NVMe SSD 150GB）**。本仕様の規模（同時20ルーム・約200接続 + coturn）に対し十分な余裕がある
- VPS上で `deno run` 単一プロセス + Caddy/Nginx でTLS終端（WebSocketプロキシ設定必須）。coturn 用の UDP ポートはパケットフィルターで開放する
- Deno Deploy利用時は isolate 間でメモリ非共有のため BroadcastChannel/KV 同期の改修が必要。v1では採用しない
- 環境変数: `.env`（TURN認証情報等）。リポジトリには `.env.example` のみ

## 7. 非機能要件

- 同時ルーム数 20 / 1ルーム最大10人（ボットで50接続まで負荷確認）
- 操作から他クライアント反映まで500ms以内（同一リージョン）
- 対応ブラウザ: 直近版 Chrome / Safari / Edge（iOS Safari を必須動作対象に含む）
- 日本語UIのみ

## 8. 異常系マトリクス

行=フェーズ、列=イベント。★はチームで最終確認したい項目。ボットテスト（§9）はこの表のセルを網羅する。

| | 参加者切断 | 再接続(60s内) | ホスト切断 | 途中参加/入室 | 遅延メッセージ | キック | キック済みの再入室/再ノック |
|---|---|---|---|---|---|---|---|
| lobby | 一覧から非表示 | 復帰 | 60s後委譲 | 参加可 | 無視 | 即退出・全員に通知 | 拒否(error) |
| prompt/input | 未提出のまま進行、完了判定から除外 | 復帰・残り時間で入力可 | 続行、60s後委譲 | ★観戦のみ(次ラウンドから) | 期限後submitは破棄しerror | スコアごと除外。完了判定から即除外 | 拒否 |
| reveal/judge | 影響なし | 復帰 | 同上 | 観戦のみ | 期限後voteは破棄 | 同上。当人への票は無効化 | 拒否 |
| roundResult | 影響なし | 復帰 | 同上 | ★次ラウンドから参加 | 無視 | 即退出 | 拒否 |
| finalResult | 影響なし | 復帰 | 同上 | 参加可(次ゲーム) | 無視 | 即退出 | 拒否 |
| ノック承認待ち(公開) | 申請破棄 | ★申請は復元しない(再ノック) | 承認者不在→委譲後のホストに引継ぎ | — | 60s無応答で自動拒否 | — | 拒否 |
| VC接続中 | 該当ピアのみ切断。ゲームに影響させない | 再ネゴシエーション | VCは対等、影響なし | 7人目以降はVCなし | ICE遅延は許容 | 全ピアが対象との接続を即クローズ | — |

共通規定:

- 進行中に2人未満になったゲームは中断し lobby へ
- 同一イベントの二重送信（連打）はサーバー側で冪等処理
- ホスト委譲後も blockedSessions は維持する
- **サーバー再起動（デプロイ・クラッシュ含む）で全ルームは消滅する**（ルーム状態はメモリのみのため）。アカウントとゲーム定義は KV 上に残る。v1 の割り切りとして許容し、**発表デモ・運用中の再起動は行わない**運用ルールとする

## 9. テスト計画

1. **ユニット**: 採点ロジック（vote/match/correct、§3.4 正規化規則）、GameDefinitionバリデーション、フェーズ遷移関数、ブロックリスト判定、パスワードハッシュ/セッション検証、entryToken 発行・消費・失効、レート制限判定
2. **ボット結合テスト**: N人分の自動クライアントで§8マトリクスの各セルを再現。公開ルーム系（ノック→承認→entryToken→入室→キック→再ノック拒否）と満員時の approveKnock 拒否のシナリオを必須に含める。CIでは8ボット1ゲーム完走をスモークとして実行
3. **実機テスト**: スマホ実機4台以上、Wi-Fi/モバイル回線混在で通し確認（P5必須）
4. **VC**: 4人通話を Chrome/Safari 混在で確認。TURN経由を強制するケースを1つ含める

## 10. リスクと対応

| リスク | 兆候 | 対応 |
|---|---|---|
| WebRTCが期間内に安定しない | P4開始2日目で4人通話が不安定 | §3.6フォールバック発動（VC切り・外部通話併用を正式化） |
| 公開ルームの荒らし | デモ/運用中の妨害 | ノック承認とキックで対処。発表デモは招待制ルームで行い、公開側はスクリーンショット/別動画で見せる選択肢を持つ |
| 同期バグ多発 | ボットテストで再現する競合 | §3.2規約違反を疑い、遷移関数内awaitを監査 |
| スコープ肥大 | 仕様書にない機能のPR | ホワイトリスト運用で差し戻し |
| Deno向けでないコード生成 | 非推奨import等 | CLAUDE.md規約＋`deno check`/`deno lint`をCIとフックで強制 |

## 11. 発表デモ手順（骨子）
