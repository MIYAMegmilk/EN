## 1. 用語

| 用語 | 定義 |
|---|---|
| ルーム | 1つの飲み会に対応するセッション。6桁コードとURLを持つ。公開 / 招待制のいずれか |
| 公開ルーム | トップの一覧に表示されるルーム。作成時に「オープン入室」か「承認制」を選ぶ（`entryMode: "open" \| "knock"`） |
| オープン入室 | 公開ルームの入室方式の1つ。一覧から承認なしで即入室できる |
| 承認制 | 公開ルームの入室方式の1つ。ノック→ホスト承認で入室する |
| 招待制ルーム | 一覧に表示されないルーム（`visibility: "private"`。知り合い向け）。6桁コード・URL で入る（**QR は【未実装】**。`public/` にも `server/` にも QR の実装は無い。§2 ロビーの記載も同じ）。**任意で合言葉**（4〜20文字。サーバー内のみ保持しクライアントへ送らない）を付けられ、付けた場合は合言葉でも入れる |
| 合言葉 | 招待制ルームに任意で設定できる入室用の言葉。全ルーム横断で一意・大文字小文字は区別しない（§3.1） |
| ランダムマッチ | 待機列に並んだ利用者同士を一定周期で自動的に相席させる入室方式（§3.1.2） |
| ノック | 承認制の公開ルームへの入室申請。ホストが承認/拒否する |
| bot | ルームの場回しを行うルールベースのファシリテーター（§3.10）。外部 AI API は使わない |
| あだ名 | 入室時に名乗る表示名（ニックネームと同義、20文字以内）。ログイン済みならアカウントに保存され自動入力される |
| 趣味タグ | 運営が用意したプリセットから選ぶ興味関心のタグ（§3.11）。表示・マッチング優先・bot の話題振りに使う |
| 名札 | あだ名・趣味タグを編集する軽量プロフィールページ（`profile.html`）。ログイン中・ゲストのどちらもここで編集する |
| entryToken | ノック承認時に発行されるワンタイム入室トークン（60秒有効・1回限り、§3.1.1） |
| ホスト | ルーム作成者。ゲーム操作・ノック承認・キックの権限を持つ |
| ホスト画面 | 画面共有やプロジェクター投影を想定した表示専用ビュー。**【未実装】v1 では全員同一ビュー（レイアウト分離なし）** |
| 手元画面 | 各参加者のスマホ/PCに表示される入力用ビュー。**【未実装】同上（v1 では全員同一ビュー）** |
| アカウント | ユーザーID+パスワードで登録する利用者情報。**作成系機能（ルーム作成・ゲームスタジオ）にのみ必須** |
| ゲスト | アカウントなしの参加者。ルームへの参加（合言葉・ノック・オープン入室・ランダムマッチ）はゲストのまま可能 |
| ゲーム定義 (GameDefinition) | ゲーム1本を宣言的に記述したデータ。公式も自作も同一形式 |
| フェーズ | ゲーム進行の状態。サーバーのみが遷移を決定する |

## 2. 画面一覧と遷移

「画面」は論理単位であり、**物理的な HTML ページは以下の7枚**（`public/` 直下）。ホーム・公開ルーム一覧・マッチング待機・ロビー・ゲーム中・結果は独立ページではなく、すべて `index.html` 1枚の中のセクション切り替えで実現している（`room.html` / `studio.html` は存在しない）。

| ページ | 役割 |
|---|---|
| `login.html` | ログイン / 登録（タブ切替）。「ふらっと（ゲスト）で入る」導線もここ |
| `entrance.html` | 入り口選択。お座敷一覧（`index.html`）／廊下（`corridor.html`）／卓を建てる（`create-room.html`）への3カードのみ。**名札（`profile.html`）への導線は無い**（カード内に見える「名札」ピルは `index.html` の見た目を縮小した装飾画像の一部で、`aria-hidden="true"` のリンクではない要素） |
| `index.html` | メイン画面。**ホーム＋公開ルーム一覧**（`#entry`）、**マッチング待機**（ホーム内のインライン表示 `#queue-waiting`）、**ロビー**（`#room`: 参加者一覧・ノック承認 `#knocks`・ゲーム選択 `#lobby-controls`）、**ゲーム中**（`#phase`）、**結果**（`#result`）、VC（`#vc`）・チャット（`#chat`）を内包する単一ページ |
| `create-room.html` | ルーム作成（卓を建てる）。作成内容は `room-handoff.js`（sessionStorage）経由で `index.html` に渡し、`index.html` が WS の `createRoom` を送る |
| `corridor.html` | 廊下ビュー（3Dの代替導線）。扉を選ぶと `room-handoff.js` 経由で `index.html` に遷移し自動入店する |
| `profile.html` | 名札（軽量プロフィール編集）。あだ名・趣味タグの編集はこのページに一本化 |
| `debug.html` | 開発用デバッグ画面。`EN_DEBUG_TOKEN` 未設定時は404（存在を伏せる） |

- トップ `/` はログイン済みなら `entrance.html`、未ログインなら `login.html` を返す（Cookie 依存のため `cache-control: no-store`）。招待URL `/r/{code}` は `index.html` を返す。
- ログイン成功後・ゲスト入室後は、まず [入り口選択] 画面を経由して [ホーム]（一覧）または [廊下ビュー]（3D・実験的な代替導線）のどちらで卓を探すか選ぶ。

```
[ログイン/登録 login.html] ─ログイン or ゲスト→ [入り口選択 entrance.html]
   ├─→ [ホーム index.html] ─公開一覧から入室/ノック・コード/合言葉入力・いますぐ飲む→ [ロビー(index.html内)]
   ├─→ [廊下ビュー corridor.html] ─扉を選ぶ→ (room-handoff) → [index.html で自動入店]
   └─→ [卓を建てる create-room.html] ─作成(要ログイン)→ (room-handoff) → [ロビー(ホスト)]
[ロビー] ─ゲーム開始→ [ゲーム中] → [結果] ─次ラウンド/ゲーム変更のループ→ [ロビー/ゲーム中]
```

| 画面（論理） | 主要要素 |
|---|---|
| ホーム | **「いますぐ飲む」（ランダムマッチ）** / 公開ルーム一覧 / 合言葉入力 / 参加コード入力 / 卓を建てる導線（`create-room.html` へ遷移。ログイン時のみ表示）/ ログイン状態表示・名札・ログイン導線（のれんをくぐる／お会計）/ ゲームスタジオ導線【未実装】 / 通報フォームへのリンク【未実装】 |
| マッチング待機 | ホーム内のインライン表示（`#queue-waiting`）。「席を探しています…」＋やめる（キャンセル）ボタン。成立するとロビーへ自動遷移 |
| ログイン / 登録 | ユーザーID・パスワード入力。登録とログインをタブ切替。作成系機能へ未ログインで進んだ場合の誘導先 |
| 入り口選択 | 卓の探し方（お座敷いちらん／廊下を歩く／卓を建てる）の選択。あだ名・趣味タグの編集は独立ページ「名札」（`profile.html`）に統合している。**入り口選択から名札へ行く導線は【未実装】**で、現状は一度ホーム（`index.html`）まで進み、ヘッダーの「名札」リンクから入る |
| 廊下ビュー | 3Dで通路を歩いて卓を探す実験的な代替導線。扉を選ぶと room-handoff（sessionStorage）経由で `index.html` に遷移し自動入店する |
| 公開ルーム一覧 | ルーム名・卓の説明文（100文字以内）・タグ・現在人数・遊んでいるゲーム・入室/ノックボタン。HTTP GETで取得（10秒ポーリング）。サムネ（プリセット画像選択）【未実装】 |
| ロビー | 参加者一覧、ノック承認バッジ（ホスト・公開のみ）、ゲーム選択、VC操作、チャット。QR表示【未実装】 |
| ゲーム中 | フェーズごとの表示（§3.3）。ホストはノック承認・キックをここでも操作可。ホスト画面と手元画面のレイアウト分離【未実装・全員同一ビュー】 |
| 結果 | ラウンド/累計スコア、次ラウンド・ゲーム変更・終了 |
| ゲームスタジオ | ゲーム定義の作成・編集・共有コード発行・インポート（要ログイン）。**【未実装】ページ・導線とも未着手（サーバー側の KV CRUD 関数のみ存在。§4.0 参照）** |

## 3. 機能要件

### 3.0 認証・アカウント

- **ログインが必須なのは作成系のみ**: ルーム作成・ゲームスタジオ（定義の作成/編集/共有コード発行。スタジオ自体は【未実装】）。ルームへの参加（合言葉ルームの入室・公開ルームへのノック）はゲスト可。
- 登録: ユーザーID（半角英数 4〜20 文字、一意）+ パスワード（8〜64 文字）。メールアドレスは扱わない。ID の一意性は KV の atomic チェックで保証し、重複は 409 を返す。
- パスワードハッシュ: Web Crypto の **PBKDF2-HMAC-SHA256、反復 600,000 回**（OWASP 推奨値）、ユーザーごとにランダム salt（16 バイト）。平文・可逆形式での保存禁止。ユーザー列挙対策として、存在しない ID へのログイン試行にもダミー salt で同コストのハッシュ計算を行い、比較はタイミングセーフに行う。
- セッション: ログイン成功時に 32 バイトのランダムトークンを発行し、**HttpOnly / Secure / SameSite=Lax の Cookie** で保持。サーバー側は Deno KV `authSession:{token}` に保存（`expireIn` 付き）、有効期限 30 日。ログアウトでサーバー側も破棄。
- 認証 API は HTTP（§4）。WebSocket の作成系メッセージ（`createRoom`）は、WS アップグレード時の Cookie で認証済みであることをサーバーが検証する（未認証は `AUTH_REQUIRED`）。
- パスワード変更・リセット・退会は v1 では作らない（割り切り）。リセット不能である旨（「パスワードの再発行はできません」）は `login.html` の**ログインタブに掲出済み**だが、ログインタブと登録タブは排他表示のため、**登録タブを開いている間は表示されない**（登録タブへの掲出は残作業）。
- **アカウントに保存できる軽量プロフィール**: あだ名（表示名、20文字以内・ニックネームと同じ検証規則）と趣味タグ（§3.11、最大5個）。保存済みなら入室・待機時に自動入力され、その場で変更もできる。ゲストはアカウントを持たないためサーバー・KVには保存されないが、名札ページ（`profile.html`）で編集した内容をブラウザのセッション（sessionStorage、タブを閉じるまで）に限り一時的に保持し、入室フォームへの自動入力に使う。

### 3.1 ルーム管理

- 作成時に **公開（`visibility: "public"`）/ 招待制（`visibility: "private"`）** を選ぶ（後から変更不可。変更したい場合は作り直し）。公開ルームはさらに**入室方式**（`entryMode`: オープン入室 `open` / 承認制 `knock`。省略時は `open`）を選ぶ。招待制ルームには**任意で合言葉**を付けられる（付けなければ6桁コード・URL のみで入る。**QR は【未実装】**）
  - 承認制（`knock`）は公開ルームにのみ設定でき、合言葉は招待制ルームにのみ付けられる（いずれも違反は `INVALID_INPUT`）
- 公開ルームはルーム名（20文字以内・制御文字禁止）必須。**作成にはログイン必須**（未ログインは `AUTH_REQUIRED`。ランダムマッチの自動生成ルームを除く）
- **1アカウントが同時に持てるルームは 3 つまで**（`ROOMS_PER_ACCOUNT_MAX`。超過は `RATE_LIMITED`）。ランダムマッチが建てる卓（`ownerUserId` が空文字）は数えない
- **ニックネームは全画面共通で 20 文字以内**（前後空白を除いた 1〜20 コードポイント・制御文字禁止。アカウントのユーザーIDとは独立）
  - **入室時のニックネームは省略可**で、省略するとサーバー（あだ名 bot）が趣味タグから二つ名を付ける（§3.0 / §3.10）。空文字は「入力し忘れ」と区別できないため `INVALID_INPUT` で弾く
  - **ノック時のみニックネームは必須**（ホストの判断材料が名前しかないため）
- 参加方法:
  - 招待制ルーム: URL（`/r/{code}`）・6桁コード（**QR は【未実装】**）、または**合言葉（4〜20文字。制御文字禁止。大文字小文字は区別しない。全ルーム横断で一意、重複時は作成エラー `DUPLICATE`）**を入力 → 入室（ゲスト可）。`join` は `roomCode` と `passphrase` のどちらでも引ける（両方あれば `roomCode` を優先）。合言葉が違うのか卓が無いのかは区別せず `ROOM_NOT_FOUND` を返す（総当たりで「当たり」が分からないようにするため）
  - 公開・オープン入室（`entryMode: "open"`）: 一覧から選んで**承認なしで即入室**。防波堤はキック・ブロック・通報（§3.7）
  - 公開・承認制（`entryMode: "knock"`）: 一覧からノック（ニックネームを添える）→ ホスト承認で入室（§3.1.1）。拒否・60秒無応答はその旨を申請者に表示
  - ランダムマッチ: §3.1.2
- 定員: 10人（VC参加は最大6人。7人目以降はVCなしで参加）。**VC 枠は参加順の先頭6人**に自動で割り当てられ、枠内の人が在籍から外れると7人目以降が繰り上がる。サーバーは割り当てが変わった人の `PlayerPublic.vcEligible` だけを配り直す
- 卓の説明文（100文字以内）とルームタグ（プリセットから**最大5個**、`ROOM_TAGS_MAX`）は、作成後に所有者が `PATCH /api/rooms/{code}` で設定・変更できる。`visibility` / `entryMode` / `passphrase` を後から書き換える経路は無い
- **満員時のノック承認**: 参加者が定員（10人）に達している間、ホストが `approveKnock` を送った場合サーバーは `error: ROOM_FULL` を返し、**ノック申請は保留のまま残す**（申請自体の60秒タイムアウトは進行する）。ホストUIは満員の間、承認ボタンを無効化して**「満席」**と表示する
- **キック**: ホストは自分以外の任意の参加者を退出させられる（自分自身のキックは `INVALID_INPUT`。ホストが抜けたいときは退室＝ホスト委譲を伴う既存経路を通す）。対象へ `kicked` を送ってソケットを閉じ、残存メンバーへ `playerKicked`（VCピア切断指示を兼ねる）を配る
  - キック時に対象の sessionToken を当該ルームのブロックリストに追加し、**再入室・再ノック時にクライアントが提示した sessionToken と照合して**拒否する（`BLOCKED`）。同時に、その相手へ発行済みの未使用 entryToken と保留中のノック申請も破棄する
  - **トークンの提示はクライアント任せ**（`join.session` / `knock.session` の自己申告）である。したがって sessionStorage を消す・別ブラウザや別タブで開き直す・改造クライアントを使う、といった回避は**防げない**（v1 の割り切り）。実効的な防波堤は「即キック + 通報 + 入り直せる手軽さ」（§3.7）とする
- 公開一覧には稼働中の公開ルーム（`visibility: "public"` かつルーム名あり）のみ表示する。ルームはプロセスメモリ上にのみ存在し、**在籍者が0人になった時点で破棄**される
- **【未実装】最終アクティビティから24時間での自動削除**（`server/rooms.ts` の TODO）。`Room.lastActiveAt` の更新は行っているが掃除処理が無いため、ホストがタブを開いたまま放置した卓は残り続け、`ROOMS_PER_ACCOUNT_MAX`（3）の枠と公開一覧を占有し続ける
- ホスト切断時、60秒以内の再接続でホスト権限を維持する。60秒経過で**在籍者のうち最古の「接続中」の参加者**へ自動委譲する（誰も接続していないときだけ最古の在籍者へ倒す）
  - 「最古の接続中」を優先するのは、最古の在籍者が再接続猶予中（`connected: false`）だと「その場に居ない人」がホストになり、残った全員のホスト操作が `NOT_HOST` で弾かれて最長60秒卓が固まるため
  - 権限は `hostId` 一本で判定されるため、ノック承認・キック権限も同時に移る。委譲は `hostChanged` で全員へ通知する

#### 3.1.1 ノック承認後の入室フロー（entryToken 方式）

公開ルームの6桁コードは公開一覧（`GET /api/rooms` の `PublicRoomSummary.code`）に含まれ、未ログインでも取得できる。したがってコードの秘匿では承認制を担保できない。そこで承認済みであることの証明として**ワンタイムトークン（entryToken）**を用い、`entryMode: "knock"` のルームへの `join` にはこれを必須とする。

```
申請者                         サーバー                        ホスト
  │ knock {roomCode,nickname,    │                              │
  │        session?}             │                              │
  │─────────────────────────────→│ knockRequest {knockId,...}   │
  │                              │─────────────────────────────→│
  │                              │        approveKnock {knockId}│
  │                              │←─────────────────────────────│
  │                              │ entryToken 発行(60秒有効・1回限り)
  │ knockResult {accepted:true,  │                              │
  │   roomCode, entryToken}      │                              │
  │←─────────────────────────────│                              │
  │ join {roomCode, nickname,    │                              │
  │   entryToken}                │                              │
  │─────────────────────────────→│ 検証・消費 → 入室            │
```

- 申請の増減があるたび、サーバーは**ホストにのみ** `roomState` を再送して `pendingKnocks`（`KnockPublic[]`）を更新する（承認・拒否・60秒失効・申請者の切断でも同様）。§3.2 原則3 により他の参加者には送らない
- entryToken は `crypto.randomUUID()` のハイフンを除いた32桁の16進文字列。ルームのメモリ上（`Room.pendingEntries`）に保持し、**60秒で失効・使用は1回限り**（消費時に Map から削除する。`PendingEntry.used` フィールドは定義されているが、削除方式で使い切るため実質未使用）
  - なお UUIDv4 の実エントロピーは **122 ビット**であり、当初仕様の「16バイト（＝128ビット）以上のランダム値」をわずかに下回る。厳密に満たすには `crypto.getRandomValues(new Uint8Array(16))` への変更が必要で、これはチーム判断とする
- **公開かつ承認制（`entryMode: "knock"`）のルームへの `join` は有効な entryToken を必須とする**（無い/不明/使用済み/期限切れ/ノック時のあだ名と不一致 → `error: INVALID_TOKEN`）。公開・オープン入室（`entryMode: "open"`）および招待制ルームの `join` には不要
- ノック時のニックネームと join 時のニックネームは一致させる（サーバーが検証。比較は前後空白を除いた正規化後の値どうし。表示上の別人偽装防止）
- ノック申請自体は 60秒（`KNOCK_TTL_MS`）で自動拒否される。承認後も60秒以内に join しなければ entryToken が失効する
  - **`knockResult` は拒否・時間切れ・卓の消滅を区別しない**（`{accepted: false}` のみ）。したがって申請者への表示も「入店をお断りされました（時間切れの場合もあります）」と一本化する
- ノックに割り当てるセッショントークンは**必ずサーバーが新規発行**する（`knock.session` で名乗られた値は採らない）。名乗られた値をそのまま採ると、その値を知る第三者が `join.session` の再接続経路（entryToken の検査より前に評価される）を通って、ホストの承認なしに入室できてしまう。`knock.session` は**ブロック判定にのみ**使う
- 承認時に発行したセッショントークンは、入室後の `Player.sessionToken` へそのまま引き継ぐ。これにより、キックされた相手が元のノック用トークンで再ノックすることを防げる
- キック時、その対象に発行済みの未使用 entryToken は即時無効化する。**保留中のノック申請も同時に破棄する**（どちらも sessionToken の突き合わせで削除する）

#### 3.1.2 ランダムマッチ

「いますぐ飲む」からの自動相席。メインペルソナ（企画書 §2）の主要導線。

- 利用者は `joinQueue` で**待機列**に登録する（ゲスト可）。ニックネームは省略可（省略時はマッチ成立時にサーバーが二つ名を付ける）、趣味タグ（最大5個）も一緒に持ち込める。待機中は `leaveQueue` でキャンセル可能。**WS 切断で自動的に列から外れる**
- 待機者には `queueStatus`（`waiting`: 自分を含む待機人数 / `nextCheckAt`: 次の成立判定時刻）を、並んだ直後と待機人数が変わるたびに送る
- サーバーは**30秒周期**（`MATCH_INTERVAL_MS`）で待機列を確認し、**2人以上いれば最大4人ずつ**（`MATCH_GROUP_MIN` = 2 / `MATCH_GROUP_MAX` = 4）のグループに区切ってマッチ成立させる（4人を超える待機は次のグループへ、端数の1人は次の周期へ回す）。切り出したグループのうち接続が切れた人は捨て、残りが2人未満になったら成立させず列の先頭へ戻す
- 成立するとサーバーがマッチ専用ルームを自動生成し、全員へ `matched`（`roomCode`）を送って入室させる（直後に `roomState` が続く）。ホストはグループ先頭の1人（自動）。**マッチ専用ルームは公開一覧に載せず**（`visibility: "private"` を明示設定しているため一覧の条件から外れる。ルーム名を持たないことも二次的な条件として効く）、**合言葉も持たない**（合言葉検索でも引けない。抜けた人の補充もしない）
  - ただし入室方式は `entryMode: "open"` であり、**6桁コード／招待 URL（`/r/{code}`）を知る第三者は入室できる**。卓のコードは参加者全員の画面に表示されるため、「一覧にも合言葉検索にも出ないので**見つからない**」のであって「入れない」わけではない（§11-3 のデモ手順はこの経路で聴衆を招き入れている）。締め切りたい場合は別途ロック機構が必要【未実装】
- マッチ専用ルームの `ownerUserId` は空文字（システム生成）。`ROOMS_PER_ACCOUNT_MAX` の数え上げからも除外される。それ以外の挙動（ゲーム・VC・キック・チャット・bot）は通常ルームと同じ
- 同一接続が同時に複数の待機登録をすることはできない（`DUPLICATE`）。すでにルームに参加している接続も列に並べない（`INVALID_INPUT`）
- 待機列の上限は 100 人（`MATCH_QUEUE_MAX`）。超過時は `RATE_LIMITED` を返して受け付けない
- **【未実装】共通タグの多い組み合わせを優先したグループ化**（§3.11 用途2）。現状は並んだ順に先頭から最大4人ずつ切り出すだけで、タグは成立した卓へ持ち回るのみ

### 3.2 リアルタイム同期基盤

**設計原則（実装より優先される規約）**

1. サーバーが唯一の状態機械。クライアントは表示とイベント送信のみを行い、状態遷移を判断しない
   - ただし**クライアント実行型ゲーム**（`server/games/client.ts`、§3.5.1）はこの原則の対象外。サーバーは `gameEvent` の payload を解釈せず同室へ中継するだけとし、その結果は公式スコア（`ScoreEntry`）に算入しない
2. ルームごとにイベントを直列処理する。**状態遷移関数の内部で await を使用しない**（KVアクセス等は遷移の前後で行う）。`server/rooms.ts` には `async` / `await` が1つも存在せず、直列化はキューを同期的に drain する形で実装している
3. クライアントには各自に見えてよい情報のみ送る（回答の匿名性、クイズ正解、ノック申請者一覧はホストのみ）
   - `PlayerPublic` に `sessionToken` / `userId` は含めない。`Room.passphrase` はスナップショットにも公開一覧にも載せない。匿名 reveal 用の `GameState.revealTokens` はいかなる view にも載せない

**接続管理**

- WebSocket 1本を全用途（ゲーム同期・ゲーム内イベント中継・VC シグナリング・通話の文字起こし・テキストチャット・bot 操作・ノック/キック通知・ランダムマッチ待機列）で共用する。用途ごとのレート枠だけ分ける（§3.8）
- **アプリ層のハートビート（ping/pong）は持たない。** サーバー・クライアントとも周期的な keep-alive を送らず、**切断検知は WebSocket の close / error イベント**（`socket.onclose` / `socket.onerror`。どちらも `manager.disconnect` へ配線している）による
  - ただし `server/main.ts` は `Deno.upgradeWebSocket(req)` を**オプション無し**で呼んでいるため、**ランタイム（Deno）が protocol 層の ping/pong を行う**。`UpgradeWebSocketOptions.idleTimeout` の**既定は 30 秒**で、pong が返らない接続は「不健全」と見なされて閉じられ、`close` / `error` が発火する（出典: Deno 2.8.3 同梱の型宣言 `deno types`）。したがって**半死接続（TCP は生きているが相手が応答しない状態）は概ね 30 秒で検出され**、そこから 60 秒の再接続猶予に入る
  - v1 の割り切りは「検出できないこと」ではなく、**`idleTimeout` を明示せずランタイムの既定値に依存していること**。将来 `idleTimeout: 0`（無効化）を入れると半死接続が検出されなくなる
- 切断後60秒はセッション保持。同一 sessionToken での再接続時にフルスナップショット（`roomState`）を送って復帰する
  - sessionToken は `RoomSnapshot.session` として**本人にのみ**渡り、クライアントは `sessionStorage`（キー `en-session`）へ保存して再接続時に `join.session` として送り返す
  - クライアントの再接続リトライは指数バックオフ（1秒 → 最大30秒）で**最大8回**
- 60秒超過で退室扱い。進行中ゲームは§8の異常系マトリクスに従う
- スナップショットにはチャット履歴の直近 100 件（`CHAT_HISTORY_MAX`、§3.9）を含める。**通話の文字起こし（`voice`）は履歴に積まないため、再接続すると消える**

**タイムアウト値・上限値（実装値）**

| 定数 | 値 | 用途 |
|---|---|---|
| `DISCONNECT_GRACE_MS` | 60,000 ms | 切断 → 退室化までの猶予（§3.2） |
| `KNOCK_TTL_MS` | 60,000 ms | ノック申請の自動拒否（§3.1.1） |
| `ENTRY_TOKEN_TTL_MS` | 60,000 ms | entryToken の失効（§3.1.1） |
| `MATCH_INTERVAL_MS` | 30,000 ms | ランダムマッチ成立判定の周期（§3.1.2） |
| `WS_RATE_WINDOW_MS` | 1,000 ms | WS レート判定窓（一般枠・`rtcSignal` 枠・`gameEvent` 枠で共用、§3.8） |
| `CHAT_RATE_WINDOW_MS` | 10,000 ms | チャットのレート判定窓（窓内 `CHAT_RATE_MAX` = 5件、§3.9） |
| `KNOCK_RATE_WINDOW_MS` | 10,000 ms | 同一相手から同一ルームへのノック間隔（判定キーは **IP**。取れなければ接続ID） |
| `MAX_MESSAGE_BYTES` | 65,536 B（64KB） | WS 1メッセージのサイズ上限。超過は close code 1009 で切断 |

`MAX_MESSAGE_BYTES` のみ `server/main.ts`、他はすべて `server/types.ts` に定義がある。

### 3.3 ゲームエンジン

ゲームの進行基盤は**2層**に分かれる。どちらの基盤で作るかの判断は設計書 [games-unified.md](../design/games-unified.md) を正とする。

1. **エンジン（`server/engine.ts`）** — 下記のフェーズ状態機械を持つ。**宣言的ゲーム（§3.5 の GameDefinition）を進行させる prompt モジュール専用**であり、全ゲーム共通ではない
2. **専用モジュール（`server/games/<id>.ts`）** — 自前のフェーズを持つ（§3.4.2）。エンジンの状態機械は通らない

フェーズ状態機械（**prompt モジュールが進行させる宣言的ゲーム共通**）:

```
lobby → intro → prompt → input → reveal → judge → roundResult → (次ラウンド: prompt へ) → finalResult → lobby
```

- 各フェーズは**タイマーで遷移**する（既定秒数は下記）。加えて **input（接続中の採点対象者が全員提出したとき）** と **judge の scoring=vote（投票可能者が全員投票したとき）** の2つだけは全員完了で即座に次へ進む。判定に使うのは接続中の採点対象者のみ（`activePlayerIds`）なので、**切断猶予中の人の提出は待たない**（中断条件の「在籍する採点対象者」＝切断中を含む `scoredPlayerIds` とは別の集合である点に注意）。他のフェーズはタイマー満了のみ。**ホストはいつでもスキップできる**（`skipPhase`）
- reveal は入力を匿名シャッフル表示（定義の `reveal: "named"` で実名に変更可）。匿名表示には不透明トークンを使い、**ラウンドごとに配り直す**ため同じ人でもラウンドが変われば別の値になる
- judge は scoring 方式に従いサーバーが計算する（採点はこの遷移でのみ行う）
- **フェーズ既定秒数**（input のみゲーム定義の `inputTimeSec`）: intro 8 / prompt 5 / reveal 12 / judge 30 / roundResult 12 / finalResult 20。**vote 以外のゲームの judge は表示のみのため 5 秒**に短縮する
- **中断条件の確定**: ゲーム中断（→lobby）は在籍する採点対象者が2人未満になったとき（キック・退室化）。一時切断（60秒猶予内）では中断しない

**卓としてのフェーズ（`RoomPhase`）**

専用モジュール型ゲーム（§3.4.2）は内訳のフェーズを自前で持ち、表示は S2C `gameView` が担うため、**卓の外からは進行中を表す `"playing"` としか見えない**。クライアント専用ゲーム（§3.4.3）にはフェーズの概念自体が無い。したがって卓のフェーズ語彙は次のとおりとする（正本は `server/types.ts`）。

```ts
type RoomPhase = Phase | "playing";
```

エンジンが扱うのはあくまで `Phase`（上の8フェーズ）であり、`RoomPhase` はルーム層とクライアントの間だけで使う。**§8 の異常系マトリクスの行（lobby / prompt/input / reveal/judge / …）は宣言的ゲームにのみ対応する**。専用モジュール型は「在籍が `minPlayers` を割ったら中断」を各モジュールが自前で実装している。

### 3.4 収録ゲーム

収録ゲームは実装基盤で**3系統**に分かれ、現在**11本**が遊べる。**カタログの正本は系統によって2つに分かれる**:

- **宣言的ゲーム（4本）**: `server/official_games.ts` の `OFFICIAL_GAMES`。ルームは作成時に `availableGames` をこれで固定初期化する
- **専用モジュール型・クライアント専用（7本）**: `server/games/index.ts` の `GAME_MODULES`（現在8エントリ。うち `promptModule` は宣言的ゲームを動かす枠なので、ゲーム本数としては数えない）

卓に出る一覧（`RoomSnapshot.availableGames`）は、`server/rooms.ts` の `availableGameSummaries()` が**この2つを結合**して作る。**「1行足すだけ」で追加できるのは専用モジュール型とクライアント専用の2系統**（`GAME_MODULES` に1行）であり、5本目の公式宣言的ゲームを足す場合は `OFFICIAL_GAMES` に追加する。

なお、この11本はすべて `RoomSnapshot.availableGames` に `official: true` で載る（モジュール型のゲームはリポジトリ入りのコードなので常に公式扱い）。**ユーザーから見れば公式ゲームは11本**である。

#### 3.4.1 宣言的ゲーム（公式4種 / kind: "prompt"）

GameDefinition（§3.5）を prompt モジュールが §3.3 のフェーズ状態機械で進行させる。実装は `server/official_games.ts`。

| ゲーム | id | rounds | input | inputTimeSec | reveal | scoring |
|---|---|---|---|---|---|---|
| 大喜利 | `official-ogiri` | 3 | text | 60 | anonymous | vote |
| 以心伝心 | `official-ishindenshin` | 3 | text | 45 | **named** | match |
| 雑学クイズ | `official-quiz` | 5 | choice（4択） | 20 | anonymous | correct |
| 格付けクイズ | `official-kakuzuke` | 5 | choice（2択） | 20 | anonymous | correct |

- **公式ゲームも自作と同じ GameDefinition 形式で記述し、同一の prompt モジュールで動かす**（エンジンに公式ゲーム専用の分岐を置かない）。公式かどうかの判定はゲーム一覧の表示フラグにしか使わない
- 人数は §3.3 の `MIN_PLAYERS = 2` に従い 2人以上（上限はルーム定員の10人）

#### 3.4.2 専用モジュール型ゲーム（kind: "module"）

**秘密の配布（お題・役職）・独自のフェーズ進行・公式スコアへの加点**が要るゲーム。`server/games/<id>.ts` に GameModule を実装し、表示は `public/room/games/<id>.js` が担う。

- §3.3 のフェーズ状態機械は適用されず、モジュール自身のフェーズを持つ。卓からは `"playing"` に見える（§3.3）
- `init` / `reduce` / `view` はすべて純粋関数とし、`Math.random()` / `Date.now()` を使わず、`init` で受け取った seed と引数の `now` から決定的に進める
- サーバーが状態機械を持つため、**結果は `{ t: "score" }` 効果として宴の公式スコア（`ScoreEntry` / `Player.score`）に加点する**
- 在籍が各モジュールの `minPlayers` を割ったらモジュール自身がゲームを中断する

#### 3.4.3 クライアント専用ゲーム

`public/room/games/<id>.js` だけで完結し、**ゲームごとのサーバー側コードを持たない**ゲーム。「画像ファイルを置いたら普通のブラウザゲームとして動く」ことを担保する経路。ゲーム作者はサーバーのコードを書かないが、**共通の受け皿 `server/games/client.ts`（`clientGame(spec)`）はサーバー側に存在し**、中継のほか在籍名簿の維持（`playerJoined` / `playerLeft` / `playerKicked`）・`minPlayers` 割れでの中断・非在籍者からのイベント拒否・`payloadMaxBytes` / `relayLogMax` によるサイズと件数の制限を担う。

- サーバーは payload を解釈せず、同室へ**中継するだけ**（§3.8 の `rtcSignal` と同じ扱い）。ゲームのルールを一切知らない
- したがって**秘密は持てず、得点はサーバーが関与しない**。自己申告のスコアは改造クライアントで書き換えられるため、§3.2 原則1（サーバーが唯一の状態機械）を曲げないよう、**クライアント専用ゲームの結果は宴の公式スコア（`ScoreEntry`）に算入しない**。ゲーム内での勝敗表示は自由
- 中継ログはゲームごとの `relayLogMax` 件のみ保持し、1件のサイズを `payloadMaxBytes` で制限する。中継ログは view（`events`）に載って同室全員へ配られるため、**途中参加者・再接続者も直近 `relayLogMax` 件（本書収録のゲームでは 12〜24 件）は受け取る。それより前のイベントは復元されない**（＝履歴の完全復元は保証しない）
- 全員で同じ盤面を使いたいゲームは、サーバーが配る `view.seed` から各自が同じ手順で盤面を作る（通信で配らない）

#### 3.4.5 宣言的ゲームの採点仕様

以下は §3.4.1 の宣言的ゲーム（および §3.5 の自作ゲーム）に適用される確定仕様であり、ユニットテストの対象とする。

- **match の正規化規則**: ①前後空白を除去 ②連続空白を1つに圧縮 ③英字は小文字化 ④全角英数字・記号は半角化 ⑤カタカナはひらがな化。**漢字/かなの表記ゆれ（例:「猫」と「ねこ」）は同一視しない**（v1 の割り切り）。内部の適用順は「④→③→⑤→②→①」（全角英字を確実に小文字化するため）。**半角カタカナは変換しない**（「ﾈｺ」と「ネコ」は別扱い。v1 の割り切り）
- **配点の確定値**: vote は1票=1点（自票禁止）。match は「自分以外の一致人数」＝得点、**全員が提出しかつ正規化後1種類になったとき**は各自 +3。correct は正解の基礎点 10 に、正解者の提出が早い順で +5 / +3 / +1（4位以降 +0）
- **回答テキストの上限は 140 文字**（サーバーで検証。超過は INVALID_INPUT）
  - 現状、エンジンの提出検証（`server/engine.ts`）は **UTF-16 コード単位**で数え、ゲーム定義の検証（`server/gamedef.ts`）は**コードポイント単位**（`[...s].length`）で数えており、**数え方が食い違っている**。サロゲートペアを含む絵文字入りの回答は 140 文字未満でも弾かれうる。**コードポイント単位に統一する**ことを確定仕様とし、エンジン側の修正を残作業とする（§12-2）

### 3.5 ゲームスタジオ（自作ゲーム）

> **【未実装】実装状態（2026-08-28 時点）**
> ゲームスタジオは**ユーザーから利用できない**。GameDefinition の型（`server/types.ts`）、バリデーション（`server/gamedef.ts` の `validateGameDefinitionDraft` / `validateGameDefinition`）、Deno KV アクセス層（`createGame` / `updateGame` / `deleteGame` / `getGame` / `listUserGames` / `issueShareCode` / `resolveShareCode`）、共有コード生成は**サーバー側に実装済み**だが、**これらを呼び出す HTTP API・WebSocket ハンドラ・スタジオ画面がまだ無い**。
>
> - `public/studio.html` / `studio.js` は存在しない。UI にスタジオへの導線も無い
> - `server/main.ts` に `/api/games` 系ルートも `/g/{shareCode}` ルートも無い
> - `server/gamedef.ts` から production コードに出ているのは `toSummary` 1本のみ。他の関数の参照はテスト（`server/tests/gamedef_test.ts`）だけ
> - ルームの `availableGames` は**公式ゲームで固定初期化される**のみで、自作定義が入る経路が無い
> - C2S `importGame` は型としては定義済みだが、`server/rooms.ts` が `INVALID_INPUT`（未実装メッセージ）を返す
>
> **残作業は4点**: ①スタジオ画面（`public/studio.html` / `studio.js`）②CRUD・共有コード発行 API（`/api/games` 系）③`/g/{shareCode}` ルート ④`importGame` ハンドラ。
> 以下は**その実装が満たすべき仕様**であり、実装済みの記述ではない。

GameDefinition はコードではなく宣言的データ。実行可能スクリプトは受け付けない。

```ts
type GameDefinition = {
  id: string;              // uuid
  ownerId: string;         // 作成者のユーザーID（サーバーが付与。クライアント指定不可）
  title: string;           // 20文字以内
  description?: string;    // 100文字以内
  rounds: number;          // 1..10
  inputType: "text" | "choice";
  inputTimeSec: number;    // 10..180
  reveal: "anonymous" | "named";
  scoring: "vote" | "match" | "correct";
  prompts: Prompt[];       // 1..50件
};

type Prompt =
  | { kind: "open"; text: string }
  | { kind: "choice"; text: string; options: string[]; answer?: number }; // answer必須は scoring=correct のみ

// クライアントが送る形（id / ownerId はサーバーが付与するため含まない）
type GameDefinitionDraft = Omit<GameDefinition, "id" | "ownerId">;
```

- **作成・編集・共有コード発行はログイン必須**。定義は作成者アカウントに紐づき、スタジオには自分の定義のみ一覧表示。編集・削除は所有者のみ
- **インポート（共有コード/URL からの取込）とルームでの使用はゲスト可**（ホストがルームのゲーム選択に追加する操作を含む）
- バリデーション（**実装済み**: `server/gamedef.ts`）: 文字数/件数上限、scoring と inputType の整合をサーバー側で検証。**整合の確定値**: vote → text / match → text / correct → choice（answer 必須。範囲も検証し、correct 以外での answer 指定は拒否）。**追加上限**: お題本文 120 文字・選択肢 40 文字・選択肢 2〜6 件（重複禁止）・制御文字禁止
- **共有コードの文字集合**（**実装済み**）: 読み間違えやすい I/O/0/1 を除いた英大文字+数字の32文字（`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`。口頭伝達を想定）。長さは 8 桁で、生成には `crypto.getRandomValues` を使う
- 保存: Deno KV。キーは `["game", id]` に定義本体、`["gameShare", shareCode]` → id のマップ、`["userGames", userId]` に所有一覧（**KV アクセス層は実装済み。呼び出し元が無い**）
- **保存上限: 1アカウントにつき 50 定義**（超過時はエラー。古いものの削除を促す）
- 共有: 共有コード入力またはURL（`/g/{shareCode}`）でインポート。ルームのゲーム選択に「コードで追加」
- **安全性の考え方**: GameDefinition は実行不能な宣言的データのみのため、**任意コード実行のリスクは構造的に存在しない**。バリデーションは既知の8フィールドだけを組み立てて返すため、未知フィールド（スクリプト文字列等）が定義に持ち越されることも無い。残るリスクは①表示テキスト経由の XSS（§3.8 の描画規定で対処）と②不適切な文言（通報＋ホスト承認制で対処）の2点であり、公開フィード・検索・ランキングは作らないことで拡散面も抑える

#### 3.5.1 チーム製ゲーム（専用モジュール型 / クライアント専用型）

反射神経・お絵かき等、毎秒動くゲームは §3.5 の宣言的な GameDefinition（vote/match/correct の3方式、text/choice の2入力のみ）では表現できない。これらは**リポジトリに含まれるチーム製コード**として実装する（§3.4.2 / §3.4.3）。設計の詳細は [games-unified.md](../design/games-unified.md) を正とする。

> **旧方針からの変更（重要）**: 本節はかつて「JavaScript ゲームを `<iframe sandbox="allow-scripts">` 内で実行する」と規定し、[game-sandbox.md](../design/game-sandbox.md) を参照していた。**この iframe サンドボックス基盤は games-unified.md v0.2 で廃止され、実装も存在しない。** game-sandbox.md はアーカイブであり（冒頭に「本書の設計を新規に実装してはならない」と明記）、CSP と opaque origin の実測知見を保存する目的でのみ残している。

- **§3.5「実行可能スクリプトは受け付けない」との関係**: この規定は**ユーザー投稿**（スタジオ経由で登録される GameDefinition）を対象としたものであり、引き続き有効。チーム製ゲームはリポジトリに入り、**PR レビュー（人間の承認）を経てのみ追加される**ため、スタジオが「受け付ける」対象ではない。**ユーザーからのゲームコード投稿は今後も作らない**（games-unified.md §0.1）
- **公式スコアへの算入**: 系統によって異なる（§3.4.2 / §3.4.3）
  - **専用モジュール型**: サーバーが状態機械を持ち、得点計算もサーバー側で行うため、**公式スコアに加点する**（`{ t: "score", totals }` 効果）。§3.2 原則1と矛盾しない
  - **クライアント専用型**: サーバーは payload を解釈せず中継するのみで、得点は自己申告となるため、**公式スコアに算入しない**
- **読み込み方式と隔離について（現行方式）**: ビューモジュールは **iframe に入れず、アプリのオリジンで直接 ES モジュールとして動く**。`public/app.js` がカタログ由来のゲームIDだけを使って `import("/room/games/<id>.js")` する（ビルドレスの動的 import。URL 組み立てにユーザー入力を混ぜないことでパス注入を防ぐ）。**postMessage も runner も使わない。CSP は本体と同じものが適用される**
- **したがってコードの隔離は行わない。** ゲームコードは親の DOM・Cookie・localStorage に触れられる。この方式が安全と言えるのは、次の2点を前提にしているからである
  1. **ゲームを追加できるのはチームだけ**であり、コードはリポジトリに入って**人間の PR レビュー（Definition of Done）を通る**。これは `chat.js` / `vc.js` / `corridor.js` といった既存フロントコードと**同じ信頼水準**であって、ゲームだけを特別扱いする理由が無い
  2. **ユーザー投稿にコード実行の経路を作らない**（上記のとおりスタジオは宣言的データのみ）。信頼できない第三者のコードが動く状況そのものを作らない
- **将来ユーザー投稿のコード実行を受け付ける判断が出た場合**は、この信頼モデルが崩れるため、games-unified.md §9.2 のとおり game-sandbox.md（アーカイブ）に立ち返って隔離設計をやり直す。その際は Worker 化＋実行時間監視（無限ループ・メモリ食い潰しへの対処）も併せて設計する
- **表示規約**: ゲームのビューでもユーザー由来テキストは必ず `textContent` で描画する（`innerHTML` 禁止。§3.8 / CLAUDE.md セキュリティ基準）。canvas 描画は制約なし。**音は出さない**（VC の会話にかぶせないため）
- **対応ブラウザ**: 収録ゲームは標準機能のみで書かれており、§7 の対応ブラウザで動く見込みだが、**iOS Safari での実機確認は未実施**。読み込みに失敗した場合はその旨のメッセージを表示する

### 3.6 VC / カメラ / 画面共有（分離モジュール）

- **VC（音声）はコンセプト上の必須要素**（v0.5）。見知らぬ人とのランダムマッチでは「外部通話ツール併用」が成立しないため、旧フォールバック（VC切り）は廃止する
- WebRTC P2P フルメッシュ。シグナリングは既存WebSocketの `rtcSignal` メッセージとして実装（サーバーは payload を解釈せず、同一ルーム在籍・接続中・双方 VC 枠内の相手にのみ中継する。§3.8）
  - **VC に参加できるのは先着 6 人まで（`VC_CAPACITY = 6`）**。ルームの定員 10 人（§3.1 / §7）とは別の枠で、7 人目以降は VC なし（チャット・ゲームには通常どおり参加できる）。メッシュは最大 6 ノード＝1 人あたり最大 5 接続が帯域設計の前提
  - VC 枠に空きが出たら（枠内の誰かの退出）、参加順で自動的に繰り上がる
  - オファー衝突は Perfect Negotiation（MDN のパターン）で解消する。polite 役は playerId の辞書順で決める
- STUN: 公開STUNサーバー（`stun:stun.l.google.com:19302` を常に配布）。TURN: VPS上の coturn（P2P不成立の回線対策）。**TURN の配布経路はコード側で導入済み**:
  - サーバーが `.env`（無ければ環境変数）の `TURN_URL` / `TURN_USER` / `TURN_PASS` / `TURN_SECRET` から iceServers 一覧を組み立てる。`TURN_SECRET` 設定時は coturn の TURN REST API 方式（HMAC-SHA1）の**時限クレデンシャル**を発行する（TTL は `TURN_TTL_SEC`、既定 3600 秒・60〜86400 秒の範囲）。未設定なら `TURN_URL`/`TURN_USER`/`TURN_PASS` が3つ揃ったときのみ長期認証情報を配る
  - 配布は `GET /api/ice`（Origin 検証 + IP レート制限付き）。クライアントは起動時に取得して `RTCPeerConnection` へ注入する。取得失敗時は既定の STUN のみで動作する
  - `.env` に TURN が未設定の環境では STUN のみとなる（coturn 本体のデプロイ状況は環境に依存）
- **品質劣化時は映像を自動停止し音声優先**。送信側統計（`getStats`）を定期サンプリングし、RTT・送出ビットレート・FPS 低下などのしきい値超過が続いたら映像トラックのみを止める（音声は触らない）。判定しきい値・ウォームアップ・自動停止回数上限などの数値は `public/room/vc.js` に集約する（多くは【暫定値】のため仕様書には転記しない）。**回復を検知しても自動では再開せず、「再開できます」の通知のみ。再開は本人の明示操作**
- **カメラは全ルームで初期OFF**。本人の明示操作でのみON（公開ルームで知らない人にいきなり顔が映る事故の防止）。要求解像度は 640×360
- **ミュート**: マイクは各自でミュートでき、ミュート状態は卓の全員に表示される（状態未通知の相手は「声入り」として安全側に表示）
- **発話検知・主役表示**: 話し中の参加者は卓上で表示される（自分・相手とも AnalyserNode による同一経路の音量検知）。任意の参加者の映像を主役枠に拡大でき、端末の全画面表示にも対応する
- キックされた参加者のピア接続はサーバー通知（`playerKicked`）を受けた各クライアントが即時クローズする。キックされた本人側は VC 全体を畳む
- **フォールバック規定（改）**: 切り捨てて良いのは**カメラのみ**。音声が期間内に安定しない場合の最終フォールバックは「チャット中心の運用」（§3.9）とし、その判断はチーム合意で行う。マイク取得に失敗した参加者は VC 不参加のまま入室を続ける

#### 3.6.1 画面共有

VC 参加者は自分の画面（画面全体 / ウィンドウ / タブ）を卓へ共有できる（`getDisplayMedia`）。設計の詳細は [vc-screenshare.md](../design/vc-screenshare.md) を参照。

- **同時に共有できるのは卓で1人**。他の人が共有中は開始できない（選択ダイアログを出す前に断る）。告知の行き違いで2人が同時に始めた場合は **playerId の小さい側を残して**自動収束する
- **送出する映像トラックは常に高々1本**（不変条件）。カメラと画面は排他で、**共有中は自分のカメラを物理的に停止する**（カメラLEDを嘘にしないため）。共有をやめたとき、共有前にカメラがONだった場合のみ取り直して復帰する
- **共有音声は扱わない**（音声トラックは常に0本。共有ストリームに音声が付いてきても捨てる）
- 送出プロファイルは3種。取り込み（`applyConstraints`）と送出（`setParameters` の maxBitrate）の二重制限を掛ける:
  - `text`（既定）: 1280×720 / 10fps / 700kbps（文字用途）
  - `motion`: 1280×720 / 24fps / 1.2Mbps
  - `light`: 640×360 / 5fps / 250kbps
- **TURN リレーを検知したら `light` へ自動降格**する（リレーは上下とも VPS を通るため）。中継が外れたら（品質降格中でなければ）元へ戻す
- 品質劣化時は「① `light` へ降格 → ②（60秒の保持後も劣化が続くなら）共有停止」の**二段構え**とし、終着点は本節の原則どおり音声優先（音声は止めない）
- 受信側には「画面を共有中」の表示と、共有画面を主役枠へ拡大する操作を出す。画面全体（monitor）を共有した場合は「通知やパスワード入力も映る」旨を本人へ警告する（選択自体は妨げない）
- **送信可否は UA ではなく機能検出で決める**。`public/room/vc.js` の `screenShareSupported()` は `navigator.mediaDevices.getDisplayMedia` が関数として存在するかだけを見ており（ブラウザ名の分岐は無い）、無ければ共有ボタンを無効化して理由を表示する。したがって `getDisplayMedia` を持たない環境では**送信できず受信のみ**になり、将来対応したブラウザでは自動的に送信可になる
  - **【要確認】** どのブラウザが非対応かは実装からは導けない。設計書 [vc-screenshare.md](../design/vc-screenshare.md) は iOS Safari / Android Chrome を非対応（受信のみ）としているが、リポジトリ内に一次情報（MDN / WebKit の互換性表）の引用が無い。§7 の必須動作対象（iOS Safari）で送信を対象外とするかは、この裏取りののち確定する

#### 3.6.2 通話の文字起こし（任意・既定OFF）

VC 参加者は、自分のマイクの音声認識結果をテキスト化して卓へ流せる。bot（§3.10）が声を拾うための入力経路であり、字幕表示にもなる。

- ブラウザの **Web Speech API**（`SpeechRecognition`、認識言語 `ja-JP`）を使う。**既定 OFF・本人の明示操作でのみ ON**（カメラと同じ扱い）
- 認識するのは**自分のマイクのみ**。他人の声を勝手に文字起こしはしない。ブラウザによっては音声がブラウザベンダのサーバーへ送られるため、ON にする前にその旨を本人へ表示する（§3.7）
- 確定した認識結果のみを C2S `{ t: "voice", text }` で送る。1件 200 文字以内（チャットと共通の検証）・レート制限は **12件/10秒**（クライアント側は 10件/10秒 で自主的に間引く）。受理は **VC 枠内（先着6人）の参加者からのみ**
- 受信行はチャット欄ではなく**字幕行（最新1〜2行）**に表示し、**チャット履歴（§3.9）には積まない**
- bot（§3.10）は voice も「人間の活動」として扱い、せりは声から川柳を拾う

### 3.7 安全設計（見知らぬ人と会う導線すべて）

見知らぬ人同士を引き合わせるサービスであるため、オープン入室・ランダムマッチを含む全導線で以下を守る。

- キック + ブロックリスト（§3.1）は全ルーム共通。承認制ルームではさらにノックで入口を絞れる
- **カメラは全ルーム初期OFF**（§3.6）。他者に見えるのは**あだ名とプリセット趣味タグのみ**（軽量プロフィール）。自由記述のプロフィール・フレンド/DMは作らない。アカウントのユーザーIDは他者に表示しない
- **退出はワンタップ**: どの画面からも即座にルームを離れられる（引き止めの確認ダイアログを挟まない）
- 通報: ホームとルーム内フッターに外部フォーム（Google Forms）へのリンクを常設。自動処理は作らない。**【未実装】通報リンクはまだどの画面にも置かれていない（外部フォーム URL の確定後に追加する）**
- 対象年齢20歳以上を想定する旨をトップに表記（自己申告。厳密な年齢確認は作らない）。**【未実装】この表記はまだどの画面にもない**
- オープン入室・ランダムマッチの荒らし対策は「即キック + ブロック + 通報 + 自分が抜けて入り直せる手軽さ」で担保する（v1 の割り切り。アカウント単位の永久BANなどは作らない）。ただし構成要素のうち通報は上記のとおり未実装

### 3.8 セキュリティ要件（全画面共通）

- **XSS**: ユーザー由来のテキスト（ニックネーム・ルーム名・ゲーム定義の全文言・回答・チャット的表示のすべて）を DOM に出す際は `textContent` を使用する。`innerHTML` への未サニタイズ代入は禁止。HTML を組み立てる場合は明示的にエスケープする（CLAUDE.md セキュリティ基準に準拠）
- **CSP**: 全静的配信の応答に **HTTP レスポンスヘッダ**として `Content-Security-Policy` を付与する（`server/main.ts` の `SECURITY_HEADERS`。HTML の meta タグは使わない）。実際のディレクティブは次のとおり:

  ```
  default-src 'self'; base-uri 'none'; object-src 'none'; frame-ancestors 'none';
  form-action 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'
  ```

  - `connect-src` は明示せず `default-src 'self'` に従わせる（同一オリジンの WebSocket はこれで許可される）。STUN/TURN（WebRTC のメディア経路）はそもそも CSP の統制対象外であり、CSP では制御しない
  - インラインスタイルのため `style-src 'unsafe-inline'`、data: URI の画像のため `img-src data:` を緩和している
  - あわせて `x-content-type-options: nosniff`・`referrer-policy: no-referrer`・`permissions-policy: display-capture=(self), camera=(self), microphone=(self)`（画面取得・カメラ・マイクを自オリジンに限定）も同時に付与する
- **CSRF**: 状態を変更する HTTP エンドポイントは `Origin` ヘッダを検証する。Cookie は SameSite=Lax
- **レート制限**（IP / アカウント / 接続単位。超過は `error: RATE_LIMITED`）:
  - ログイン試行: IP ごとに 5回/分
  - 登録: IP ごとに 3件/時（数えるのは実際にアカウント作成を試みた回数のみ＝登録成功とユーザーID重複。JSON不正や入力形式不正は数えない）
  - プロフィール保存（`PUT /api/profile`）: IP ごとに 30件/分
  - ノック: **同一 IP** から同一ルームへ 10秒に1回（キーはセッションではなく IP。WS を張り直すと接続単位の制限は無効化されてしまうため。IP が取れないときのみ接続IDに倒す）。1ルームの保留ノックは最大5件（超過分は即時拒否）
  - ルーム作成: 1アカウントにつき同時 3 ルームまで
  - `GET /api/ice`: IP ごとに 60件/分（未ログインでも叩けるため、TURN クレデンシャルの大量収集よけ）
  - WS メッセージ: 1接続あたり 20件/秒 を超えたら切断。また **1メッセージの上限は 64KB**（超過は close 1009）
    - ただし `rtcSignal`（VC シグナリング、§3.6）は別枠でカウントし、1接続あたり 100件/秒 とする。**超過分は当該メッセージを破棄するだけで切断しない**（通知は判定窓につき最大1回）。さらに 500件/秒 を超えた場合は乱用とみなして切断する
    - 理由: フルメッシュの trickle ICE が短時間に集中するため、20件/秒 では正当な VC 利用者を切断してしまう。また WS は全用途を1本で共用する（§3.2）ため、シグナリングの超過で切断するとチャットもゲーム進行も巻き添えで落ちる。VC は §3.6 のとおりフォールバックできるので破棄で足りる
    - `gameEvent`（クライアント専用ゲームの中継、§3.4.3）も別枠でカウントし、ソフト上限 30件/秒（超過分は破棄）・ハード上限 150件/秒（超過で切断）とする。1件の payload 上限は 4KB
- **rtcSignal の中継条件**: サーバーは `to` が送信者と同一ルームの接続中メンバーで、**かつ送信者・宛先の双方が VC 枠（先着6人、§3.6）内である**場合のみ中継する。それ以外は破棄。payload の直列化サイズは 16KB 以内（超過は `INVALID_INPUT`。自分宛ての送信も拒否）
- **KV 上限**: ゲーム定義は 1アカウント 50 件（§3.5）。1定義の直列化サイズ上限 64KB。**【未実装】この上限を外部に晒すスタジオ CRUD（API・画面）は未実装で、バリデーション・KV 永続化層（`server/gamedef.ts`）のみ完成している**
- **デバッグ機能**: 内部診断用のデバッグ API・画面（`server/debug.ts` / `public/debug.html`）は環境変数 `EN_DEBUG_TOKEN` の設定時のみ有効。無効時・トークン不一致時は API・静的ファイルとも 404 を返して存在自体を伏せる。トークン比較はタイミング安全で、応答中の機微キー（password/token/cookie 等）は自動 redact する
- 秘密情報（TURN 認証情報等）は `.env` のみ。クライアント配布物に埋め込まない

### 3.9 テキストチャット

VC を使わない/使えない参加者の会話手段であり、bot（§3.10）の発話面でもある。

- ルーム内の全員に届くテキストチャット1本のみ（個別DM・スレッドは作らない）
- 1件 **200 文字以内**（コードポイント単位）。制御文字（改行含む）禁止。前後の空白は落とす。描画は `textContent`（§3.8）
- レート制限: 1参加者 **5件/10秒**（超過は RATE_LIMITED）
- 履歴はルームのメモリ上に**直近 100 件**のみ保持し、スナップショット（再接続・途中入室）に含める。永続化しない
  - bot の発話（§3.10）も同じ 100 件の枠に含める。VC の文字起こし（§3.6.2）は履歴に含めない
- 発言者の表示はニックネーム。bot の発言には bot であることが分かる表示を付ける
- **進行中のゲームがチャットを回答として受け取ることがある**。正解に該当する発言はゲームモジュールの判断で卓に表示しない（suppressChat: 履歴にも積まず配信もしない。当てゲームの正解が他の参加者に見えないようにするため）
- VC の文字起こしは専用の `voice` チャネルで流れ、チャットとはレート制限・表示・履歴の扱いが異なる（§3.6.2）

### 3.10 場回し bot（ルールベース・4体構成）

ルームの沈黙を防ぎ、初対面の場を温めるファシリテーター。**LLM 等の外部 AI API は使用しない。** 発話はすべてサーバー内蔵のテンプレート（運営が用意した定型文・話題カード）から選ぶ。川柳判定にローカル形態素解析（kuromoji、同梱辞書）を使うが、外部 API 呼び出しはしない。

- ルームには**役割の違う bot が4体**常駐する:
  - **しゅんぴ（命名）**: あだ名未入力の入室者に趣味タグから連想した二つ名を付け、由来を明かす
  - **せり（川柳）**: 発言・声から 5-7-5 を拾って一句として取り上げる
  - **ぐっちー（場を温める）**: 挨拶・話題カード・結果への相槌
  - **なべ（進行）**: ゲーム提案・終了アンケート・締め
- **ホストが1体ずつ ON/OFF を切り替えられる**（既定は全 ON。ランダムマッチ生成ルームも全 ON）
- bot は参加者数にカウントしない。ゲームの採点対象・VC 枠にも入らない。**チャット（§3.9）でのみ発話する。音声合成（speechSynthesis）は使わない**（この方針は VC の文字起こし対応後も維持。文字起こしは bot への**入力**であり、bot の音声出力は作らない）
- 沈黙は「**卓で最後に何かが起きた時刻**」（`lastActivityAt`）から数える。数えるのはチャット・ゲーム操作・**VC の文字起こし（§3.6.2）** に加えて、**bot 自身の発話も含む**（話題カード・ゲーム提案・締め等を出すと `lastActivityAt` が進み、次の沈黙判定までまた 30 秒待つ）。人間の活動だけを見るのは、ゲーム再提案の可否判定（`lastHumanAt`）に限る
- **発話頻度の上限は bot ごとに独立**（うるささ防止）:
  - ぐっちー: 10 分あたり最大 5 発話
  - なべ: 10 分あたり最大 2 発話（ただしアンケートの締め・続行宣言は枠を見ずに必ず出す）
  - しゅんぴ: 枠なし（入室1回につき1発話が自然な上限）
  - せり: クールダウン制 — 同一人のチャット句は 15 秒間隔、声の句は 90 秒間隔、ルーム全体で 1 分に最大 10 発話、直近 5 句と重複する句は無視
- 話題カード・定型文はサーバー内のデータファイル（`server/bot_templates.ts`）で管理し、運営（チーム）だけが追加できる（ユーザー投稿は受け付けない）
- **川柳判定（せり）**: 5-7-5 のモーラ検出。チャットは各句 ±1 の字余り・字足らずも拾い、声（文字起こし）はぴったり 5-7-5 のみ。判定はローカル形態素解析 **kuromoji を既定で使用**し、`EN_SENRYU_KUROMOJI=0` で「かなのみ」に縮退できる（縮退時は漢字混じりの句と字余りを拾えない。メモリ影響は §6 参照）
- **終了アンケート（なべ）**: 話題カード・ゲーム提案を出し切ってなお沈黙が続くとき、お開きの是非を問う投票を開始する。条件はルーム開始から 45 分以上・1ルーム最大 2 回・前回から 60 分。集計 60 秒（全員投票または過半数確定で即締め）。過半数賛成なら締めの一言、届かなければ続行宣言。退室者の票は無効化し、一時切断（§8）では票を保持する。**合意が取れても部屋は自動で閉じない（解散はホストの判断）**

### 3.11 趣味タグ（プリセット選択制）

VRChat のタグのように「人となりが少し見える」ための興味関心タグ。**自由入力は受け付けず、運営が用意したプリセット一覧から選ぶ**（不適切文言の混入を構造的に防ぐ。追加はチームがサーバー内のデータファイル `server/hobby_tags.ts` を更新する。**プリセットの正本は同ファイル**）。

- プリセット（全20種）: ゲーム / アニメ / 漫画 / 音楽 / 映画 / スポーツ / 料理 / 旅行 / お酒 / 推し活 / プログラミング / ペット / 読書 / キャンプ / ファッション / 写真 / 筋トレ / カフェ巡り / ボードゲーム / ガーデニング
- **参加者タグ**: 入室・マッチ待機時に**最大5個**選択（ゲスト可。上限の正本は `HOBBY_TAGS_MAX = 5`）。ログイン済みならアカウントに保存され次回自動復元（§3.0）
- 用途:
  1. **参加者表示**: ルーム内の参加者一覧で名前の横に表示（初対面の話題のきっかけ）
     - **あだ名の連想元**: あだ名を省略して入室した人には、あだ名 bot が本人のタグから連想した二つ名を付ける（例: 読書 →「よふかしフクロウ」）。命名の発話で由来のタグも明かし、あだ名そのものを名札兼・話題のフックにする。タグ未選択の人は従来どおり汎用の語彙から付ける
  2. **ランダムマッチの優先条件**: マッチング周期内で共通タグが多い組み合わせを優先してグループ化する。ただし**完全一致は待たない**（成立の速さ優先。タグゼロ一致でも人数が揃えば成立させる）。**【未実装】現状は並んだ順のまま成立させる（§4.3 の実装状況メモ参照）**
  3. **公開ルームのタグ**: 趣味タグとは**別の専用プリセット（`server/room_tags.ts`、全12種**: 初心者歓迎 / ゆるく雑談 / がっつり飲む / 軽く一杯 / 顔出し必須 / 顔出し任意 / 音声のみ / ゲームしながら / 作業しながら / 無言OK / 初参加歓迎 / 深夜まで**）から、作成時にルームへ最大5個付与**できる（`ROOM_TAGS_MAX = 5`。作成後もオーナーは `PATCH /api/rooms/{code}` で変更可）。公開一覧にタグを表示する。一覧のタグ絞り込み【未実装】
  4. **bot の話題振り**: 場回し bot は参加者に共通タグがあれば、それに対応する話題カードを優先して使う（例: 共通タグ「ゲーム」→「最近遊んで良かったゲームは？」）
- タグはサーバーが ID で管理し、クライアントは ID→表示名の対応表を起動時に取得する（趣味タグは `GET /api/tags`、部屋タグは `GET /api/room-tags`。表示テキストはサーバー由来のみ＝XSS 面の入力経路にしない）

## 4. メッセージプロトコル

TypeScript の discriminated union で先に固定し、実装はこの型に従う。**型定義の変更はチーム合意を必須とする。**

### 4.0 HTTP エンドポイント

| メソッド/パス | 認証 | 内容 |
|---|---|---|
| `POST /api/auth/register` | 不要 | `{ userId, password }` → 登録+ログイン。Cookie 発行。ID重複は409。レート制限: IPごと3件/時（429） |
| `POST /api/auth/login` | 不要 | `{ userId, password }` → Cookie 発行。失敗は401（文言統一）。レート制限: IPごと5回/分（429） |
| `POST /api/auth/logout` | 不要 | セッション破棄（KV削除+Cookie削除）。セッションが無くても 200 `{ ok: true }` を返す |
| `GET /api/me` | 任意 | ログイン状態の確認（`{ userId }`。軽量プロフィール保存済みなら `nickname` / `tags` も含む。未ログインは401） |
| `GET /api/tags` | 不要 | プリセット趣味タグ一覧（§3.11）。`{ tags: { id, label }[] }` |
| `PUT /api/profile` | 要 | 軽量プロフィール（あだ名・趣味タグ）の保存（§3.0 / §3.11）。`{ nickname, tags }` → 保存後の正本値を返す。同時更新は409 |
| `GET /api/rooms` | 不要 | 稼働中公開ルームの一覧（10秒ポーリング用）。応答は配列ではなく **`{ rooms: [...] }`** のオブジェクト |
| `GET /api/room-tags` | 不要 | プリセット部屋タグ一覧（§3.11 用途3）。`{ tags: { id, label }[] }`（12種） |
| `PATCH /api/rooms/{code}` | 要（卓のオーナーのみ） | 卓の説明文（100文字以内）とタグ（プリセットから最大5個）の更新。`{ description, tags }` → 保存後の正本値。ルーム不在404・オーナー以外403 |
| `GET /api/ice` | 不要（Origin 検証+IPごとのレート制限） | WebRTC の ICE サーバー設定（§3.6）。ゲストの VC を通すためログインは要求しない。TURN 資格情報は `TURN_SECRET` 設定時に時限化 |
| `GET /api/debug/events` / `GET /api/debug/summary` / `POST /api/debug/reset-limits` | `EN_DEBUG_TOKEN` | 開発用デバッグAPI。トークン未設定・不一致時は常に404（存在を伏せる）。本番仕様外 |
| スタジオ CRUD (`/api/games` 系) | 要 | 定義の作成/更新/削除/一覧。**【未実装】HTTP への配線なし（`server/gamedef.ts` に KV CRUD 関数のみ存在。`main.ts` に TODO 明記）。詳細は設計書で確定** |

- **同一 Origin 検証（不一致は403。§3.8 の CSRF 対策の具体化）を通すのは、状態を変える `/api/*` と `/api/ice`** に限る。内訳は次のとおり:
  - **通す**: auth 配下（`/api/auth/*`）・`GET /api/me`・`GET /api/tags`・`PUT /api/profile`（`main.ts` の `/api/` 総取り分岐）／`PATCH /api/rooms/{code}`／`GET /api/ice`／`POST /api/debug/reset-limits`
  - **通さない**: `GET /api/rooms`・`GET /api/room-tags`（Origin 検証より前で応答する）／`GET /api/debug/events`・`GET /api/debug/summary`（`EN_DEBUG_TOKEN` の一致のみで判定。不一致・未設定は404）
  - 「通さない」側を許容できるのは、いずれも**副作用のない GET** だからである。**状態を変えるエンドポイントを足すときは必ず検証側（`/api/` 総取り分岐の内側、または個別に `isAllowedOrigin`）に入れること**
- 認証系（auth 配下・`/api/me`・`/api/profile` 等）は KV 未設定の構成では 501「auth not configured」を返す。
- WS は接続後のリアルタイム用途に限定する。

### 4.2 ErrorCode（初版）

```ts
type ErrorCode =
  | "AUTH_REQUIRED"    // 作成系を未ログインで実行
  | "ROOM_NOT_FOUND"   // コード不正・削除済み
  | "ROOM_FULL"        // 定員超過（join / approveKnock）
  | "NOT_HOST"         // host only メッセージを非ホストが送信
  | "INVALID_TOKEN"    // entryToken 不正・期限切れ・使用済み
  | "BLOCKED"          // キック済みセッションの再入室/再ノック
  | "RATE_LIMITED"     // §3.8 のレート制限超過
  | "PHASE_MISMATCH"   // 現フェーズで受理できないメッセージ（期限後 submit 等）
  | "INVALID_INPUT"    // バリデーション不正（文字数超過等）
  | "DUPLICATE";       // 冪等処理で弾いた二重送信
```

この10件は `server/types.ts` の `ErrorCode` と**完全に一致**しており、10件とも実装で実際に投げられている（仕様書に無いコードは1つも使われていない）。実装での用法が上のコメントより広いものについて補足する。

- `AUTH_REQUIRED` … 作成系を未ログインで実行、**および所有者でないゲーム定義への操作**（`FORBIDDEN` の流用、§4.3）
- `ROOM_NOT_FOUND` … コード不正・削除済み、**およびゲーム定義／共有コードが見つからない**（`NOT_FOUND` の流用、§4.3）。合言葉が違う場合もこれを返す（卓の有無と区別しない）
- `INVALID_TOKEN` … entryToken が無い／不明／使用済み／期限切れ、**またはノック時のあだ名と一致しない**
- `RATE_LIMITED` … §3.8 のレート制限超過、**および同時保有ルーム数の上限（3）超過・ランダムマッチ待機列の上限（100）超過・1ルームの保留ノック上限（5）超過**
- `DUPLICATE` … 冪等処理で弾いた二重送信、**および一意制約の衝突**（合言葉の重複・同一接続からの重複ノック・重複した待機登録・Deno KV の書き込み競合）
- `INVALID_INPUT` … バリデーション不正のほか、**未実装メッセージ（`importGame`）への応答**にも使う

### 4.3 型の正本（確定済み）

**プロトコル・データモデルの全型は `server/types.ts` を正本として確定済み。** 本書 §4.1 は全数の一覧であり、フィールドレベルで差異があれば `server/types.ts` が優先する。**以後の型変更はチーム合意必須**（本節冒頭の規約に従う）。

主要な型:

- 進行: `Phase` / `RoomPhase` / `PhaseView`（`PlayingPhaseView` を含む）/ `GameState` / `ActiveGame` / `ScoreEntry` / `GameSummary`
- ルーム: `Room` / `RoomVisibility` / `RoomEntryMode` / `RoomSnapshot` / `PublicRoomSummary` / `PlayerPublic`
- 入室: `Knock` / `KnockPublic` / `PendingEntry`
- チャット・bot: `ChatMessage` / `VoiceLine` / `BotId` / `BotSwitches` / `BotKind` / `BotCard` / `BotPollPublic`
- プロトコル: `C2S` / `S2C` / `ErrorCode`

確定にあたっての主な設計点:

- `PhaseView` は `phase` を判別子とする union とし、**フェーズごとに「その時点で見えてよい情報だけ」を型レベルで保証**する（input 中は他人の回答を送らず件数のみ、クイズの正解は reveal で初めて開示、投票の内訳は送らず投票済み人数のみ）
- 専用モジュール型ゲーム用に `PlayingPhaseView`（`phase: "playing"; gameId: string`）を追加した。表示データ本体は S2C `gameView` / `RoomSnapshot.game` で別に配る（`docs/design/games-unified.md` §3.2）
- `RoomSnapshot` に **`session?: string`（本人にのみ入るサーバー発行の再接続トークン）を追加**。§3.2 の「同一 sessionToken での再接続」をクライアントへ受け渡すために必須だったため（v0.3 の型には経路が無かった）。型は任意だが、実装は本人向けスナップショットに常に入れる
- `RoomSnapshot.serverTime` でクライアントの時計ずれを補正する
- ゲーム定義 CRUD の「対象が無い」「所有者でない」エラーは v1 では `ROOM_NOT_FOUND` / `AUTH_REQUIRED` を流用している。専用コード（`NOT_FOUND` / `FORBIDDEN` 等）の追加はチーム合意のうえ将来検討

**v0.5 で追加した型（すべて実装済み。正本は `server/types.ts`）:**

- C2S: `joinQueue` / `leaveQueue`（ランダムマッチ §3.1.2）、`chat`（§3.9）、`setBot` / `endPollVote`（bot、§3.10）、`voice`（通話の文字起こし、`docs/design/bot-voice.md`）、`gameEvent`（`docs/design/games-unified.md` §2.2）
- S2C: `queueStatus` / `matched`（マッチ成立 → 自動入室）、`chat`（`ChatMessage`。bot 発言は `bot` / `botId` / `botKind` / `card` で区別）、`voice`（`VoiceLine`）、`botState` / `botPollClosed`（§3.10）、`gameView`（モジュール型ゲームの表示データ）
- `Room` への追加: `entryMode`（`open` / `knock`）、`passphrase`（**クライアントへは絶対に送らない**。スナップショット・公開一覧のいずれにも載せない）、`description` / `tags`
- `S2C phase.phase` の型を `Phase` から `RoomPhase`（= `Phase | "playing"`）へ拡張
- 趣味タグ（§3.11）: `PlayerPublic.tags`、`join` / `joinQueue` / `createRoom` の `tags`、公開ルーム一覧のルームタグ、`GET /api/tags`（§4.0）
- あだ名保存（§3.0）: `PUT /api/profile`、`GET /api/me` 応答へのあだ名・タグ反映（§4.0）

**残る未実装項目:**

- **【未実装】ランダムマッチのタグ優先マッチ**（§3.11 用途2）。共通タグの多い組み合わせを優先してグループ化する処理は無く、いまは並んだ順のまま成立させる。趣味タグの用途1（参加者表示）・用途3（ルームタグ）・用途4（bot の話題振り）は実装済み
- **【未実装】ルームの24時間自動削除**（§3.1）。`Room.lastActiveAt` は型・実装ともに存在するが、それを見て掃除する処理が無い
- **【未実装】C2S `importGame`**（§3.5）。型は `types.ts` にあるが、ハンドラは `INVALID_INPUT`（未実装メッセージ）を返すだけ

## 5. データモデル

型の正本は `server/types.ts`（本節はその写し。変更はチーム合意必須）。

```ts
type User = {
  userId: string;          // 半角英数 4..20、一意
  passwordHash: string;    // PBKDF2-HMAC-SHA256 600,000回（Base64）
  salt: string;            // ユーザーごとのランダム salt（Base64、16バイト）
  createdAt: number;
  nickname?: string;       // 軽量プロフィールのあだ名。未保存なら undefined（§3.0）
  tags?: string[];         // 軽量プロフィールの趣味タグID配列。最大5個・未保存なら undefined（§3.11）
};

type AuthSession = {
  userId: string;
  expiresAt: number;       // 発行から30日
};

type Room = {
  code: string;                      // 6桁の参加コード
  visibility: "public" | "private";  // 公開 / 招待制。作成後は変更不可
  entryMode: "open" | "knock";       // 公開ルームの入室方式（§3.1）。合言葉ルームでは常に open 相当
  roomName?: string;                 // publicのみ必須（20文字以内）
  passphrase?: string;               // 合言葉ルームのみ（4〜20文字）。クライアントへは絶対に送らない
  description?: string;              // 卓の説明文（100文字以内・任意）
  tags?: RoomTagId[];                // プリセット部屋タグ（最大5個・任意）
  ownerUserId: string;               // 作成者のアカウントID（hostId=playerId とは別物）
  hostId: string;                    // 現在のホストの playerId
  players: Map<string, Player>;      // メモリ上。KVには置かない
  pendingKnocks: Map<string, Knock>; // publicのみ
  pendingEntries: Map<string, PendingEntry>; // entryToken → 承認情報（60秒TTL・1回限り）
  blockedSessions: Set<string>;      // キック済みsessionToken
  availableGames: Map<string, GameDefinition>; // ルームで選択できるゲーム定義（gameId → 定義）
  selectedGameId: string | null;     // 選択中のゲームID
  game: ActiveGame | null;           // 進行中のゲーム。未開始は null
  chatHistory: ChatMessage[];        // 直近 CHAT_HISTORY_MAX 件のみ・古い順（§3.9）
  createdAt: number;
  lastActiveAt: number;              // 最終アクティビティ時刻（24時間での自動削除は【未実装】。§3.1）
};

// 進行中のゲーム1本（docs/design/games-unified.md §2.1）。
// かつての GameState に代わる型。state の中身はモジュールごとに異なるため
// ルーム層は unknown のまま持ち運び、解釈は moduleId で引いたモジュールに任せる
type ActiveGame = {
  moduleId: string;   // カタログ上のモジュールID（server/games/index.ts の正本）
  state: unknown;     // モジュールが持つ状態。ルーム層は中身を解釈しない
  running: boolean;   // 進行中か。終了後も view 配信のため state は捨てない
};

type Player = {
  id: string; nickname: string;      // nickname は 20文字以内
  connected: boolean; disconnectedAt?: number;
  sessionToken: string;
  score: number;
  userId?: string;                   // ログイン済みの場合のアカウントID（他者には公開しない）
  tags?: HobbyTagId[];               // 趣味タグ（§3.11、最大5個）。入室時に持ち込む。未選択なら undefined
};
```

- ルーム状態はプロセスメモリのみ（KV不使用）。**単一プロセスデプロイが前提**
- Deno KV に置くのは以下の**5つの名前空間のみ**（KV を触るコードは `auth.ts` と `gamedef.ts` だけ）。ただし**実際に書き込まれるのは現状 2 つだけ**である:
  - **稼働中に読み書きされる（`server/auth.ts`）**
    - `user:{userId}` → User
    - `authSession:{token}` → AuthSession（`{ userId, expiresAt }`。expireIn 付き）
  - **【未実装】KV アクセス層のみ実装済みで、production からの呼び出しが無いため現状データは入らない（`server/gamedef.ts`。§3.5 のとおりスタジオが未着手のため。呼び出し元はテストのみ）**
    - `game:{id}` → GameDefinition 本体
    - `gameShare:{shareCode}` → gameId（共有コード→id のマップ）
    - `userGames:{userId}` → gameId[]（所有ゲームID一覧。1アカウント50件上限の判定に使う）

## 6. デプロイ

- **想定環境: Xserver VPS 4GB プラン（vCPU 4コア / メモリ 4GB / NVMe SSD 150GB）**。本仕様の規模（同時20ルーム・約200接続 + coturn）に対し十分な余裕がある。この環境で稼働中（`en` / `caddy` / `coturn` の3サービス。公開 URL は sslip.io の TLS 付きドメイン）
- **回線は 100Mbps（全プラン共通・1契約あたり）、通信量は無制限**。メモリ/CPU と違い回線は上位プランでも増えないため、映像本数を増やす拡張（SFU・画面共有の同時本数）はこの帯域を前提に設計する
- VPS上で `deno run` 単一プロセス + **Caddy**（採用済み）でTLS終端（WebSocketプロキシ設定必須）。coturn 用の UDP ポートはパケットフィルターで開放する。アプリは 127.0.0.1 にバインドし、リバースプロキシ経由でのみ公開する
- Deno Deploy利用時は isolate 間でメモリ非共有のため BroadcastChannel/KV 同期の改修が必要。v1では採用しない
- **環境変数**: `.env` で管理し、リポジトリには `.env.example` のみ置く。実際に参照する変数は次の10種:

  | 変数 | 既定値 | 用途 |
  |---|---|---|
  | `TURN_URL` | なし | coturn の URL（例 `turn:example.com:3478`）。TURN_USER / TURN_PASS と3つ揃うと `/api/ice` が TURN を配る |
  | `TURN_USER` | なし | TURN の長期認証ユーザー名 |
  | `TURN_PASS` | なし | TURN の長期認証パスワード |
  | `TURN_SECRET` | なし | 設定すると TURN REST API 方式の**時限クレデンシャル**を発行（固定値は配らない。推奨） |
  | `TURN_TTL_SEC` | 3600 | 時限クレデンシャルの有効期間（秒）。60〜86400 の整数のみ |
  | `KV_PATH` | なし（Deno 既定位置） | Deno KV の保存先。**本番は `/var/lib/en/kv.sqlite3` を必須設定とする**（下記注意） |
  | `EN_SENRYU_KUROMOJI` | 有効 | 川柳判定の kuromoji。`0`/`false`/`off`/`no` で かなのみに倒す |
  | `EN_TRUSTED_PROXY_HOPS` | 1 | 信頼するリバースプロキシの段数（X-Forwarded-For から実クライアントIPを採る位置。0〜16） |
  | `PORT` | 8000 | リッスンポート（環境変数のみ。`.env.example` 未記載） |
  | `EN_DEBUG_TOKEN` | なし（無効） | デバッグ API・画面の有効化トークン（§3.8。環境変数のみ。`.env.example` 未記載） |

- **KV_PATH に関する注意（データ消失リスクの申し送り）**: `KV_PATH` 未設定時、KV は Deno の既定位置（`~/.cache/deno/` 配下）に置かれる。ここは**キャッシュ扱いのディレクトリ**であり、deno のキャッシュ削除や OS の掃除でアカウント・認証セッション・ゲーム定義・共有コードが**消失しうる**。`.env.example` は本番推奨値 `/var/lib/en/kv.sqlite3` を明記しており、`deno task start:prod` も `--allow-write=/var/lib/en` を渡しているが、**現在の本番 VPS の `.env` には `KV_PATH` が未設定のまま稼働している**（設定するつもりで漏れている可能性が高い。既存 KV ファイルの移行を含めた設定作業を最優先で行うこと）
- **川柳判定（§3.10 せり）の形態素解析辞書（kuromoji）は、Deno プロセスに常駐して +220〜330MB を占める**（実測 Deno 2.9 / Windows・5回。RSS 57MB → 277MB または 384MB の2値に振れる。初期化 約390ms、辞書ファイル 17MB）。ルーム数には比例せず、最初の発言時にプロセスで1回だけ読み込む。**サーバープロセスの常駐分として 400MB を見込む**（4GB プランの約 10%。同時20ルーム・約200接続 + coturn を載せても余裕は残る）。倒すと せり が漢字混じりの句を拾えず VC の文字起こし（§3.6.2）由来の句が実質検出されなくなるため、**既定は有効**とする。**この項目はチームの ack を要する（上の「十分な余裕がある」の前提が変わるため）**。メモリが問題になったときは `EN_SENRYU_KUROMOJI=0` で かなのみに倒せる（再デプロイ不要）

**【既知の不具合】ノックの委譲後ホストへの引継ぎ**: 保留ノックはルームに紐づいて委譲後も残り、新ホストは承認操作を実行できる。しかし**委譲時に保留一覧は再送されない**（`server/rooms.ts` は `hostChanged` のみを送出し、`pendingKnocks` を運ぶ唯一の経路である `roomState` を送り直さない。`public/app.js` の `hostChanged` 処理も `hostId` / `youAreHost` を書き換えて再描画するだけで `roomState` を要求しない）。したがって**委譲前から在室していた新ホストの画面には、次の新規ノック・承認・拒否・失効・再接続で `roomState` が飛ぶまで既存の保留ノックが表示されない**。実機確認は未了だが、挙動はコード上で確定している。

共通規定:

- 進行中に2人未満になったゲームは中断し lobby へ
- 同一イベントの二重送信（連打）はサーバー側で冪等処理
- ホスト委譲後も blockedSessions は維持する
- **サーバー再起動（デプロイ・クラッシュ含む）で全ルームは消滅する**（ルーム状態はメモリのみのため）。アカウントとゲーム定義は KV 上に残る。v1 の割り切りとして許容し、**発表デモ・運用中の再起動は行わない**運用ルールとする

## 11. 発表デモ手順（骨子）

7. 締め: 「**会いたい人がいなくても飲み会が始まる**」（競合比較は企画書 §4）

## 12. チーム合意が必要な項目（v0.6 時点）

v0.6 は「実装との同期」を目的とした改版であり、**仕様と実装が食い違っていた箇所は原則として実装側の値を記載した**。ただし以下の3件は「実装が正しい」とチームが合意したわけではなく、**どちらを正とするかが未決**である。合意の結果によっては仕様書の書き換え、または実装の修正が必要になる。
