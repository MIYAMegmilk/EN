# VC（音声・カメラ）手動テスト手順書

- 対象: `public/room/vc.js` + `server/rooms.ts` の rtcSignal 中継
- 前提: 詳細仕様書 [overall.md](../spec/overall.md) §3.6 / §3.8 / §8
- 自動テストで担保できるのはサーバーの中継条件のみ（`server/tests/rooms_test.ts`）。
  WebRTC 本体はブラウザ API のためモックが困難で、本書の手動確認で担保する。

## 0. 準備

```powershell
deno task dev
```

- ブラウザで `http://localhost:8000/` を2窓（別ウィンドウ推奨。タブでも可）開く。
- **`localhost` は Secure Context として扱われるため `getUserMedia` が使える。**
  他端末から IP 直打ち（`http://192.168.x.x:8000/`）でアクセスすると
  Secure Context でないためマイクを取得できない。実機確認は HTTPS 経由で行うこと。
- マイク・カメラの許可ダイアログが出たら「許可」を選ぶ。
- **同一 PC の2窓ではハウリングする。** 片方をミュートするか、両方にイヤホンを使う。
  音の疎通は「片方だけミュート解除して声を出し、もう片方で聞こえるか」で確認する。
- **同一 PC ではカメラを2窓同時に使えない**（Windows のカメラは一度に1プロセス占有。
  マイクは共有可）。後から ON した側が `NotReadableError` / `AbortError` で失敗する。
  §3 のカメラ確認は「片方ずつ交互に ON」で行い、双方同時 ON の検証は
  物理カメラ2台（スマホ実機。HTTPS 必須）が使えるようになってから行う。

## 1. 音声の疎通（最重要）

| # | 手順 | 期待結果 |
|---|---|---|
| 1-1 | 窓Aでニックネームを入れて「招待制ルームを作成」 | ルーム画面と6桁コードが表示される |
| 1-2 | 窓Bでニックネームと同じコードを入れて「参加」 | 両方の参加者一覧に2人表示される |
| 1-3 | 窓Aで「VCに参加」 | 状態表示が「参加中」になる。マイク許可を求められる |
| 1-4 | 窓Bで「VCに参加」 | 双方の状態表示に相手の名前と接続状態が出る |
| 1-5 | 数秒待つ | **双方の状態表示が `<相手の名前>: connected` になる**（`connecting` → `connected`） |
| 1-6 | 窓Bをミュートし、窓Aで声を出す | 窓B側で声が聞こえる（イヤホン推奨） |
| 1-7 | 通信ログを見る | `rtcSignal` が双方向に流れている（`desc` → `ice` の順） |

`connected` にならない場合の確認点:

- ブラウザの DevTools コンソールに `VC ...failed` のログが出ていないか
- `chrome://webrtc-internals`（Chrome）で ICE candidate が交換されているか
- 同一 LAN 内であれば STUN 無しでも成立するため、`stun:stun.l.google.com:19302`
  への到達性は必須ではない。NAT 越え（別回線）の確認は TURN 導入後に行う

## 2. ミュート

| # | 手順 | 期待結果 |
|---|---|---|
| 2-1 | 窓Aで「ミュート」 | ボタンが「ミュート解除」に変わる |
| 2-2 | 窓Aで声を出す | 窓Bで聞こえない。接続状態は `connected` のまま（切断しない） |
| 2-3 | 窓Aで「ミュート解除」 | 再び聞こえる |

## 3. カメラ ON / OFF（§3.6: 初期 OFF）

| # | 手順 | 期待結果 |
|---|---|---|
| 3-1 | VC 参加直後の表示を見る | **映像は出ていない**（初期 OFF。本人操作でのみ ON） |
| 3-2 | 窓Aで「カメラON」 | 窓Aに自分のプレビュー（ミュート）、窓Aに相手の枠、**窓Bに窓Aの映像**が出る |
| 3-3 | 窓Bでも「カメラON」 | 双方向で映像が出る（再ネゴシエーションが走る） |
| 3-4 | 窓Aで「カメラOFF」 | 窓Aのプレビューが消え、窓B側の窓A映像が消える。**音声は途切れない** |
| 3-5 | 3-2 → 3-4 を数回繰り返す | 毎回 ON/OFF できる（映像要素が二重に増えない） |

## 4. 切断・再接続（§8 VC 行）

| # | 手順 | 期待結果 |
|---|---|---|
| 4-1 | 窓B で「退室」 | 窓A から窓B の音声枠が消える。窓A はエラーにならない |
| 4-2 | 窓B で再度同じコードで参加 → 「VCに参加」 | 再び `connected` になり音声が通る |
| 4-3 | 窓B の**タブを閉じずに**機内モード/ネットワーク切断 → 60秒以内に復帰 | 窓A 側で一度ピアが閉じ、窓B の復帰（roomState 受信）後に張り直されて `connected` に戻る |
| 4-4 | 窓B を 60 秒以上切断 | 窓A の参加者一覧から窓B が消え、ピアも閉じている |

> 4-3 の「復帰」は、窓B のページ再読み込み（`sessionStorage` のセッションで自動再入室）でも再現できる。

## 5. キック時のピア切断（§3.6）

- `kick` はサーバー未実装（`server/rooms.ts` の TODO）のため、**現時点では手動確認できない**。
- 実装され次第、以下を確認する。
  - キックされた本人（`kicked` 受信）: VC から抜け、マイク・カメラの取得が止まる（ブラウザのマイク使用インジケータが消える）
  - 残ったメンバー（`playerKicked` 受信）: 対象のピアが**即座に**閉じ、音声枠が消える
- 現状は `playerLeft`（退室・切断）経由の切断で同等の経路を確認できる（第4節）。

## 既知の制約

- **同一 PC の2窓ではハウリングする。** 片方をミュートするかイヤホンを使う。
- **`localhost` 以外の HTTP では動かない**（getUserMedia は Secure Context 必須）。
  実機・複数端末での確認は HTTPS（リバースプロキシで TLS 終端）が前提。
- **TURN は未導入。** 現在は STUN（`stun:stun.l.google.com:19302`）のみのため、
  対称型 NAT やモバイル回線同士では P2P が成立しないことがある（§3.6）。
  coturn 導入後は `VC.setIceServers([...])` で差し替える（認証情報はサーバーから配る）。
- **Perfect Negotiation は `setLocalDescription()` の引数なし呼び出しに依存する。**
  Safari 15 未満では動作しない（対応ブラウザは直近版のみ・仕様書 §7）。
- カメラ ON 時の映像は 640x360 を要求するだけで、品質劣化時の自動停止（§3.6）は未実装。
- 現時点で `public/index.html` は開発用ページ。本番の部屋ページ（`room.html`）では
  `VC.init({ send, container, onStatus })` と `VC.handleServerMessage(msg)` を
  同じ形で呼べば再利用できる。

## 参考: rtcSignal payload の契約（vc.js 内で完結）

```js
{ kind: "ready", session }     // VC 参加中の告知。session は接続世代の識別子
{ kind: "bye" }               // VC 離脱の告知
{ kind: "desc", description }  // offer / answer
{ kind: "ice",  candidate }    // ICE candidate（null は収集完了）
```

サーバーは `payload` を解釈せず、`{ t: "rtcSignal", from, payload }` として転送するだけ（§3.8）。
