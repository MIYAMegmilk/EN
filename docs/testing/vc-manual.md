# VC（音声・カメラ）手動テスト手順書

- 対象: `public/room/vc.js` + `server/rooms.ts` の rtcSignal 中継
- 前提: 詳細仕様書 [overall.md](../spec/overall.md) §3.6 / §3.8 / §8
- 自動テストで担保できるのはサーバーの中継条件のみ（`server/tests/rooms_test.ts`）。
  WebRTC 本体はブラウザ API のためモックが困難で、本書の手動確認で担保する。

## 0. 準備

```powershell
deno task dev
```

- ブラウザで `http://localhost:8000/` を2窓（別ウィンドウ推奨。タブでも可）開く。
- **`localhost` は Secure Context として扱われるため `getUserMedia` が使える。**
  他端末から IP 直打ち（`http://192.168.x.x:8000/`）でアクセスすると
  Secure Context でないためマイクを取得できない。実機確認は HTTPS 経由で行うこと。
- マイク・カメラの許可ダイアログが出たら「許可」を選ぶ。
- **同一 PC の2窓ではハウリングする。** 片方をミュートするか、両方にイヤホンを使う。
  音の疎通は「片方だけミュート解除して声を出し、もう片方で聞こえるか」で確認する。
- **同一 PC ではカメラを2窓同時に使えない**（Windows のカメラは一度に1プロセス占有。
  マイクは共有可）。後から ON した側が `NotReadableError` / `AbortError` で失敗する。
  §3 のカメラ確認は「片方ずつ交互に ON」で行い、双方同時 ON の検証は
  物理カメラ2台（スマホ実機。HTTPS 必須）が使えるようになってから行う。

## 1. 音声の疎通（最重要）

| # | 手順 | 期待結果 |
|---|---|---|
| 1-1 | 窓Aでニックネームを入れて「招待制ルームを作成」 | ルーム画面と6桁コードが表示される |
| 1-2 | 窓Bでニックネームと同じコードを入れて「参加」 | 両方の参加者一覧に2人表示される |
| 1-3 | 窓Aで「VCに参加」 | 状態表示が「参加中」になる。マイク許可を求められる |
| 1-4 | 窓Bで「VCに参加」 | 双方の状態表示に相手の名前と接続状態が出る |
| 1-5 | 数秒待つ | **双方の状態表示が `<相手の名前>: connected` になる**（`connecting` → `connected`） |
| 1-6 | 窓Bをミュートし、窓Aで声を出す | 窓B側で声が聞こえる（イヤホン推奨） |
| 1-7 | 通信ログを見る | `rtcSignal` が双方向に流れている（`desc` → `ice` の順） |

`connected` にならない場合の確認点:

- ブラウザの DevTools コンソールに `VC ...failed` のログが出ていないか
- `chrome://webrtc-internals`（Chrome）で ICE candidate が交換されているか
- 同一 LAN 内であれば STUN 無しでも成立するため、`stun:stun.l.google.com:19302`
  への到達性は必須ではない。NAT 越え（別回線）の確認は TURN 導入後に行う

## 4. 切断・再接続（§8 VC 行）

| # | 手順 | 期待結果 |
|---|---|---|
| 4-1 | 窓B で「退室」 | 窓A から窓B の音声枠が消える。窓A はエラーにならない |
| 4-2 | 窓B で再度同じコードで参加 → 「VCに参加」 | 再び `connected` になり音声が通る |

| 4-4 | 窓B を 60 秒以上切断 | 窓A の参加者一覧から窓B が消え、ピアも閉じている |

## 8. 品質劣化時の映像自動停止（§3.6）

「品質劣化時は映像を自動停止し音声優先」の確認。**音声が途切れないことが最優先の合格条件**であり、
映像が止まること自体は正常な保護動作（画面上もエラー表示ではなく専用の枠に出る）。

判定ロジックの単体確認は [vc-quality-test.html](vc-quality-test.html)（ブラウザで直接開く）で行う。
本節は実回線・実ブラウザでしか確認できない部分だけを扱う。

### 8.0 この節の前提条件

- **Chrome 124 以上が必須。** 124 未満では DevTools のネットワークスロットリングが WebRTC に効かず、
  劣化を再現できないため**テスト自体が無効になる**。最初に 8-0 でバージョンを確認すること。
- **iOS 実機は Network Link Conditioner を使う**（設定 → デベロッパ → Network Link Conditioner）。
  デベロッパメニューは Mac に一度接続して開発者モードを有効にすると出る。
- **`setParameters({ maxBitrate })` は劣化再現に使えない。** 送信ビットレートに上限を掛けるだけで
  輻輳が起きないため、`qualityLimitationReason` が `bandwidth` にならない。必ず実際の
  スロットリング（DevTools / Network Link Conditioner）で確認する。
- スロットリングは DevTools の Network タブ → Throttling で適用する。カスタムプロファイルは
  「Add profile」から Packet loss を指定して作る。
- 2窓で確認する場合、**同一 PC ではカメラを2窓同時に使えない**（第0節）。双方向の映像確認が
  必要な項目（8-4 の相手側表示など）は物理カメラ2台（スマホ実機・HTTPS）で行う。

### 8.1 手順

| # | 手順 | 期待結果 |
|---|---|---|
| 8-0 | Chrome のバージョンを確認（`chrome://version`） | **124 以上**であること。124 未満では DevTools のスロットリングが WebRTC に効かず、テスト自体が無効になる |
| 8-1 | 2窓で VC 参加・カメラON。DevTools で "Slow 4G" を適用 | カメラONから30秒（ウォームアップ）経過後、10〜20秒以内に「**回線が不安定なため映像を停止しました**」と表示され、両窓で映像が消える。**音声は途切れない** |
| 8-2 | カスタムプロファイルで Packet loss 20% | 同上 |
| 8-3 | スロットリングを解除 | **映像は自動では戻らない**（§3.6 の明示操作規定）。「**回線が回復しました。カメラを再開できます**」と表示され［カメラを再開］が強調される。停止から**60秒**（最小保持時間）は回復通知が出ないので、それまで待つ |
| 8-4 | ［カメラを再開］を押す | 映像が戻り、相手窓にも表示される |
| 8-5 | Packet loss 5% で3分放置 | ON/OFF を繰り返さない（ヒステリシス） |
| 8-6 | カメラOFF のままスロットリング | 何も起きない（監視はカメラON時のみ） |
| 8-7 | VC参加直後・カメラON直後にスロットリング | **カメラONから30秒間**は停止しない（ウォームアップ除外。`QUALITY_CAMERA_WARMUP_MS`） |
| 8-8 | 6人フルメッシュで1人だけ劣化 | 他の5人のカメラは停止しない（bandwidth の切り分け） |
| 8-9 | CPU 負荷で `cpu` 制限を誘発 | 1本でも cpu 制限が出たら停止する。このとき通知は「**端末の負荷が高いため映像を停止しました**」（回線の文言ではない）。最小保持時間の経過後は「**負荷が下がりました。カメラを再開できます**」が出る |
| 8-9b | 回線を細らせず（スロットリングなし）カメラを ON にして30秒以上放置 | **映像は停止しない**。Chrome は送出開始直後に回線が健全でも `qualityLimitationReason: "bandwidth"` を報告するが、裏付け（低帯域 / 高RTT）が無いため誤検知にならないこと |
| 8-10 | 自動停止を3回発生させる | 3回目以降は自動停止しない（回数上限） |
| 8-11 | 自動停止中に退室→再入室 | タイマーが停止し状態がリセットされる |
| 8-12 | **iOS 実機**（設定→デベロッパ→Network Link Conditioner の "Very Bad Network"） | 自動停止が働き、音声は維持される |
| 8-13 | iOS Safari で**画面の判定モード表示**を確認 | Safari 17.4 以上なら「主指標」、17.3 以下なら「代替指標」と表示される。**コンソール不要で確認できること** |
| 8-14 | 自動停止後にページ再読み込み | カメラは **OFF** の状態で復帰する（§3.6 の初期OFF規定） |

### 8.2 補足

- 8-9 の CPU 負荷は、同じ端末で他アプリ（動画エンコード等）を並行させるか、
  ブラウザのタブを多数開いて誘発する。狙って出しにくいため、出なければ「未確認」と記録する。
- **主判定の `bandwidth` は単体では停止理由にならない。** Chrome は送出開始直後、
  回線が健全でも `qualityLimitationReason: "bandwidth"` を報告し続ける
  （実測: 同一環境で 9.8 秒 / 18.1 秒とばらつく）。そのため
  `bandwidth` は「送出可能帯域が 320kbps 未満」または「RTT が 0.8 秒超」の
  いずれかで裏付けが取れたときだけ原因として採る（`sampleCause()`）。
  8-1 / 8-2 が期待どおり停止しない場合は、スロットリングが実際に
  `availableOutgoingBitrate` / `currentRoundTripTime` に効いているかを
  `chrome://webrtc-internals` で確認すること。
- 8-9 / 8-9b の通知文言は停止理由で分岐する。`cpu` は「端末の負荷が高いため…」、
  それ以外（`bandwidth`）は「回線が不安定なため…」。回復通知も同様に分岐する。
- 8-13 の判定モードは画面の「判定: 主指標 / 代替指標 / 判定不可」表示で読む。
  `qualityLimitationReason` は Safari 17.4 で入ったため、それ以前は代替指標
  （パケットロス・RTT）にフォールバックする。
- 8-1 / 8-2 で**音声が途切れた**場合は、映像停止の判定より先に音声側の劣化を疑う。
  §3.6 の優先順位（音声 > 映像）に反するため、その時点で不合格として扱う。

## 既知の制約

- **同一 PC の2窓ではハウリングする。** 片方をミュートするかイヤホンを使う。
- **`localhost` 以外の HTTP では動かない**（getUserMedia は Secure Context 必須）。
  実機・複数端末での確認は HTTPS（リバースプロキシで TLS 終端）が前提。
- **TURN は未導入。** 現在は STUN（`stun:stun.l.google.com:19302`）のみのため、
  対称型 NAT やモバイル回線同士では P2P が成立しないことがある（§3.6）。
  coturn 導入後は `VC.setIceServers([...])` で差し替える（認証情報はサーバーから配る）。
- **Perfect Negotiation は `setLocalDescription()` の引数なし呼び出しに依存する。**
  Safari 15 未満では動作しない（対応ブラウザは直近版のみ・仕様書 §7）。
- カメラ ON 時の映像は 640x360 を要求するだけ。品質劣化時の自動停止（§3.6）の手動確認は第8節。
- **フォールバック判定は `getSettings().frameRate` が取れないブラウザでは働かない。**
  実効 FPS の分母（要求 FPS）はカメラ ON 時に `track.getSettings().frameRate` から
  一度だけ控えている。`getSettings()` を持たない、または `frameRate` を返さない
  ブラウザではこの分母が `null` になり、`fpsRatio` も常に `null` になる。
  フォールバック判定は `fpsRatio` が閾値を下回ることを入口条件にしているため、
  そうした環境で主判定（`qualityLimitationReason`）も取れない場合は、
  品質監視が事実上働かない（画面の判定モード表示は「判定不可」になる）。
  音声は保たれるため、誤検知より検知漏れに倒す方針（リスク R6）で許容している。
- **主判定の `bandwidth` は裏付けが取れたときだけ原因として採る。** 詳細は 8.2 の補足を参照。
- 現時点で `public/index.html` は開発用ページ。本番の部屋ページ（`room.html`）では
  `VC.init({ send, container, onStatus })` と `VC.handleServerMessage(msg)` を
  同じ形で呼べば再利用できる。

## 参考: rtcSignal payload の契約（vc.js 内で完結）

```js
{ kind: "ready", session }     // VC 参加中の告知。session は接続世代の識別子
{ kind: "bye" }               // VC 離脱の告知
{ kind: "desc", description }  // offer / answer
{ kind: "ice",  candidate }    // ICE candidate（null は収集完了）
```

サーバーは `payload` を解釈せず、`{ t: "rtcSignal", from, payload }` として転送するだけ（§3.8）。
