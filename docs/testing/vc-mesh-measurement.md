# フルメッシュ6人 VC 実測手順書（SFU 移行の要否を判断するため）

- 対象: `public/room/vc.js`（フルメッシュ・SFU なし・`VC_CAPACITY = 6`）
- 前提: 詳細仕様書 [overall.md](../spec/overall.md) §3.6 / §3.8
- 関連: [vc-manual.md](vc-manual.md)（VC 全体の手動テスト）、
  [vc-quality-test.html](vc-quality-test.html)（品質判定ロジックの単体テスト）
- 計測ツール: [vc-mesh-stats.html](vc-mesh-stats.html)（本書 第7節）

## 0. この文書の目的

**「フルメッシュ6人は本当に破綻するのか」を、体感ではなく測定値で決める**ための手順書である。

SFU（Cloudflare Realtime 等）への移行は `vc.js`（1374 行）の作り直しを伴い、数日規模の工数になる。
壊れないのであれば、その工数は画面共有の作り込みに回したい。したがって**払う前に測る**。

この測定が出す結論は次の4つのいずれかであり、第5.7節の総合判定がどれを指すかを決める。

| 結論                    | 内容                                                                  |
| ----------------------- | --------------------------------------------------------------------- |
| **A. メッシュ据え置き** | 6人・全員カメラ ON でも破綻しない。工数を画面共有へ回す               |
| **B. 定員を下げる**     | 4人までは健全、6人で破綻。`VC_CAPACITY` を下げて据え置く              |
| **C. 音声のみメッシュ** | 音声だけなら6人で健全、映像で破綻。カメラ／画面共有だけ別経路を考える |
| **D. SFU へ移行**       | 音声を含めて破綻する。作り直しの工数を払う                            |

## 1. 前提（再調査不要な確定事実）

測定の設計はこの4点に基づいている。測定中にこれを疑う必要はない。

- **エンコーダは `RTCPeerConnection` ごとに独立**（libwebrtc のソースで確認済み）。
  6人なら同じカメラ映像を **5 回エンコードする**。→ CPU 負荷は人数にほぼ比例して増える
- **輻輳制御も `RTCPeerConnection` ごとに独立**。5 本が互いの帯域を食い合い、
  それぞれが「自分だけが使える帯域」を過大に見積もる。→ 上り帯域の奪い合いが起きる
- WebRTC 創設メンバーの Justin Uberti が **「メッシュは5人以下を推奨」**と述べている。 現状の
  `VC_CAPACITY = 6` は**すでにその推奨を超えている**
- カメラは **640×360 で取得**（`vc.js` の `getUserMedia` 制約。`width.ideal` / `height.ideal`
  のみ）。 **フレームレートは指定していない**ため、端末とブラウザが決める（多くは 30fps）。 → 送信
  FPS の「要求値」は端末ごとに違う。必ず `track.getSettings().frameRate` を記録する

> **なぜ 5 回か**: 自分を除く 5 人ぶんの `RTCPeerConnection` が立つ。 受信も 5
> 本あるので、デコードも 5 本ぶん走る。エンコード 5 + デコード 5 が同時に動くのが
> 「6人フルメッシュ」の実体である。

## 2. 準備

### 2.1 必要なもの

| 項目     | 内容                                                                                          |
| -------- | --------------------------------------------------------------------------------------------- |
| 人数     | **6人**（最低でも異なる 6 端末。同一 PC の複数窓は不可、下記参照）                            |
| ブラウザ | **Chrome 124 以上**を推奨。`chrome://webrtc-internals` を使うため                             |
| 接続     | **HTTPS 必須**（`getUserMedia` は Secure Context 必須）。`localhost` 以外の HTTP では動かない |
| カメラ   | 各端末に 1 台。**同一 PC の 2 窓ではカメラを同時に使えない**（Windows は 1 プロセス占有）     |
| 記録役   | 1人。第6節のテンプレートに書き込む。参加者は全員が自分の値を記録役へ送る                      |

> **同一 PC の複数窓で代用してはいけない。** 1 台に 6 人ぶんのエンコード／デコードが集中し、
> 「メッシュだから重い」のか「1 台に押し込んだから重い」のかが区別できなくなる。
> この測定の目的そのものが失われる。

### 2.2 事前に全員がやること

1. ブラウザを再起動し、**他のタブ・他のアプリ（動画・ゲーム・ビルド等）を閉じる**。 CPU
   測定が汚れる。
2. `chrome://version` でバージョンを控える。
3. **イヤホンを着ける**（ハウリング防止。音声の途切れを耳でも確認するため必須）。
4. 端末情報を第6節「環境シート」に記入して記録役へ送る。
5. 回線速度を測って控える（[fast.com](https://fast.com) 等。**上り**の値が重要）。
   - 6人メッシュでは自分の上りに **5 本ぶんの送信**が乗る。上りが細い端末が真っ先に落ちる。

### 2.3 計測ツールの用意

各参加者は自分の端末で [vc-mesh-stats.html](vc-mesh-stats.html) を開き、
表示されている**収集スニペット**をコピーしておく（詳細は第7節）。

## 3. 何を測るか

### 3.1 `vc.js` の既存の品質監視から流用できるもの

`vc.js` の `extractRawStats()` が**すでに取っている値**は次の 5 つだけである。

| 値                         | 取得元                       | 本測定での扱い                                           |
| -------------------------- | ---------------------------- | -------------------------------------------------------- |
| `framesEncoded`            | `outbound-rtp`(video) の合計 | **流用**。差分で実効送信 FPS を出す                      |
| `timestamp`                | `outbound-rtp`(video)        | **流用**。差分の分母（壁時計ではなく統計側の時刻を使う） |
| `qualityLimitationReason`  | `outbound-rtp`(video)        | **流用**。CPU 律速か帯域律速かの主判定                   |
| `currentRoundTripTime`     | 選択された `candidate-pair`  | **流用**。閾値 0.8 秒もそのまま使う                      |
| `availableOutgoingBitrate` | 選択された `candidate-pair`  | **流用**。閾値 320 kbps もそのまま使う                   |

`candidate-pair` の選び方（`transport.selectedCandidatePairId` → `selected` →
`nominated && succeeded` の順に探す
`pickCandidatePair()`）も**そのまま流用**する。ブラウザによって出る値が違うため、 自前で `selected`
だけを見ると取り漏らす。

### 3.2 追加で要るもの

既存の監視は**「自分の送出が劣化しているか」だけ**を見ており、受信側の統計は意図的に使っていない
（`vc.js`
の品質監視のコメント参照）。しかし今回知りたいのは「**6人メッシュが体験として破綻するか**」
であり、次が足りない。

| 不足しているもの                                                             | なぜ要るか                                                                                                                                                                                                                          |
| ---------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CPU の実測値**（`totalEncodeTime`）                                        | `qualityLimitationReason` は「律速したか」の真偽でしかない。**5 本ぶんのエンコードに CPU をどれだけ食われているか**という量が取れない。SFU にすれば 1 本になる ＝ ここが 1/5 になる、という**移行効果の見積もりに直結する唯一の値** |
| **受信側の破綻**（`freezeCount` / `totalFreezesDuration` / `framesDropped`） | 送信が健全でも受信が固まっていれば体験は破綻している。5 本のデコードが詰まるのはメッシュ特有の症状                                                                                                                                  |
| **音声の途切れ**（`concealedSamples` / audio `packetsLost`）                 | §3.6 の最優先は音声。「音声が途切れたか」を耳ではなく数値で判定するため                                                                                                                                                             |
| **実際の送信量**（`bytesSent`）                                              | `availableOutgoingBitrate` は**推定値**。実際に何 bps 出ているかとは別物。5 本の合計が上り帯域を食い潰しているかを見る                                                                                                              |
| **再送率**（`retransmittedPacketsSent`）                                     | 輻輳の先行指標。5 本が食い合っていると、破綻の前に再送が増える                                                                                                                                                                      |
| **受信可能帯域**（`availableIncomingBitrate`）                               | 6人メッシュでは**下りにも 5 本**乗る。上りだけ見ていると片手落ち                                                                                                                                                                    |
| **relay(TURN) 経由か**                                                       | TURN 経由になると経路が伸びて RTT が跳ね、VPS の帯域も食う。**メッシュ 5 本が全部 relay** になった場合の影響は P2P とまったく別問題                                                                                                 |
| **人数のスケール**                                                           | 既存監視は「今」しか見ない。2人 → 4人 → 6人で**どう増えるか**が判断の本体                                                                                                                                                           |

### 3.3 指標の定義表

計測ツール（第7節）が自動で集めるのはこの表の全項目である。
**「破綻の閾値」列の根拠は第5節にまとめてある。**

#### 送信側（`outbound-rtp`, `kind: "video"`）— ピアごとに 5 本

| 指標                         | 何が分かるか                                                   | 見方                                                                            |
| ---------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `framesEncoded`              | 累積エンコード枚数                                             | **差分で見る**。`Δframes / Δt` が実効送信 FPS                                   |
| `framesPerSecond`            | ブラウザが出す送信 FPS                                         | 上の実効値と突き合わせる。片方しか出ないブラウザがある                          |
| `qualityLimitationReason`    | `none` / `cpu` / `bandwidth` / `other`。**何が律速しているか** | 主判定。`cpu` が出ればエンコード飽和、`bandwidth` なら回線                      |
| `qualityLimitationDurations` | 上の各理由で**過ごした累積秒数**                               | **これが本命**。真偽値ではなく「全体の何 % を `cpu` で過ごしたか」が出る        |
| `totalEncodeTime`            | 累積エンコード時間（秒）                                       | `ΔtotalEncodeTime / Δt` = **エンコード占有率**。5 本の合計が CPU コア換算の負荷 |
| `bytesSent`                  | 累積送信バイト                                                 | `Δbytes × 8 / Δt` = 実効送信ビットレート。5 本の合計が上り消費                  |
| `retransmittedPacketsSent`   | 累積再送パケット数                                             | `Δ再送 / Δ送信` = 再送率。輻輳の先行指標                                        |
| `frameWidth` / `frameHeight` | 実際に送っている解像度                                         | 640×360 から落ちていたら、ブラウザが解像度を下げて延命している                  |

#### 受信側（`inbound-rtp`, `kind: "video"`）— ピアごとに 5 本

| 指標                   | 何が分かるか     | 見方                                                    |
| ---------------------- | ---------------- | ------------------------------------------------------- |
| `framesDecoded`        | 累積デコード枚数 | 差分で受信 FPS                                          |
| `framesDropped`        | 累積で捨てた枚数 | `Δdropped / (Δdecoded + Δdropped)` が破棄率             |
| `freezeCount`          | 累積フリーズ回数 | **体感に最も近い指標**。1 分あたり何回固まったか        |
| `totalFreezesDuration` | 累積フリーズ秒数 | 計測時間に占める割合 = **映像が止まっていた時間の割合** |
| `jitter`               | 到着ゆらぎ（秒） | バッファが吸収しきれるか。大きいほど遅延も増える        |
| `packetsLost`          | 累積ロスパケット | `Δlost / (Δlost + Δreceived)` がロス率                  |

#### 受信側（`inbound-rtp`, `kind: "audio"`）— §3.6 の最優先項目

| 指標                     | 何が分かるか                          | 見方                                                                                          |
| ------------------------ | ------------------------------------- | --------------------------------------------------------------------------------------------- |
| `concealedSamples`       | 失われた音を補間（PLC）したサンプル数 | `Δconcealed / ΔtotalSamplesReceived` = **音声の途切れ率**。耳で「途切れた」と感じる部分の正体 |
| `totalSamplesReceived`   | 累積受信サンプル数                    | 上の分母                                                                                      |
| `packetsLost` / `jitter` | 音声のロス・ゆらぎ                    | 映像と分けて見る。**映像を止めても音声が戻らなければ、それは §3.6 の前提が崩れている**        |
| `bytesReceived`          | 累積受信バイト                        | 差分が 0 の区間 = **完全な無音（通信断）**                                                    |

#### 経路（`candidate-pair` / `transport` / `local-candidate` / `remote-candidate`）

| 指標                                         | 何が分かるか                         | 見方                                                                                                                             |
| -------------------------------------------- | ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| `currentRoundTripTime`                       | 往復遅延（秒）                       | 会話の噛み合いに直結。5 本のうち最悪値を見る                                                                                     |
| `availableOutgoingBitrate`                   | 輻輳制御の**上り推定値**             | 5 本が互いに食い合って推定を誤るのがメッシュの弱点。**5 本の推定の合計が実際の上り実測を超えていたら、過大評価が起きている証拠** |
| `availableIncomingBitrate`                   | 下り推定値                           | 出さないブラウザもある（`null` 可）                                                                                              |
| `localCandidateType` / `remoteCandidateType` | `host` / `srflx` / `prflx` / `relay` | どちらかが **`relay` なら TURN 経由**。現状 TURN 未導入のため通常は出ないはずで、出たら記録して報告する                          |
| `bytesSent` / `bytesReceived`（pair）        | この経路の実トラフィック             | 送信側 `outbound-rtp` の合計と突き合わせる                                                                                       |

#### 端末側（`getStats()` では取れない。人が記録する）

| 指標                             | 測り方                                         |
| -------------------------------- | ---------------------------------------------- |
| ブラウザ全体の CPU 使用率        | 第4.4節                                        |
| ファンの音・端末の発熱           | 主観だが記録する。サーマルスロットリングの兆候 |
| バッテリー消費（ノート／スマホ） | 開始時と終了時の %                             |

## 4. どう測るか

### 4.1 原則

- **人数を段階的に増やす。** いきなり6人で測ると、CPU が効いたのか帯域が効いたのか、
  誰の回線が足を引っ張ったのかが分からない。**2人 → 4人 → 6人**の順に測り、**増え方**を見る。
- **カメラの ON 本数も段階的に増やす。** 音声のみ・半数 ON・全員 ON の 3 段階。
  音声のみで壊れるならメッシュそのものが駄目、映像でだけ壊れるなら結論 C の目がある。
- **1 ラウンド 5 分。** 最初の 30 秒は捨てる（`QUALITY_CAMERA_WARMUP_MS = 30000` と同じ理由で、
  Chrome は送出開始直後、回線が健全でも `bandwidth` を報告し続ける。実測 9.8〜18.1 秒）。
  **有効測定区間は 30 秒〜5 分の 4 分 30 秒**。
- **各条件 3 回。** 1 回だけでは回線の一時的なゆらぎと区別できない。 **3 回中 2
  回以上**で閾値を超えたら「その条件は破綻」と判定する（多数決）。
- **順番を変えて 1 セット追加する**（時間があれば）。端末の発熱が後半に効く可能性があるため、 6人 →
  4人 → 2人の逆順でも 1 セット取れると、熱の影響を切り分けられる。

### 4.2 シナリオ表

各行が 1 ラウンド。**上から順に実施する**（軽い条件から重い条件へ）。

| #  | 人数 | カメラ ON         | 時間     | 回数 | 何を見るか                                                             |
| -- | ---- | ----------------- | -------- | ---- | ---------------------------------------------------------------------- |
| R1 | 2    | 0人（音声のみ）   | 5分      | 3    | **基準線**。ここが壊れるなら回線側の問題でメッシュの話ではない         |
| R2 | 2    | 2人（全員）       | 5分      | 3    | 1 本ぶんのエンコード負荷。単独エンコードの `totalEncodeTime` を採る    |
| R3 | 4    | 0人（音声のみ）   | 5分      | 3    | 音声 3 本での挙動                                                      |
| R4 | 4    | 2人（半数）       | 5分      | 3    | 送信する人／しない人の非対称を見る                                     |
| R5 | 4    | 4人（全員）       | 5分      | 3    | 3 本エンコード＋3 本デコード                                           |
| R6 | 6    | 0人（音声のみ）   | 5分      | 3    | **音声メッシュの限界**。ここが緑なら結論 C が残る                      |
| R7 | 6    | 3人（半数）       | 5分      | 3    | 中間。ON の人と OFF の人の差が最も出る                                 |
| R8 | 6    | 6人（全員）       | **10分** | 3    | **本命**。5 本エンコード＋5 本デコード。熱の影響も見たいので長めに取る |
| R9 | 6    | 6人（全員）＋会話 | 5分      | 1    | **実運用に近い状態**。全員が実際に喋る。R8 は無言でよいが、これは喋る  |

- R4 / R7 で「カメラ ON にする人」は**毎回同じ人**にする。回ごとに変えると比較できない。
- **ラウンド間は 1 分あける。** 全員 VC から抜けて、CPU が落ち着いてから次へ。
- R8 は 3 回とも 10 分取る。**熱によるサーマルスロットリング**は 5 分では出ないことがある。

### 4.3 1 ラウンドの手順

各参加者が自分の端末で行う。

1. `docs/testing/vc-mesh-stats.html`
   を開き、**「計測対象のルームを開く」**でルーム画面を開く（第7節）。
2. **VC に参加する前に**、DevTools コンソールに収集スニペットを貼って実行する。 `RTCPeerConnection`
   を差し替えるため、**ピアが立った後では捕まえられない**。
3. `chrome://webrtc-internals` を**別タブ**で開いておく（第4.5節）。
4. 全員そろったら「VCに参加」。シナリオ表の指定どおりカメラを ON にする。
5. **30 秒待つ**（ウォームアップ）。
6. 計測ツールで**［計測開始］**を押す。以後 2 秒間隔でサンプルが積まれる。
7. 指定時間そのまま待つ。R9 以外は無言でよい（音声の統計は取れる）。 **タブを裏に回さない**。Chrome
   はバックグラウンドタブでタイマーを間引くため、 サンプル間隔が崩れて差分が壊れる。
8. 途中で **CPU 使用率を 1 分おきに 3 回**メモする（第4.4節）。
9. 時間になったら**［計測停止］**→**［CSV をコピー］**。 記録役へ送る（ファイル名は
   `R8-回2-<あだ名>.csv` のように）。
10. 計測ツールの**［判定］**欄に出た結果を、第6.2節の表に転記する。
11. VC から抜ける。1 分あけて次のラウンドへ。

### 4.4 CPU 使用率の測り方

**3 つの層があり、混同しないこと。**

#### (1) `getStats()` の `totalEncodeTime`（自動収集・最も信頼できる）

計測ツールが自動で拾う。`ΔtotalEncodeTime / Δt` が**エンコード占有率**で、単位は「秒/秒」。

- 1 本で 0.05（= 50 ms/s）なら、そのピア向けのエンコードに CPU 1 コアの 5% を使っている
- **5 本の合計**が、フルメッシュでエンコードに払っているコスト
- **SFU に移行するとこれが 1/5 になる。**移行効果はこの数字で見積もれる

> これは**エンコードだけ**の時間である。デコード・描画・輻輳制御・ネットワーク処理は含まない。
> ブラウザ全体の CPU 使用率とは一致しないので、(2) と併用する。

#### (2) Chrome のタスクマネージャ（ブラウザ内訳）

`Shift + Esc`（Windows）／メニュー → その他のツール → タスク マネージャ。

- ルーム画面のタブ行と、**「GPU プロセス」**行、**「ユーティリティ: Audio Service」**行を見る
- CPU 列の値を控える。**Chrome の CPU 列は 1 コアを 100% とした値**なので、 4 コアの端末なら合計
  400% が上限。**論理コア数で割って正規化してから比較する**
- 論理コア数は DevTools コンソールで `navigator.hardwareConcurrency` で取れる

#### (3) OS のタスクマネージャ（端末全体）

Windows: `Ctrl + Shift + Esc` → パフォーマンス → CPU。 macOS: アクティビティモニタ → CPU。

- 端末全体が張り付いているか（100% 近いか）を見る。ここが 100% なら他アプリも巻き添えになる
- **CPU の周波数**も見る（Windows のパフォーマンスタブに出る）。基本周波数を大きく下回っていたら
  **サーマルスロットリング**が起きている。ファンの音とあわせて記録する

**記録するのは (1) 自動 / (2) と (3) は 1 分おきに 3 回、その中央値。**

### 4.5 `chrome://webrtc-internals` の使い方

計測ツールが取りこぼした場合の裏取りと、グラフでの傾向確認に使う。

1. **VC 参加前に開く**。参加後に開くと、それ以前の統計が取れない。
2. ページ上部に `RTCPeerConnection` が**ピアの本数だけ**並ぶ（6人なら 5 個）。 **5
   個並んでいること自体が「フルメッシュである」ことの確認**になる。
3. 各ピアを開くと `outbound-rtp` / `inbound-rtp` / `candidate-pair` のグラフが出る。 見るべきは次の
   4 つ。
   - `qualityLimitationReason`（色分けの帯。`cpu` の帯がどれだけ占めるか）
   - `[bytesSent_in_bits/s]`（実効送信ビットレート）
   - `availableOutgoingBitrate`
   - `framesPerSecond`（送信・受信）
4. 右上の **［Create Dump］→［Download the PeerConnection updates and stats data］**で JSON
   をダウンロードできる。**R8 は必ずダンプを取って保存する。**
   後から「あのとき何が起きていたか」を追える唯一の手段になる。

> **注意**: `chrome://webrtc-internals` を開いている間、Chrome
> は全ピアの統計を高頻度で収集し続ける。 これ自体が CPU を食うため、**CPU
> 使用率の測定値はやや高めに出る**。 (2)(3) の CPU を測る回では webrtc-internals
> のタブを閉じておくか、 「開いていた／いなかった」を記録に残すこと。

### 4.6 回線の記録

各参加者は次を記録する（第6.1節の環境シート）。

| 項目           | 記録内容                                                           |
| -------------- | ------------------------------------------------------------------ |
| 回線種別       | 光 / ケーブル / ADSL / モバイル（4G・5G）/ テザリング / 公衆 Wi-Fi |
| 接続方法       | 有線 / Wi-Fi（2.4GHz・5GHz・6GHz のどれか）                        |
| 実測速度       | 下り ○ Mbps / **上り ○ Mbps**（測定直前に計測）                    |
| ISP・地域      | 都道府県まで（RTT の説明に使う）                                   |
| VPN / プロキシ | 使用の有無（使っていたら切って測り直す）                           |

**上りが 5 Mbps を下回る参加者がいたら、必ず記録に残す。** 6人メッシュでは 640×360 を 5
本送るため、上り 3〜5 Mbps 程度を要求する。
その人が最初に破綻するのは当然であり、**「メッシュが駄目」ではなく「その回線が細い」**という
別の結論になりうる。混同しないために記録が要る。

## 5. 何をもって「破綻」とするか

**本書の核心。**「重い」「カクつく」ではなく、**測定値で判定する。**

判定は**有効測定区間**（開始 30 秒を除いた区間）に対して行う。 各項目は
**緑（健全）／黄（兆候）／赤（破綻）** の 3 段階。 **3 回中 2
回以上が赤なら、その条件はそのカテゴリで破綻**と確定させる。

### 5.1 閾値の出どころ

| 種別                           | 内容                                                                                                                                                                                                                                      |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **外部根拠あり**               | RTT の 0.8 秒 / 0.3 秒のみ。ITU-T G.114（片道 400ms 超は多くの用途で許容不可、150ms 以下は透過的）を往復に換算した値。`vc.js` の `QUALITY_RTT_STOP_SEC` / `QUALITY_RTT_RESUME_SEC` と同一                                                 |
| **`vc.js` から流用（暫定値）** | 320 kbps（`QUALITY_BITRATE_STOP_BPS`）、FPS 比 0.5（`QUALITY_FPS_STOP_RATIO`）、時間比 60%（`QUALITY_STOP_HITS / QUALITY_WINDOW_SIZE = 3/5`）。**`vc.js` 側でこれらは【暫定値】と明記されている。**流用しているだけで、外部の裏付けは無い |
| **本書で新たに置いた暫定値**   | エンコード占有率、フリーズ、音声補間率、再送率。**すべて暫定値**。この測定自体が、これらを実測で見直すための材料になる                                                                                                                    |

> **重要**: 閾値を超えたこと自体が「SFU に移行すべき」を意味するのではない。
> 第5.7節の総合判定にかけて初めて結論になる。

### 5.2 カテゴリ A: 音声（最優先・§3.6）

**§3.6 は「品質劣化時は映像を自動停止し音声優先」と定めている。**
したがって**音声が壊れた時点で、映像がどうであれ破綻**である。ここだけは他と重みが違う。

| #  | 判定                                               | 緑       | 黄          | 赤                                                     | 根拠                                                       |
| -- | -------------------------------------------------- | -------- | ----------- | ------------------------------------------------------ | ---------------------------------------------------------- |
| A1 | 音声補間率<br>`Δconcealed / ΔtotalSamplesReceived` | < 1%     | 1〜3%       | **≥ 3%**                                               | 暫定値。PLC が 3% 発動していれば会話に聞き取りにくさが出る |
| A2 | 音声ロス率<br>`Δlost / (Δlost + Δreceived)`        | < 2%     | 2〜5%       | **≥ 5%**                                               | 暫定値                                                     |
| A3 | 音声の完全断                                       | 無し     | —           | **audio `bytesReceived` の差分が 0 の区間が 5 秒以上** | 途切れの定義。1 本でも該当したら赤                         |
| A4 | 音声の RTT                                         | < 0.3 秒 | 0.3〜0.8 秒 | **≥ 0.8 秒**                                           | ITU-T G.114（**唯一の外部根拠**）。`vc.js` と同値          |

**A のいずれかが赤 → その条件は無条件で破綻。** 判定を打ち切って次の条件へ進んでよい。

### 5.3 カテゴリ B: CPU

| #   | 判定                                                                                                 | 緑           | 黄           | 赤                                                   | 根拠                                                                                                                                                                                   |
| --- | ---------------------------------------------------------------------------------------------------- | ------------ | ------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | `qualityLimitationReason` が `cpu` だった時間の割合<br>（`Δqld.cpu / Δt`、**5 本のうち最悪のピア**） | < 5%         | 5〜20%       | **≥ 20%**                                            | 暫定値。`vc.js` は 1 本でも `cpu` を見たら（裏付け無しで）停止する設計であり、`cpu` の報告は端末側の事実の報告として重く扱う。20% は「常態的に律速している」と見なせる下限として置いた |
| B1' | 同上（**vc.js が実際に止める水準**）                                                                 | —            | —            | **≥ 60%**                                            | `QUALITY_STOP_HITS / QUALITY_WINDOW_SIZE = 3/5 = 60%` の流用。ここを超えたら**実装が自動的にカメラを止める**ので、ユーザーには「映像が勝手に消える」体験になる                         |
| B2  | エンコード占有率の**5 本合計**<br>`Σ(ΔtotalEncodeTime / Δt)`                                         | < 0.3        | 0.3〜0.5     | **≥ 0.5**                                            | 暫定値。CPU 1 コアの 50% を**エンコードだけ**で使い切っている状態。デコード 5 本と描画がこれに上乗せされるため、実質の余裕は無い                                                       |
| B3  | 実効送信 FPS 比<br>`(Δframes/Δt) / requestedFps`（最悪のピア）                                       | ≥ 0.75       | 0.5〜0.75    | **< 0.5**                                            | `QUALITY_FPS_STOP_RATIO = 0.5` / `QUALITY_FPS_RESUME_RATIO = 0.75` の流用（**暫定値**）                                                                                                |
| B4  | ブラウザ CPU（論理コア正規化）<br>= Chrome タスクマネージャ合計 ÷ `navigator.hardwareConcurrency`    | < 50%        | 50〜80%      | **≥ 80%**                                            | 暫定値。80% を超えると他アプリ・OS が巻き添えになり、入力遅延が出る                                                                                                                    |
| B5  | サーマルスロットリング                                                                               | 無し         | ファンが回る | **CPU 周波数が基本周波数を明確に下回る／端末が熱い** | 定性。10 分ラウンド（R8）で見る                                                                                                                                                        |
| B6  | 送信解像度の低下<br>`frameWidth` × `frameHeight`                                                     | 640×360 維持 | 一時的に低下 | **区間の半分以上で 640×360 を下回る**                | ブラウザが解像度を下げて延命している＝エンコード能力が足りていない直接の証拠                                                                                                           |

**判定**: B1'・B2・B4 のいずれかが赤、または B1・B3・B6 のうち 2 つ以上が赤 → **CPU が限界**。

### 5.4 カテゴリ C: 帯域・ネットワーク

| #  | 判定                                                                      | 緑         | 黄            | 赤                                         | 根拠                                                                                                                                                                                                    |
| -- | ------------------------------------------------------------------------- | ---------- | ------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| C1 | `availableOutgoingBitrate`（最悪のピア）                                  | ≥ 800 kbps | 320〜800 kbps | **< 320 kbps**                             | `QUALITY_BITRATE_STOP_BPS = 320000` / `QUALITY_BITRATE_RESUME_BPS = 800000` の流用（**暫定値**）                                                                                                        |
| C2 | `currentRoundTripTime`（最悪のピア）                                      | < 0.3 秒   | 0.3〜0.8 秒   | **≥ 0.8 秒**                               | ITU-T G.114（外部根拠）。`vc.js` と同値                                                                                                                                                                 |
| C3 | `qualityLimitationReason` が `bandwidth` だった時間の割合                 | < 20%      | 20〜60%       | **≥ 60% かつ C1 か C2 のどちらかが黄以上** | `vc.js` の `sampleCause()` が主判定の `bandwidth` に**裏付けを要求する**設計をそのまま流用。Chrome は送出開始直後、回線が健全でも `bandwidth` を報告し続けるため（実測 9.8〜18.1 秒）、単体では採らない |
| C4 | 再送率<br>`Δretransmitted / Δpackets`（最悪のピア）                       | < 2%       | 2〜10%        | **≥ 10%**                                  | 暫定値。輻輳の先行指標                                                                                                                                                                                  |
| C5 | **上り推定の総和 vs 実測上り**<br>`Σ availableOutgoingBitrate` ÷ 上り実測 | < 0.8      | 0.8〜1.2      | **≥ 1.2**                                  | 暫定値。**メッシュ特有の症状の直接証拠**。5 本の輻輳制御が独立しているため、各本が「自分は N bps 使える」と推定し、合計が実回線を超える＝**互いに食い合っている**                                       |
| C6 | 実効送信ビットレートの総和<br>`Σ(Δbytes × 8 / Δt)` ÷ 上り実測             | < 0.5      | 0.5〜0.8      | **≥ 0.8**                                  | 暫定値。上り帯域を実際に食い潰している                                                                                                                                                                  |
| C7 | relay(TURN) 経由のピア数                                                  | 0          | 1〜2          | **3 以上**                                 | 現状 TURN は未導入のため**通常は 0 のはず**。0 でない場合は設定を確認する。relay になると経路が伸びて RTT が跳ね、サーバー帯域も食う                                                                    |

**判定**: C1・C2・C3 のいずれかが赤、または C4〜C6 のうち 2 つ以上が赤 → **帯域が限界**。

### 5.5 カテゴリ D: 受信映像の体感

| #  | 判定                                                         | 緑        | 黄           | 赤            | 根拠                                                |
| -- | ------------------------------------------------------------ | --------- | ------------ | ------------- | --------------------------------------------------- |
| D1 | フリーズ頻度<br>`ΔfreezeCount ÷ 測定分数`（最悪のピア）      | < 1 回/分 | 1〜3 回/分   | **≥ 3 回/分** | 暫定値。20 秒に 1 回固まれば会話にならない          |
| D2 | フリーズ時間比<br>`ΔtotalFreezesDuration / Δt`（最悪のピア） | < 2%      | 2〜10%       | **≥ 10%**     | 暫定値。**映像の 1 割が止まっている**状態           |
| D3 | フレーム破棄率<br>`Δdropped / (Δdecoded + Δdropped)`         | < 1%      | 1〜5%        | **≥ 5%**      | 暫定値。デコードが追いつかない ＝ 受信側 CPU の飽和 |
| D4 | 受信ロス率（video）                                          | < 2%      | 2〜5%        | **≥ 5%**      | 暫定値                                              |
| D5 | 受信 jitter（video）                                         | < 0.03 秒 | 0.03〜0.1 秒 | **≥ 0.1 秒**  | 暫定値                                              |

**判定**: D1・D2 のどちらかが赤、または D3〜D5 のうち 2 つ以上が赤 → **受信が限界**。

### 5.6 カテゴリ E: 実装の自動停止が発動したか

`vc.js` の品質ガード（`stopVideoForQuality`）は**破綻を隠す**。
「壊れなかった」のではなく「壊れる前にカメラが自動で止まった」場合を見逃さないため、必ず記録する。

| #  | 記録                                                                                   | 意味                                                                                                                                          |
| -- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| E1 | 自動停止が発動したか（画面に「回線が不安定なため…」「端末の負荷が高いため…」が出たか） | **発動＝その条件で映像は維持できていない。** 音声は守られているので A が緑なら「§3.6 が意図どおり働いた」だが、**体験としては映像が使えない** |
| E2 | 発動理由（`bandwidth` / `cpu`）                                                        | 画面の文言で分かる（回線 or 端末の負荷）。どちらがボトルネックかの直接証拠                                                                    |
| E3 | 発動までの時間                                                                         | カメラ ON から何秒で止まったか                                                                                                                |
| E4 | 発動した人数                                                                           | 6 人中何人が止まったか                                                                                                                        |

**E1 が「発動した」なら、そのラウンドは B か C のどちらかが赤だったのと同義に扱う。**

### 5.7 総合判定 — 結論の出し方

R8（6人・全員カメラ ON・10 分・3 回）の結果を軸に、次の順で当てはめる。

```
1. R6（6人・音声のみ）で A が赤か？
     YES → 結論 D（SFU へ移行）。音声すら守れない
     NO  → 2 へ

2. R8（6人・全員カメラ ON）で A が赤か？
     YES → 結論 D（SFU へ移行）。§3.6 の最優先である音声が映像に潰されている
     NO  → 3 へ

3. R8 で B / C / D のうち 2 カテゴリ以上が赤か？
   （または E1 が「6人中4人以上で自動停止が発動」）
     YES → 4 へ
     NO  → 結論 A（メッシュ据え置き。工数を画面共有へ）

4. R5（4人・全員カメラ ON）で B / C / D がすべて緑〜黄か？
     YES → 結論 B（VC_CAPACITY を 4 に下げる）
     NO  → 5 へ

5. R6（6人・音声のみ）で B / C / D がすべて緑〜黄か？
     YES → 結論 C（音声のみメッシュ。カメラ／画面共有は別経路を検討）
     NO  → 結論 D（SFU へ移行）
```

**赤の中身によって、SFU 以外の選択肢が残ることがある。** 結論 D を出す前に次を確認する。

| 赤だったカテゴリ  | SFU 以外の選択肢                                                                                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **B（CPU）だけ**  | SFU で確実に解決する（エンコードが 1 本になる）。**移行の効果が最も大きいケース**。B2 の実測値 ÷ 5 が移行後の見積もり                                                   |
| **C（帯域）だけ** | SFU でも上りは 1 本になるので効く。ただし**特定の 1 人だけ上りが細い**（第4.6節）なら、その人の回線の問題。全員が赤かを確認する                                         |
| **D（受信）だけ** | 下り 5 本はメッシュでも SFU でも変わらない（SFU も 5 本送ってくる）。**SFU では解決しない可能性がある。**simulcast / 解像度の切り替えが要る。SFU 移行の理由としては弱い |
| **C5 が赤**       | メッシュ特有の輻輳制御の食い合い。SFU で 1 本になれば消える。**メッシュ固有の症状としては最も明快な証拠**                                                               |

> **D だけが赤の場合は要注意。** 「SFU にすれば直る」は成り立たない。 受信 5
> 本はどちらでも同じであり、必要なのは解像度を落とす仕組みである。 このケースで SFU
> の工数を払うと、払った後も直らない。

倍）していればメッシュの構造が原因**である。

| 指標                        | 2人（1本） | 4人（3本） | 6人（5本） | 2人比（6人） | 本数比（5倍）との一致 |
| --------------------------- | ---------- | ---------- | ---------- | ------------ | --------------------- |
| エンコード占有率 合計（B2） |            |            |            |              |                       |
| 実効送信ビットレート 合計   |            |            |            |              |                       |
| ブラウザ CPU%（B4）         |            |            |            |              |                       |
| 最悪 RTT（C2）              |            |            |            |              |                       |
| 音声補間率（A1）            |            |            |            |              |                       |
| フリーズ回数/分（D1）       |            |            |            |              |                       |

| ---------------------------------------------- | ---------------------- |

## 7. 計測ツール（`vc-mesh-stats.html`）の使い方

### 7.1 なぜ「コンソールに貼るスニペット」なのか

**`vc.js` は変更しない**という制約があり、また `vc.js` が公開している `VC.getState()` は
**`RTCPeerConnection` オブジェクトそのものを返さない**（`connectionState` などの文字列だけ）。 `VC`
のどの公開 API からも生の `RTCPeerConnection` は取れない。

一方 `vc.js` はピアを `new global.RTCPeerConnection(...)`（`createPeer()`）で作っており、
**`window.RTCPeerConnection` を呼び出し時に参照している**。 そのため、**VC 参加前に
`window.RTCPeerConnection` を差し替えておけば**、
以後に作られる全ピアを捕まえられる。これが唯一の手段である。

また `docs/` はサーバーが配信しない（配信対象は `public/` のみ）ため、
計測ページはルーム画面と**別オリジン**（`file://` vs `http(s)://`）になる。
そのため計測ページからルーム画面の DOM や JS には直接触れない。 データの受け渡しは次の 2
通りで行う。

- **ライブモード**: 計測ページからルーム画面を `window.open()` で開き、 スニペットが
  `window.opener.postMessage()` でサンプルを送る（`postMessage` はオリジンをまたげる）
- **貼り付けモード**: スニペットが出力した JSON を、計測ページのテキスト欄に貼る

### 7.2 手順

1. `docs/testing/vc-mesh-stats.html` をブラウザで開く（`file://` で直接開いてよい）。
2. ルーム URL を入れて**［計測対象のルームを開く］**を押す。新しいタブでルーム画面が開く。
   - **この順番が必要。** ルーム画面を先に開くと `window.opener` が繋がらず、ライブモードにならない
     （貼り付けモードは使える）。
3. 開いたルーム画面で DevTools（F12）→ Console を開き、
   計測ページの**［収集スニペットをコピー］**で得たコードを貼って Enter。
   - `[vc-mesh] 収集を開始しました` と出れば成功
   - **VC に参加する前に実行すること**
4. ルームに入り、VC に参加してカメラを操作する。
5. 計測ページに戻ると、ピアごとの表が 2 秒おきに更新されている。
6. ウォームアップ 30 秒が過ぎたら**［計測開始］**。時間になったら**［計測停止］**。
7. **［CSV をコピー］**または**［JSON をコピー］**で結果を持ち出す。
8. **［判定］**欄に第5節の緑／黄／赤が出るので、第6.2節の表に転記する。

### 7.3 スニペットのコンソール API

スニペットは `window.__vcMesh` を作る。DevTools から直接叩ける。

| 呼び出し               | 動作                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `__vcMesh.status()`    | 捕捉したピア数・サンプル数を返す                            |
| `__vcMesh.csv()`       | 収集済みサンプルを CSV 文字列で返す                         |
| `__vcMesh.json()`      | 同じく JSON 文字列で返す                                    |
| `copy(__vcMesh.csv())` | クリップボードへコピー（`copy` は DevTools の組み込み関数） |
| `__vcMesh.stop()`      | 収集を止め、`RTCPeerConnection` を元に戻す                  |

計測ページを使わず、**スニペットだけで完結させることもできる**。 その場合は `copy(__vcMesh.csv())`
で CSV を取り、表計算ソフトで集計する。

### 7.4 ピアの識別について

スニペットは `RTCPeerConnection` の**生成順**（`pc#1`〜`pc#5`）でピアを区別し、 生成直後に
`VC.getState().peers` を読んで**あだ名の対応づけを試みる**。
ただしこれは推定であり、次の場合に外れることがある。

- 短時間に複数のピアが同時に立った（全員がほぼ同時に VC 参加した）
- 切断・再接続でピアが張り直された

**確実に識別したい場合**は、`candidate-pair` の相手アドレス（表の「相手」列）を使うか、 1
人ずつ順番に VC 参加してもらう。

## 8. 既知の限界

- **この測定は「参加者 6 人の実端末・実回線」でしか意味を持たない。** 同一 PC
  の複数窓、ボット、ヘッドレスでは「メッシュだから重い」を再現できない。
- **`getStats()` の項目はブラウザによって出ない。** Safari は `qualityLimitationDurations` /
  `freezeCount` などを出さないことがある。
  計測ツールは取れなかった項目を空欄（`-`）として扱い、**推測で埋めない**。
  空欄が多い端末は、判定を「測定不能」として扱う。
- **`vc.js` の品質ガードが破綻を隠す。** 自動停止が発動すると、そのピアの映像統計は
  そこで止まる。第5.6節（カテゴリ E）を必ず記録すること。
- **`availableOutgoingBitrate` は推定値であって実測ではない。** C5（推定の総和 vs
  実測上り）は、この推定が信用できない条件を炙り出すためにある。
- **本書の閾値は、RTT 以外すべて暫定値である。** `vc.js` 側も同じ断り書きを置いている。
  測定が終わったら、実測に照らして**閾値そのものを見直す**こと（第6.5節）。
- **TURN は未導入。** 現在は STUN（`stun:stun.l.google.com:19302`）のみ。 C7 が 0
  でない場合は環境の確認が要る。TURN 導入後は relay 経由の測定を別途行う。
- **バックグラウンドタブでは測定が壊れる。** Chrome はタイマーを間引くため、
  サンプル間隔が伸びて差分の分母が狂う。計測中はルーム画面を前面に置くこと。
