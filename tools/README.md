# tools

開発のための道具置き場。

| 場所 | 何をするもの |
| --- | --- |
| `corridor-layout-check.js` | 廊下の**間取り生成と卓の割り当て**を机上で測る |
| `corridor-harness/` | 廊下ビューを**ブラウザ抜きで実際に動かして**測る検証台 |
| `blender/` | 3D モデルのビルドスクリプトと、その取り決め（`blender/README.md`） |

**3D 関係を触ったら、この2つを両方走らせること。**どちらもブラウザを起動しない。

## `corridor-layout-check.js` — 間取りと卓の割り当て

```sh
deno run tools/corridor-layout-check.js      # 2秒ほど。権限は要らない
```

`corridor-view.js` の判定式を写して持っているだけの単体スクリプト。three.js も GLB も
読まないので、**間取りの理屈だけ**を速く回して確かめられる。

測れるもの:

1. **歩き回っての壁抜け** — 40万歩あるいて壁の中に入らないか、どこかに閉じ込められないか
2. **通路の形の割合** — 直線 / 角 / T字 / 十字 / 行き止まり
3. **1地点から見える扉の枚数の分布** — 「見える」は距離ではなく**視線**で決める
   （目から扉の板までの線分が塞がった辺を跨いだら見えない扱い）
4. **卓の重複** — 卓数 3 / 7 / 12 / 30 で、扉ごとに独立ハッシュを引いていた頃と
   いまのブロック連番方式を並べて比較する
5. **壁の穴** — 隅柱を GLB のまま1本だけ置いた場合と、四隅ぶん置いた場合の比較

**`P_STREET` / `P_SEGMENT` / `P_SHORTCUT` / `P_DOOR` を触るなら、必ずここで測ってから決めること。**
`P_SEGMENT` を 0.7 より下げると通路の網が千切れ、歩ける範囲が半分以下に落ちる。

いまの数値（変えたらここも直す）:

```
歩数 400000 / 訪れたマス 363 / 壁抜け 0
直線 29.1% / 角 10.3% / T字 22.1% / 十字 10.3% / 行き止まり 28.1%
1地点から見える扉 5489地点 / 平均 8.48枚 / 最大 25枚
卓 7: 下限 2.19 ／ 重複 3.68 → 3.12 ／ 隣り合う扉が同卓 14.8% → 5.3%
壁の穴: 隅柱1本 → 漏れ 767.0 m² ／ 四隅4本 → 漏れ 0.0 m²
```

## `corridor-harness/` — 廊下ビューの検証台

```sh
deno run --allow-read tools/corridor-harness/run.js    # 2秒ほど
```

**`deno task test` にも入っている**（`corridor_harness_test.js` が子プロセスで走らせる）。
2秒で終わるうえ、ここで見つかる類の壊れ方は**目視ではまず気づけない**ので、
毎回走るようにしてある。

### 何をしているか

**ブラウザを起動しない。**本物の three.js（`public/vendor/three/`）と本物の GLB
（`public/assets/3d/izakaya_corridor_kit.glb`）を Deno に読ませ、
`public/assets/3d/corridor-view.js` を**そのまま**動かす。

three.js の数学まわり（`Matrix4` / `Vector3` / `PerspectiveCamera` / `InstancedMesh`）は
DOM を要らないので Deno で動く。画面が要るのは `WebGLRenderer` だけなので、
**そこだけ偽物に差し替える**（`three-shim.js`）。偽レンダラは `render()` のたびに
シーンを辿って「実際に描かれる物の数」＝ドローコールを数える。

**`corridor-view.js` はコピーしない。**あちらの `import` はブラウザ向けの絶対パス
（`/vendor/three/...`）なので Deno では解決できないため、**その2行だけ**書き換えて
data URL として読む（`setup.js` の `loadCorridorView`）。
**検証台と本体がずれることが原理的に起きない。**

`requestAnimationFrame` は自動では回さず、1フレームずつ手で進める。おかげで
「`pause()` が rAF の予約そのものを消しているか」まで確かめられる
（フラグで描画を飛ばすだけの実装だと予約が残るので、そこで落ちる）。

### 測れるもの

| 項目 | 中身 |
| --- | --- |
| ドローコール | 400地点を歩いて最大値を測る。**22 以下**であること |
| 枠の溢れ | `InstancedMesh` に確保した枠を超えていないか（超えると部品が黙って欠ける） |
| **壁の穴** | 廊下から「見えてはいけない場所」へ抜けられないか。**漏れ 0** であること |
| `visibleDoors()` | 画面座標・前後（`behind`）・方位角（`bearing`）・距離・並び順 |
| 扉の `id` | 視点を振っても歩いて戻っても、同じ扉が同じ `id` を指し続けるか |
| 扉を押す | 当たり判定の枠番号 → 扉の対応。壁越しの扉を押せないこと |
| 決定性 | 遠くまで歩いて戻ったとき、間取りと卓の割り当てが一致すること |
| `pause` / `resume` | rAF の予約が消えて、また戻るか。二重呼びで壊れないか |
| `setInput` | 進む向き（前後・左右）、範囲外の値や `NaN` を渡したとき |
| `dispose` | rAF が止まるか。二重呼びで落ちないか |

### 壁の穴の測り方

目線の高さ（1.55m）の断面を 5cm の升目にして、廊下の起点から実体の無いところを
塗り広げ、「見えてよい場所」（通れるマスの通路断面と、開いた辺の連結部）の外へ
出られたら穴とみなす。

- 遮蔽物は**実際に scene へ置かれたインスタンスの行列から**組み立てる。
  つまり測っているのは理屈ではなく、コードが本当に置いた物
- 数えるのは**壁板（2.00 × 2.35 × 0.14）と隅柱（0.50 × 2.35 × 0.50）だけ**。
  扉の枠など内側にしか無い物は数えないので、判定が甘くならない（穴を見逃さない）
- 目線を横切る部品はどれも床から天井まで通っているので、この断面だけ見れば足りる
- 塗り広げは視線より広く回り込むため、**漏れ 0 なら「見えない」ことまで保証できる**

### アセット（GLB）を差し替えたら

**必ず両方走らせること。**壁板や隅柱の寸法が変わると、目では気づけない穴が開く。

`Kit_Core` は隅柱を **+X / -Z の1本しか持っていない**。マスの1辺は 3.00 だが壁板の幅は
通路と同じ 2.00 なので、マスの境目には幅 1.00 の区画が残り、その角を4つのマスが
0.50 ずつ分け合う形になる。柱が1本では**どの角も4分の1しか埋まらず**、
まっすぐな廊下でもマスの継ぎ目ごとに 0.5m 幅・天井まで届く縦穴が開く（実測 767 m²）。

そこで `corridor-view.js` は読み込み時に柱の三角形を `Kit_Core` から切り離し、
0 / 90 / 180 / 270° に置き直して四隅を埋めている。柱は名前でも並び順でもなく
**「三角形が 0.50 × 2.35 × 0.50 の箱に丸ごと入るか」**だけで特定しているので、
**柱の寸法や位置を変えると起動時に例外になる**（黙って穴が開くよりましなため）。
その場合は `corridor-view.js` の `POST_BOX` を測り直すこと。詳細は
`tools/blender/README.md` の「隅柱」を参照。
